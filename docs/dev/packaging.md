# External tools and packaging

The external solvers, how their paths resolve, install rules and the container image.

## External tools

- `ltl2tgba`, `ltlsynt`, `ltlfilt`, `autfilt`: SPOT, built at configure time by `cmake/spot.cmake` into `spot/` and found via the `SPOT_BIN_DIR` macro.
- `spot-forkserver`: those four tools linked into one binary that forks a child per call, built from `tools/spot-forkserver/` on Linux only and found via the `SPOT_SERVER_PATH` macro. It links the tool objects `cmake/spot_forkserver_objects.cmake` keeps under `spot/forkserver/`, which is why the Spot stamp carries `forkserver 1`: an install made without them fails the stamp and rebuilds once. It is statically linked against Spot, so it is installed beside `spot/bin` without a wrapper. A Spot upgrade relinks it, and the `spot_server_runner` suite replays a checked-in corpus through it against the execs. Read only under `runtime.spot_server`; see "Spot fork server" in `docs/dev/performance.md`. macOS builds make no server, and the key then warns and stays off.
- `black`: linear temporal logic (LTL) satisfiability checker, installed by `cmake/black.cmake` into `black/<version>-<flavour>/`. Always run it with a timeout, `black -t <seconds> ...`. The cache variable `PEREDUR_BLACK_FLAVOUR` is `auto` by default, or `path`, `deb` or `source`. `auto` takes a black on `PATH` only if its `--version` reports 25.09.0, else the prebuilt `.deb` on Linux x86_64 Ubuntu noble, else a source build; `path` requires such a black and fails configure otherwise. A source-built black's marker records the resolved real paths of libfmt and of its solver library, z3 or cryptominisat, and configure rebuilds it when those change or when `--version` fails, as after a Homebrew z3 upgrade removes the `libz3` it linked. Inside the Nix dev shell on macOS the source build hides the system environment path, so black links the dev shell's z3 and fmt instead of Homebrew's, the flake providing fmt on Darwin. Hiding that path hides `install_name_tool` too, and black's install then silently left an *rpath* into its deleted build tree, so the build passes `install_name_tool` explicitly.
- `ganak`: model counter, a release binary fetched by `cmake/ganak.cmake` into `ganak/<version>/`.
- `node`: runs the vendored FRET formaliser (`vendor/fretCLI.main.js`) for the tests and the fuzzer, found on `PATH` at run time and never fetched by CMake. Only `peredur_tests` and the fuzzer link `peredur_formaliser`.

`cmake/third_party.cmake` holds the install protocol the three tool modules share. Each tool installs at configure time, under `file(LOCK)`, into its own directory under `PEREDUR_THIRD_PARTY_DIR`. The lock lets several build trees share one third-party directory: a second configure waits, then finds the tool installed. An install ends by writing a *marker*, `.peredur-installed`, holding a stamp of the version and platform, plus the library paths above for a source-built black and `PEREDUR_FMT9_LIB_DIR` for the deb flavour. Configure trusts an installed tool only when the marker matches and `<tool> --version` exits 0 within 60 s; otherwise it deletes the directory and rebuilds. The marker replaced ExternalProject done-stamps, which survived interrupted builds, version bumps and library upgrades underneath the binary. An earlier Spot install whose done-stamp is present and whose binary runs is adopted by writing the marker, so it is not rebuilt. Downloads go to `downloads/` as a `.part` file, renamed only once its SHA-256 matches the pinned hash; a mismatch removes the `.part` and stops configure. Archives stay for later rebuilds, build logs go to `logs/<tool>-<version>/`, and build trees are deleted once installed. A tool path set with `-D`, such as `-DGANAK_EXECUTABLE=...`, is replaced with a warning, since the paths follow `PEREDUR_THIRD_PARTY_DIR`; the `PEREDUR_*` variables below point a built binary elsewhere at run time. A build reruns configure only when a CMake input changes, and neither `brew upgrade` nor a Nix garbage collection is one. The `tool_health` target covers that gap. It runs each tool's `--version` on every build and before `peredur_tests`, and on a failure it names the tool and touches `tools-stale.stamp`, a configure dependency, so the next build reconfigures and configure reinstalls the tool. With the cached ganak made non-executable, one build failed naming ganak, and the next reinstalled it and passed.

## Packaging

Five paths are compiled in as build-tree absolutes, and each yields to an environment override: `PEREDUR_SPOT_BIN_DIR`, `PEREDUR_SPOT_SERVER_PATH`, `PEREDUR_GANAK_PATH`, `PEREDUR_BLACK_PATH`, `PEREDUR_FORMALISER_SCRIPT`. `tool_path_from_env` (`src/runner/tool_paths.hpp`) is the one reader, and callers hold its result in a function-local `static`, since `getenv` races `setenv` across the scoring pool's threads. An empty value reads as unset, because shells and container runtimes export an unset variable as empty. The `external_tools` block of `run.json` records Spot, Ganak and black as resolved, whether the environment supplied each, and each tool's version line, and has a `spot_server` row with its path, `from_env` and whether the run used it. The formaliser is a test oracle that no binary runs, so it has no row.

Install with `--component peredur` (`cmake/install.cmake`): FetchContent's `add_subdirectory` imports the dependencies' install rules, so an unqualified install writes Eigen's headers and cpptrace's cmake config beside the binaries. Spot's binaries carry an absolute libtool RUNPATH into their build tree, so each is installed behind a wrapper (`cmake/tool-wrapper.sh.in`) setting `LD_LIBRARY_PATH` to a sibling `lib` resolved from `$0`. Without it the first `ltlsynt` call fails silently. On macOS the wrapper is not enough, because dyld ignores its `LD_LIBRARY_PATH` and follows absolute *install names* and rpaths, so an installed copy still loaded Spot's and black's libraries from the build machine's third-party tree. At install time on macOS, `cmake/relocate_macho.cmake`, run from `cmake/install.cmake`, rewrites each installed *Mach-O* file's references into `PEREDUR_THIRD_PARTY_DIR` relative to `@loader_path` and ad-hoc re-signs the file, since arm64 macOS refuses to run a binary whose signature `install_name_tool` invalidated. The `.dylib` files are installed beside the binaries. black's z3 and fmt are not shipped, so a macOS install runs only where those libraries exist at the same paths. A `--component peredur` install, moved to a new prefix with `peredur-env.sh` sourced, ran `realize` on an example, and no installed file referred to the third-party tree.

`Config::parallel` defaults to `available_parallelism()` (`include/thread_pool.hpp`), the minimum of `hardware_concurrency()`, the `sched_getaffinity` count and the cgroup CPU quota, each skipped when unreadable and floored at 1. `hardware_concurrency()` ignores `--cpuset-cpus` and `--cpus`, so a `--cpus=4` run on a 64-core host sized its pool at 64. The cgroup parsers are pure functions in `src/cpu_limits.hpp` so they can be tested.

`-DPEREDUR_GIT_COMMIT=<sha>` (`cmake/version.cmake`) names the commit for a build from a source copy, which is how the image is built. It takes the full 40 characters and fills in only what git cannot answer: a disagreement with git fails the build, and `PEREDUR_GIT_DIRTY` can set the dirty flag but never clear one git set. Without it the build reports `commit=unknown` and `run_experiments.py` refuses to launch.

The Dockerfile has one stage per fetched dependency, each copying only its own cmake module, so Spot's layer is keyed on `cmake/spot.cmake` alone; Spot takes 248.1s to build against black's 3.6s at `BUILD_JOBS=8`. `docs/docker.md` is the user-facing half.

`.github/workflows/docker.yml` builds each architecture on a native runner, loads the image into the runner's daemon, runs `scripts/docker_smoke.sh` on it, and only then pushes by digest under no tag. A push-by-digest build leaves no local image to run, so the smoke test needs the separate `load: true` build, and the push step replays it from the builder's cache. A local build goes through `scripts/docker_build.sh`, which sets `PEREDUR_GIT_DIRTY` from the working tree; the Dockerfile's default of `false` holds only for CI's clean checkout. Only the merge job's `imagetools create` tags, so a half-failed matrix cannot publish one architecture alone. `cmake/black.cmake`'s architecture guard must cover only the prebuilt `.deb`: around the whole Linux branch it fails arm64 configure instead of falling through to the source build, which an amd64 build will not show.
