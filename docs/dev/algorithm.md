# Search pipeline

How a `peredur` run proceeds from input to `run.json`, and the design record behind its search budget, output and dashboard.

## Algorithm flow (`peredur`)

1. Load `Specification` from `--input` JSON.
2. Build `AggregateWeightedFitnessFunction` (syntactic + semantic + status) and the per-generation `FilterFunction` list from the original spec. Correctness stages come from a shared table, `correctness_checks` (`include/filter/correctness.hpp`), instantiated once per front end, with one stage per row whose `per_generation` bool is set: true for `vacuity`, false for `not-well-separated`. No correctness stage can be switched off from a config. The same table screens the input once at load time and warns rather than rejects, because an ill-separated FRETISH input is realizable outright and rejecting it would foreclose a *descendant* that fixes the property; the verdict is `input_screen` in `run.json` (null when every check passed). The `status` objective scores on the three-point scale in `include/fitness/status.hpp`: 0 for a component unsatisfiable on its own, `k_status_realizable` (1.0) for realizable *and* well-separated, `k_status_unrealizable` (0.5) for everything between, with the well-separation query asked only behind the realizability one. A candidate realizable only by defeating its own assumptions scores level with an unrealizable one, because an intermediate tier would rank cheating above failing and, ill-separation being cheap to reach and expensive to leave, would become a plateau. `status_grading = "tiered"` and `"mrs"` both do this; `"aurus"` reproduces AuRUS's six-level ladder (0, 0.05, 0.1, 0.2, 0.5, 1.0) value for value and folds in no well-separation query, since AuRUS asks none in its search. Grading changes the search's scoring alone; the step-5 gate asks every correctness row regardless.
3. Seed an RNG (from `--seed` or `std::random_device`); register crash metadata.
4. Run `Config::generations` rounds of `evolve_generation`: crossover + mutation, filter the offspring (dedup, bloat cap, vacuity), then score the survivors in a thread pool. `vacuity` runs unconditionally and tests cheapest-first: a syntactic screen (a `false` condition, plus the TLSF section-literal equivalents), a per-guarantee validity check, then the assumption-satisfiability conjunction. Only the guarantee side splits per formula, because validity distributes over conjunction and unsatisfiability does not (`G p` and `G !p` are each satisfiable, jointly not); the per-requirement cache key keeps added solver calls near zero after the first generation. FRETISH has no syntactic test for a `true` guarantee response, because `expand_after` negates the response and under `AfterTicks` a `true` response is the strongest guarantee expressible. Filters run *before* scoring, so a dropped candidate never costs a model count or synthesis query, and filter solver calls warm the caches scoring hits. A stage re-testing a filter's predicate on a population that filter already judged is therefore dead code. For the same reason there is no per-generation well-separation stage: it dropped ill-separated candidates before scoring, so the 0.5 tier never fired, as the old assumption-side tier sat unreachable behind the vacuity filter (`a64f833`, 887k scored candidates). The one deliberate re-test is the filter fallback: when the chain empties the offspring, it re-applies the `FilterKind::Correctness` filters alone to the *unfiltered* offspring, which dedup and the bloat cap had shadowed from them. That re-admits duplicates and oversized candidates but none dropped as unfit; with no correct offspring the elites carry the generation, and only an elite-free run restores them unscreened. The untagged filter default is `Correctness`, so a forgotten tag costs a wasted re-test rather than a re-admitted bad candidate. Selection follows `Config::selection_scheme`. Both NSGA-II schemes rank by non-dominated sorting + crowding distance (`include/genetic/nsga2.hpp`) with (μ+λ) pooling and differ only in the survivor step: `Nsga2Truncate` (`nsga2-truncate`) truncates the pool at `population_size`, while `Nsga2Apportion` (`nsga2-apportion`, the default since `c71ecf0`) deduplicates the pool and apportions slots over distinct survivors by `1 / (1 + rank)`. `WeightedAverage` converges prematurely and is kept for comparison only. The old spellings `nsga2` and `nsga2-replicate` are rejected rather than aliased (see "Selection scheme rename"). The scored population carries both the per-objective vector and the weighted scalar (`Scored<Spec>`).
5. Collect the realizable survivors from the final population (re-checked with `black` + `ltlsynt`). This gate is the enforcement point: it asks the status query on the run's own `status_grading`, then every correctness-table row unconditionally, in one conjunct order on both paths. `per_generation` governs search pressure alone, so nothing enforced during the search is dropped at the output, which closes the elite and seed-population leak. Well-separation goes last, being the one row not already memoised by the search. Adding a `FilterKind::Correctness` filter means adding a table row, or the gate never sees it; the `correctness` test suite asserts a matching row for every such generation stage, by name and on both paths.
6. Apply final filters over what the gate returned: dedup, then the optional implication filter to keep only maximal specs. Mutual implication keeps one side, the one with higher syntactic similarity to the original, with `Specification::operator<` breaking ties, because equivalent specifications are one repair written two ways; the total order keeps a fixed seed reproducible under concurrent checks. A timed-out check reads as non-implication, so an unproven equivalence keeps both sides. `n_equivalent_collapsed` counts collapsed pairs. FRETISH `spec_implies` lowers the whole specification to one LTL formula, as `tlsf_spec_implies` does; the per-requirement check it replaced missed implications holding only through several requirements together. Both changes move `n_repairs` and `n_implies` (and `compare` and `lint_ideals`) out of comparability with archived rows: over 25 paired FRETISH runs `n_repairs` fell 17.8% while `n_accumulated_repairs` and `implies_ideal` did not move. The final filters use their own `SatisfiabilityChecker` with `set_simplify(false)` and SPOT's budget raised to `black_timeout`, because on whole-specification queries `ltlfilt --simplify` took 96.7% of solver time on humanoid-531 and the 500ms `k_spot_budget` left queries undecided, which never escalate under `ExpectUnsat` and so read as "keep both". The per-generation checker keeps both settings, which help its single-requirement queries (`src/runner/black.cpp`); `maximal` and `compare` use the final-filter settings. No weakening screen sits before the implication filter: turning it off gained `implies_ideal` on 38 of 720 matched runs and lost none (`experiments/2026-08-20-ops-weakening`). Wherever `accumulate_repairs` and `run_implication` are both on (and on TLSF, `repair_mode = "monolithic"`), the implication filter runs *during* the search: a coordinator merges queued accumulated repairs into the maximal set batch by batch on the thread pool's background queue, and `accumulated/maximal.tsv` names the current maximal files. It reaches the same antichain as a batch sweep wherever no check times out but asks different pairs, so `implication.comparisons` and `skipped` do not compare with a batch run's. There is no config key for the route, a change moving cost and no output getting one code path. See `docs/configuration.rst`.
7. Score, sort, and write each maximal spec to `<output-dir>/repair_N.json`, then the run manifest to `<output-dir>/run.json` (see "Run output").

## Elitism

`elitism_rate` defaults to 0.1, although both standing arguments point at 0: the (μ+λ) survivor step already keeps the best parents, and elites bypass the offspring filter chain, costing search pressure though not output correctness since the step-5 gate screens them (`d7733fc`). A TLSF yield advantage for 0 (McNemar p = 0.0002, `experiments/2026-08-07-elitism`) did not replicate at `nsga2-apportion` over 500 paired TLSF runs in `experiments/2026-08-23-monotone` (exact McNemar p = 1.0000), which measured 4.0% more wall time at 0; only 0 and 0.1 have been measured. `golden_config()` in `test/genetic/determinism_tests.cpp` pins the key, so a default move fails the determinism suite rather than re-recording itself.

## Termination modes

Three keys give PEREDUR and AuRUS the same search budget: `[genetic] termination` (`"generations"`, the default, or `"individuals"`), `max_individuals` (0) and `max_wall_s` (0), all no-ops at those values. AuRUS's `GeneticAlgorithm.java` stops mid-generation once `numberOfVisitedIndividuals` reaches `GA_MAX_NUM_INDIVIDUALS` (1000), counting once per new mutant and once per crossover offspring. That is 1000 *bred individuals*, never 1000 solutions: the counts sit inside the breeding loops, and none of 600 archived `2026-08-14-aurus-h2h` runs reached 1000 solutions. The GECCO '23 paper does not say how an individual is counted, so `SearchBudget` is a code-level match and should be described as one.

An offspring counts only where it differs from its parent, as in AuRUS. The budget is checked inside `breed_offspring` (`include/genetic/pipeline.hpp`) between slots and at the head of each driver's generation loop, because a boundary check alone would overshoot by up to 20% of a 1000-individual cap at population 200. `SearchBudget` is owned by the driver and passed by reference through `run_evolution` (FRETISH) and `tlsf::run_repair` → `run_monolithic`/`run_muc` → `evolve_population` (TLSF). It must belong to the run rather than the core, because `run_muc` restarts its generation count per core and a per-core budget would multiply the cap by `muc_max_iterations`.

`scripts/gen_configs.py` emits `--termination` and `--max-individuals` only away from their no-op values, so existing grids stay byte-identical, and both keys are in `GEN_CONFIGS_FIELDS` in `scripts/check_config_schema.py`, a fifth site beyond the four in "Config keys". Matching AuRUS also needs `--population-size 100`, as the `matched` profile in `run_experiments.py` does; `generations` must stay well above what the cap needs (at least 12 at population 100), and `stopped_by` reading `generations` means a campaign measured a different budget.

`max_wall_s` works under either mode. A run stopping on its own deadline writes its repairs and `run.json`, where a harness kill writes neither. Nothing interrupts filters, scoring or the final gate, so runs overrun: `2026-08-28-selection-grading` cost 2.2x its predicted compute-hours. Size a deadlined campaign at roughly 2.2x the cap and set `timeout_caps` well clear of that. `accumulated/index.tsv` is closed per repair, so discovery curves survive a harness kill. Because `max_wall_s` makes output machine-dependent, do not set it in a seed-paired comparison unless the pairing is on the arm rather than the seed.

Manifest schema version 21 adds `stopped_by` (`generations`/`individuals`/`deadline`), `generations_run` and `individuals_bred`, the last null when the budget is inactive so that it is not mistaken for a real zero. `SearchBudget::active()` is false at the defaults, so breeding does no parent comparison or clock read and the `RandomSource` draw stream and determinism goldens are unchanged.

## Run output

stdout shows a run in progress: the per-generation status line, the filter report, the scoring report, and the closing `Done in`. Engine-internal counters print only under `--diagnostics`, and every figure in them, plus `wall_s`, the effective config and the commit, is in `<output-dir>/run.json`, which is what a campaign should read. Adding a counter to `print_diagnostics_report` means adding it to `write_run_manifest` and bumping `k_schema_version` (now 30). A new config key must likewise join `k_config_keys` in `src/config/keys.hpp`, from which `config_json` in `src/repair/manifest.cpp` writes it, as well as the schema and `example-config.toml`; `scripts/check_config_schema.py` checks they match. The scoring report must keep printing unconditionally, because `run_experiments.py` parses `"N individual(s) dropped"` out of the log.

Anything that moves the cursor must go through `stdout_is_tty()` (`include/status_line.hpp`), because runs are usually redirected to `<output-dir>/run.log` and unguarded `\r`/`\033[J` keeps every frame (59KB of escape codes for 1.2KB of content). `StatusLine` columns may be *transient*, shown live but dropped from the committed line.

Report "best fitness" as the population maximum, never `population[0]`/`front()`. NSGA-II orders the population by front rank and crowding distance, so the leading individual need not have the highest weighted scalar and the printed best would fall while the search improves (`src/repair/evolution.cpp`, `src/tlsf/evolve.cpp`).

`peredur` rejects unknown arguments (`find_unknown_arg`), so a new flag must be added to the table in `src/main.cpp`.

## Live dashboard

Opt-in, via `peredur --dashboard` or `[runtime] dashboard = true`, so campaigns do not pay for it. When on, both drivers stream to `<output-dir>/progress.jsonl` and copy `web/dashboard.html` there as `index.html`; watch with `python3 -m http.server -d <output-dir> 8000`. The page polls once a second, overridden by `?poll=<seconds>` (`?poll=0` loads once).

Each `stage` record carries `distinct`, the number of distinct specifications among the survivors, which measures whether a selection scheme keeps diversity. Computing it hashes the population, so `run_generation_pipeline` does so only when an observer is attached.

Everything above the page script's `boot()` call must be free of DOM access at load time: `boot()` runs only when `document` exists, and otherwise the script exports its functions for `test/web/`. A top-level `document.getElementById` breaks the JS tests.

The page derives its stage list from the latest generation's `stage` records, so new stages need no change to either side. `make_generation_pipeline` (`include/genetic/pipeline.hpp`) returns named `PipelineStage`s, and `run_generation_pipeline` reports each to an optional `StageObserver`. Breeding must stay a single stage, because crossover and mutation interleave per offspring slot and splitting them reorders the RNG draws; the `determinism` suite pins the draw stream.

Two calls that both draw from the `RandomSource` must never be arguments of the same call, because gcc and clang evaluate arguments in opposite orders and seeds stop reproducing across compilers. Sequence each draw into its own local (as `rewrite_post_order` does); the CI gcc job catches this, the goldens being pinned under clang.

## TLSF repair modes

Binaries: `peredur` (genetic repair), `realize`, `compare`, `ltl`, `mucs`, `maximal`; run each with `--help` for flags.

`mucs` prints a *minimal unrealizable core* (MUC): the smallest subset of the guarantee-side sections (PRESET, ASSERT, GUARANTEE) that stays unrealizable against the full environment side (INITIALLY, REQUIRE, ASSUME). It uses QuickXplain over `ltlsynt`, prints `REALIZABLE (no core)` for a realizable input, and is TLSF-only.

`Config::repair_mode` (TOML `[tlsf] repair_mode = "monolithic" | "muc"`, default `monolithic`) selects between evolving the whole spec and the MUC-guided loop in `run_muc` (`src/tlsf/repair_modes.cpp`): extract a core, evolve it, reintegrate it with the non-core guarantees (`tlsf::reintegrate`), and repeat until realizable or `muc_max_iterations` trips. The key is TLSF-only, and a FRETISH run carrying it exits 1 rather than evolving monolithically under a manifest that records `muc`. `scripts/gen_configs.py --repair both` and the `muc` profile in `run_experiments.py` cross the two modes.

Every reintegrated candidate that passes the output gate is a repair of the whole specification, so `run_muc` gates the core's whole survivor set rather than its best member, feeds each one to the accumulator and the streaming maximality filter, and returns the deduplicated union. `extract_muc` pre-screens the singletons concurrently before QuickXplain's serial walk, which warms the realizability memo with the queries that walk is about to repeat, and counts the probes `ltlsynt` left undecided. A non-zero count means the core rests on queries that never answered: `run_muc` and `mucs` both print it and call the core provisional, since a subset read as unrealizable on a timeout may not be one.

## Key types

- `Timing` — `std::variant<Immediately, NextTimepoint, WithinTicks, ForTicks, AfterTicks, Eventually, Always, Until, Before>` (see `requirement.hpp`). `Until` and `Before` hold a propositional stop condition `s`.
- `ConditionType` — `enum class { Trigger, Continual }`: the condition activates a `Requirement` on its rising edge (Trigger) or wherever it holds (Continual).
- `Requirement` — holds `m_condition`, `m_response`, `m_timing`, `m_condition_type`, the derived `m_ltl` string, and `m_weakenable`. A requirement with `m_weakenable` false is locked: never mutated, used as a crossover source, or simplified. The flag is part of `Requirement`'s identity (`operator<`/`==`/`hash`) and serialises as the optional JSON key `weakenable`, emitted only when `false`. `m_removed` is the removal tombstone (see "Removable guarantees").
- `Formula` — propositional AST with `syntactic_similarity`, `rewrite_post_order`, `n_subformulae`.
- `TransferSystem` — weighted automaton transition matrix for bounded model counting.
- `Count` — `long double` (x87 80-bit: integers exact to 2^64, exponent range to 2^16384). Trace counts are consumed only as ratios cast to `double`, so range matters more than integer width; `count_add_overflow`/`count_mul_overflow` report overflow as a non-finite result.
