# Search pipeline

How a `peredur` run proceeds from input to `run.json`, and the design record behind its search budget and output.

## Algorithm flow (`peredur`)

1. Load `Specification` from `--input` JSON.
2. Build `AggregateWeightedFitnessFunction` (syntactic + semantic + status) and the per-generation `FilterFunction` list from the original spec. Correctness stages come from a shared table, `correctness_checks` (`include/filter/correctness.hpp`), instantiated once per front end, with one stage per row whose `per_generation` bool is set: true for `vacuity`, false for `not-well-separated`. No correctness stage can be switched off from a config. The same table screens the input once at load time and warns rather than rejects, because an ill-separated FRETISH input is realizable outright and rejecting it would foreclose a *descendant* that fixes the property; the verdict is `input_screen` in `run.json` (null when every check passed). The `status` objective scores on the MRS scale in `include/fitness/status.hpp` by default: 0 for a component or a whole specification that is unsatisfiable, and otherwise the fraction of guarantee-side parts a greedy walk keeps realizable *and* well-separated, with the well-separation query asked only behind the realizability one. A part kept only by defeating the candidate's own assumptions is rejected, because a score just below 1.0 would rank cheating above failing and, ill-separation being cheap to reach and expensive to leave, would become a plateau. `status_grading = "aurus"` reproduces AuRUS's six-level ladder (0, 0.05, 0.1, 0.2, 0.5, 1.0) value for value and folds in no well-separation query, since AuRUS asks none in its search. Grading changes the search's scoring alone; the step-5 gate asks every correctness row regardless.
3. Seed an RNG (from `--seed` or `std::random_device`); register crash metadata.
4. Run `Config::generations` rounds of `evolve_generation`: crossover + mutation, filter the offspring (dedup, bloat cap, vacuity), then score the survivors in a thread pool. `vacuity` runs unconditionally and tests cheapest-first: a syntactic screen (a `false` condition, plus the TLSF section-literal equivalents), a per-guarantee validity check, then the assumption-satisfiability conjunction. Only the guarantee side splits per formula, because validity distributes over conjunction and unsatisfiability does not (`G p` and `G !p` are each satisfiable, jointly not); the per-requirement cache key keeps added solver calls near zero after the first generation. FRETISH has no syntactic test for a `true` guarantee response, because `expand_after` negates the response and under `AfterTicks` a `true` response is the strongest guarantee expressible. Filters run *before* scoring, so a dropped candidate never costs a model count or synthesis query, and filter solver calls warm the caches scoring hits. A stage re-testing a filter's predicate on a population that filter already judged is therefore dead code. For the same reason there is no per-generation well-separation stage: it dropped ill-separated candidates before scoring, so the 0.5 tier never fired, as the old assumption-side tier sat unreachable behind the vacuity filter (`a64f833`, 887k scored candidates). The one deliberate re-test is the filter fallback: when the chain empties the offspring, it re-applies the `FilterKind::Correctness` filters alone to the *unfiltered* offspring, which dedup and the bloat cap had shadowed from them. That re-admits duplicates and oversized candidates but none dropped as unfit; with no correct offspring the elites carry the generation, and only an elite-free run restores them unscreened. The untagged filter default is `Correctness`, so a forgotten tag costs a wasted re-test rather than a re-admitted bad candidate. Selection follows `Config::selection_scheme`. `Nsga2Apportion` (`nsga2-apportion`, the default since `c71ecf0`) ranks by non-dominated sorting + crowding distance (`include/genetic/nsga2.hpp`) with (μ+λ) pooling, deduplicates the pool and apportions slots over distinct survivors by `1 / (1 + rank)`; `Nsga2Truncate`, which truncated the pool at `population_size`, was removed on 2026-10-30. `WeightedAverage` converges prematurely and is kept for comparison only. The old spellings `nsga2`, `nsga2-replicate` and `nsga2-truncate` are rejected rather than aliased (see "Selection scheme rename"). The scored population carries both the per-objective vector and the weighted scalar (`Scored<Spec>`). On the FRETISH path `maximality_demotion` adds one rule to the NSGA-II ranks (see "Maximality demotion").
5. Collect the realizable survivors from the final population (re-checked with `black` + `ltlsynt`). This gate is the enforcement point: it asks the status query on the run's own `status_grading`, then every correctness-table row unconditionally, in one conjunct order on both paths. `per_generation` governs search pressure alone, so nothing enforced during the search is dropped at the output, which closes the elite and seed-population leak. Well-separation goes last, being the one row not already memoised by the search. Adding a `FilterKind::Correctness` filter means adding a table row, or the gate never sees it; the `correctness` test suite asserts a matching row for every such generation stage, by name and on both paths.
6. On FRETISH with `[filters] climb_output` on (off by default), first climb each gated repair towards the original: take proved one-step strengthenings while the result passes the step-5 gate again, and replace the repair with where the climb stops (see "Output climb" in `docs/dev/operators.md`). Then apply final filters over what the gate and the climb returned: dedup, then the optional implication filter to keep only maximal specs. Mutual implication keeps one side, the one with higher syntactic similarity to the original, with `Specification::operator<` breaking ties, because equivalent specifications are one repair written two ways; the total order keeps a fixed seed reproducible under concurrent checks. A timed-out check reads as non-implication, so an unproven equivalence keeps both sides. `n_equivalent_collapsed` counts collapsed pairs. FRETISH `spec_implies` lowers the whole specification to one LTL formula, as `tlsf_spec_implies` does; the per-requirement check it replaced missed implications holding only through several requirements together. Both changes move `n_repairs` and `n_implies` (and `compare` and `lint_ideals`) out of comparability with archived rows: over 25 paired FRETISH runs `n_repairs` fell 17.8% while `n_accumulated_repairs` and `implies_ideal` did not move. The final filters use their own `SatisfiabilityChecker` with SPOT's budget raised to `black_timeout`, because the 500ms `k_spot_budget` left whole-specification queries undecided, which never escalate under `ExpectUnsat` and so read as "keep both". The per-generation checker keeps the 500ms budget for its single-requirement queries; `maximal` and `compare` use the final-filter setting. No checker runs `ltlfilt --simplify` before deciding: on whole-specification queries it took 96.7% of solver time on humanoid-531, and on the search's own queries it cost 8x the `--satisfiable` call it preceded (`src/runner/black.cpp`). No weakening screen sits before the implication filter: turning it off gained `implies_ideal` on 38 of 720 matched runs and lost none (`experiments/2026-08-20-ops-weakening`). Wherever `run_implication` is on, the implication filter runs *during* the search: a coordinator merges queued accumulated repairs into the maximal set batch by batch on the thread pool's background queue, and `accumulated/maximal.tsv` names the current maximal files. It reaches the same antichain as a batch sweep wherever no check times out but asks different pairs, so `implication.comparisons` and `skipped` do not compare with a batch run's. There is no config key for the route, a change moving cost and no output getting one code path. See `docs/configuration.rst`.
7. Score, sort, and write each maximal spec to `<output-dir>/repair_N.json`, then the run manifest to `<output-dir>/run.json` (see "Run output").

## Elitism

`elitism_rate` defaults to 0.1, although both standing arguments point at 0: the (μ+λ) survivor step already keeps the best parents, and elites bypass the offspring filter chain, costing search pressure though not output correctness since the step-5 gate screens them (`d7733fc`). A TLSF yield advantage for 0 (McNemar p = 0.0002, `experiments/2026-08-07-elitism`) did not replicate at `nsga2-apportion` over 500 paired TLSF runs in `experiments/2026-08-23-monotone` (exact McNemar p = 1.0000), which measured 4.0% more wall time at 0; only 0 and 0.1 have been measured. `golden_config()` in `test/genetic/determinism_tests.cpp` pins the key, so a default move fails the determinism suite rather than re-recording itself.

## Maximality demotion

`[genetic] maximality_demotion` (default `false`) moves a realizable candidate one front down when another realizable candidate in the pool is proved strictly stronger. It acts under `nsga2-apportion` on the FRETISH path only, because the TLSF path has no `requirement_implies`. A weaker timing or a removed guarantee costs nothing on similarity and gains on status, so without the rule a gutted repair sits on the first front beside the repair it weakens (see "Timing donation" and "Removable guarantees" in `docs/dev/operators.md`).

A candidate is *realizable* here when its status objective reads `k_status_realizable` (1.0). Under MRS grading that is the top tier, and a partial walk score below it is never read as realizable. Y is *proved stronger* than X when `spec_implies_by_rule` (`include/filter/implication_check.hpp`) proves Y ⇒ X. Each live guarantee of X must match a live guarantee of Y by lowering, or be implied by Y's guarantee in the same slot under `requirement_implies`. Each live assumption of Y must be covered by X's assumptions in the same way. A tombstone is a `true` requirement, so it needs no cover and covers nothing. Y is *strictly* stronger when the converse is not also proved. The proof uses rules alone, launches no process and cannot time out, so an unproven pair is left alone. Equal slots are settled by a string comparison before any rule runs, and `requirement_implies` is memoised per pair of lowerings within one ranking.

The demotion adds one to the rank the non-dominated sort gave the candidate, before crowding distance is measured. A demoted candidate therefore competes for crowding inside the front it lands in, and the `1 / (1 + rank)` apportionment reads the demoted rank, so a demoted front-0 candidate gets weight 1/2 where it had 1. It moves one front and does not cascade: a candidate the demoted one dominates on the objectives keeps its own front. The flags depend on the pool as a set, and no proof draws from the `RandomSource`, so selection stays a deterministic function of the pool.

The rule is applied at survivor selection and again when the next generation orders its parents (`stage_order_parents`, `include/genetic/pipeline.hpp`). Without the second pass the re-sort would restore a demoted candidate's old front, and it would breed and stand as an elite from there. Only the survivor step counts its demotions, as `n_maximality_demotions` in `run.json` (schema 51) and in the `--diagnostics` report. At the default no flag is computed, so the population and the draw stream match a run from before the key existed, and `golden_config()` pins the key at `false`.

The rule's cost was measured on `examples/fsm-combined/spec.json` at `population_size = 200` and `generations = 10`, seeds 1 to 3, on the debug build (address and undefined-behaviour sanitisers on), through the `select/demotion` site of `PEREDUR_PROFILE`. Over the 20 calls a run makes (10 survivor selections and 10 parent orderings), seeds 1, 2 and 3 spent 0.78 s, 0.21 s and 0.13 s in the pass, against run wall times of 15.9 s, 11.3 s and 11.3 s. That is 4.9%, 1.8% and 1.1% of the run, and the slowest single call took 0.24 s. The three runs demoted 64, 60 and 24 candidates. Whole-run wall time does not isolate the cost, since the two arms run different searches once the first demotion lands: the off arm took 7.0 s, 13.2 s and 11.5 s on the same seeds. Whether the rule improves `implies_ideal` or the maximality rescore wants a campaign against plain NSGA-II.

## Termination modes

Three keys give PEREDUR and AuRUS the same search budget: `[genetic] termination` (`"generations"`, the default, or `"individuals"`), `max_individuals` (0) and `max_wall_s` (0), all no-ops at those values. AuRUS's `GeneticAlgorithm.java` stops mid-generation once `numberOfVisitedIndividuals` reaches `GA_MAX_NUM_INDIVIDUALS` (1000), counting once per new mutant and once per crossover offspring. That is 1000 *bred individuals*, never 1000 solutions: the counts sit inside the breeding loops, and none of 600 archived `2026-08-14-aurus-h2h` runs reached 1000 solutions. The GECCO '23 paper does not say how an individual is counted, so `SearchBudget` is a code-level match and should be described as one.

An offspring counts only where it differs from its parent, as in AuRUS. The budget is checked inside `breed_offspring` (`include/genetic/pipeline.hpp`) between slots and at the head of each driver's generation loop, because a boundary check alone would overshoot by up to 20% of a 1000-individual cap at population 200. `SearchBudget` is owned by the driver and passed by reference to `run_generations` (`src/genetic/generation_loop.hpp`), the one generation loop both paths run.

`scripts/gen_configs.py` emits `--termination` and `--max-individuals` only away from their no-op values, so existing grids stay byte-identical, and `scripts/check_config_schema.py` holds both to the binary's defaults. Matching AuRUS also needs `--population-size 100`, as the `matched` profile in `run_experiments.py` did until `c704970` retired it; `generations` must stay well above what the cap needs (at least 12 at population 100), and `stopped_by` reading `generations` means a campaign measured a different budget.

`max_wall_s` works under either mode. A run stopping on its own deadline writes its repairs and `run.json`, where a harness kill writes neither. Nothing interrupts filters, scoring or the final gate, so runs overrun: `2026-08-28-selection-grading` cost 2.2x its predicted compute-hours. Size a deadlined campaign at roughly 2.2x the cap and set `timeout_caps` well clear of that. `accumulated/index.tsv` is closed per repair, so discovery curves survive a harness kill. Because `max_wall_s` makes output machine-dependent, do not set it in a seed-paired comparison unless the pairing is on the arm rather than the seed.

Manifest schema version 21 adds `stopped_by` (`generations`/`individuals`/`deadline`), `generations_run` and `individuals_bred`, the last null when the budget is inactive so that it is not mistaken for a real zero. `SearchBudget::active()` is false at the defaults, so breeding does no parent comparison or clock read and the `RandomSource` draw stream and determinism goldens are unchanged.

## Run output

stdout shows a run in progress: the per-generation status line, the repair count, the scoring report, and the closing `Done in`. Under `--repair-summary` the count is followed by what each repair changed (`tlsf::write_changes` on the TLSF path, `print_repair_changes` in `src/repair/evolution.cpp` on the FRETISH one). The filter report and the engine-internal counters print only under `--diagnostics`, and every figure in them, plus `wall_s`, the effective config and the commit, is in `<output-dir>/run.json`, which is what a campaign should read. Adding a counter to `print_diagnostics_report` means adding it to `write_run_manifest` and bumping `k_schema_version`. A new config key must likewise join `k_config_keys` in `src/config/keys.hpp`, from which `config_json` in `src/repair/manifest.cpp` writes it and the schema and `example-config.toml` are generated. The scoring report must keep printing unconditionally, because `run_experiments.py` parses `"N individual(s) dropped"` out of the log.

Anything that moves the cursor must go through `stdout_is_tty()` (`include/status_line.hpp`), because runs are usually redirected to `<output-dir>/run.log` and unguarded `\r`/`\033[J` keeps every frame (59KB of escape codes for 1.2KB of content). `StatusLine` columns may be *transient*, shown live but dropped from the committed line.

Report "best fitness" as the population maximum, never `population[0]`/`front()`. NSGA-II orders the population by front rank and crowding distance, so the leading individual need not have the highest weighted scalar and the printed best would fall while the search improves (`run_generations` in `src/genetic/generation_loop.hpp`).

`peredur` rejects unknown arguments (`find_unknown_arg`), so a new flag must be added to the table in `src/main.cpp`.

## Generation pipeline

`make_generation_pipeline` (`include/genetic/pipeline.hpp`) returns named `PipelineStage`s, and `run_generation_pipeline` reports each to an optional `StageObserver`, through which the `pipeline` suite reads every stage's name and population sizes. Breeding must stay a single stage, because crossover and mutation interleave per offspring slot and splitting them reorders the RNG draws; the `determinism` suite pins the draw stream. FRETISH mutation receives a `ParentContext` per offspring, built from the parent's `Scored` entry without a draw, and the original specification by pointer through `GenerationContext::m_original` (see "Blame-targeted slot choice" in `docs/dev/operators.md`).

Two calls that both draw from the `RandomSource` must never be arguments of the same call, because gcc and clang evaluate arguments in opposite orders and seeds stop reproducing across compilers. Sequence each draw into its own local (as `rewrite_post_order` does); the CI gcc job catches this, the goldens being pinned under clang.

## TLSF repair modes

Binaries: `peredur` (genetic repair), `realize`, `compare`, `ltl`, `mucs`, `maximal`; run each with `--help` for flags.

`mucs` prints a *minimal unrealizable core* (MUC): the smallest subset of the guarantee-side sections (PRESET, ASSERT, GUARANTEE) that stays unrealizable against the full environment side (INITIALLY, REQUIRE, ASSUME). It uses QuickXplain over `ltlsynt`, prints `REALIZABLE (no core)` for a realizable input, and is TLSF-only.

TLSF repair evolves the whole specification (`run_monolithic`, `src/tlsf/repair_modes.cpp`). A MUC-guided loop, `[tlsf] repair_mode = "muc"`, evolved a core and reintegrated it with the non-core guarantees; it was removed on 2026-10-30, the `2026-07-21` campaign having found it halved pooled `implies_ideal` (see "Config vintage" in `docs/dev/config-and-provenance.md`).

`extract_muc` pre-screens the singletons concurrently before QuickXplain's serial walk, which warms the realizability memo with the queries that walk is about to repeat, and counts the probes `ltlsynt` left undecided. A non-zero count means the core rests on queries that never answered: `mucs` prints it and calls the core provisional, since a subset read as unrealizable on a timeout may not be one.

## Key types

- `Timing` — `std::variant<Immediately, NextTimepoint, WithinTicks, ForTicks, AfterTicks, Eventually, Always, Until, Before>` (see `requirement.hpp`). `Until` and `Before` hold a propositional stop condition `s`.
- `ConditionType` — `enum class { Trigger, Continual }`: the condition activates a `Requirement` on its rising edge (Trigger) or wherever it holds (Continual).
- `Requirement` — holds `m_condition`, `m_response`, `m_timing`, `m_condition_type`, the derived `m_ltl` string, and `m_weakenable`. A requirement with `m_weakenable` false is locked: never mutated, used as a crossover source, or simplified. The flag is part of `Requirement`'s identity (`operator<`/`==`/`hash`) and serialises as the optional JSON key `weakenable`, emitted only when `false`. `m_removed` is the removal tombstone (see "Removable guarantees").
- `Formula` — propositional AST with `syntactic_similarity`, `rewrite_post_order`, `n_subformulae`.
- `TransferSystem` — weighted automaton transition matrix for bounded model counting.
- `Count` — `long double` (x87 80-bit: integers exact to 2^64, exponent range to 2^16384). Trace counts are consumed only as ratios cast to `double`, so range matters more than integer width; `count_add_overflow`/`count_mul_overflow` report overflow as a non-finite result.
