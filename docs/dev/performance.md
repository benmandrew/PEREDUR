# Performance

Memoisation keys, parallel dispatch, the implication prefilter and subprocess handling, with the measurements behind each.

## Cache keys

Every *memoisation* cache in front of an external tool is keyed on a rendered formula string, and `Formula` has no canonical shape, so each spelling of one formula bought its own subprocess. In `formula_key.hpp`, `canonical()` renders `Formula::canonical()` (commutative operands flattened, ordered and deduplicated, double negation dropped) and `renamed()` also renames the atoms to a canonical sequence. Both memoise on the raw input, so a spelling already seen costs a hash.

The key a cache may take depends on what it stores, and a wrong choice is silent. A verdict or a count is invariant under renaming atoms, so the satisfiability cache, `cached_count_traces` and `run_ganak_on_formula` take `renamed()`. A stored formula or automaton would need renaming back inside a tool's output, where SPOT prints `F` over an atom `fk1` as `Ffk1`, so `run_ltl2tgba_for_counting` and `rewrite_weak_operators` take `canonical()`. `RealizabilityChecker` takes `formula_key::realizability()`, a partition-preserving renaming plus the count of declared signals left unmentioned, those being part of the alphabet ltlsynt plays over.

The satisfiability cache keys on `renamed()` alone. It once kept a second key, the `ltlfilt --simplify` spelling, which collapsed more queries than the renaming did (2,211 execs against 2,773 on `rg2`), but the pass that computed it cost 8x the `--satisfiable` call it preceded, so both were dropped.

Keys must reparse, so the parser reads temporal operators. A letter operator counts only when the next character cannot continue an identifier, or `Grant` lexes as `G` over `rant`. External strings go through `Formula::try_parse`, since the constructor only asserts.

With the search held fixed over six specifications, the keys and the subsumption table remove roughly 13% of external-tool time, against an offline ceiling of 22% that the canonical key cannot reach without the renaming. Exec counts drift a percent or two per seed, two threads missing on one key both computing it; the repairs do not drift.

`count_guard_models` counts a Hanoi Omega-Automata (HOA) guard in process through `count_models_exhaustively` (`src/fitness/exhaustive_count.hpp`), a bitwise truth table, because the widest of 2,932 distinct guards over nine specifications mentions 12 atoms. It declines temporal or unparsable formulae and anything above `k_exhaustive_count_max_atoms` (16), leaving ganak as the fallback. Ganak execs fell to zero on all nine, and median wall time 50.1% pooled over seven paired families.

That figure is a paired median over three repetitions, the binaries interleaved per family. Run one arm after the other on the shared 20-core box, the same change read *slower* on seven of nine families, and one arm against itself moved 25.2%. Interleave the arms and read a median before concluding anything about wall time.

No simplifier pass may run over a guard before counting. `ltlfilt --simplify` drops a subsumed variable (`a | (a & b)` becomes `a`), while `count_guard_models` takes its free-variable exponent from the HOA label, so the count would silently fall by 2^(dropped). `test_ganak_counts_over_every_mentioned_variable` pins this, and `simplify_ltl` is the only entry point to that pass.

`RealizabilityChecker` also keeps a *subsumption table*. Realizability is monotone in both sides, so a query that drops a guarantee from a realizable specification, or adds one to an unrealizable one, is answered without an exec (and dually for assumptions). Conjuncts are interned and each side carries a 64-bit signature, so most entries fail one AND. Only decided entries subsume, and entries are scoped by atom partition and TLSF semantics. It removes 26.2% of ltlsynt execs over six specifications.

Where a FRETISH caller passes the requirement behind each conjunct, a query the table cannot settle goes to `rule_subsumed_verdict`. It takes the conjuncts that the query and a decided entry each lack, at most four each way, and asks `requirement_implies` whether each missing conjunct is implied by one the other side has in its place. A realizable entry carries over when every assumption the query dropped is implied by one it added and every guarantee it added is implied by one it dropped; an unrealizable entry carries over in the opposite direction. Conjuncts pair by set difference, since the MRS walk compacts the guarantee list and slots do not line up across its subsets. Rule verdicts are memoised per id pair. Only executed queries join the table: adding the derived verdicts too left the exec counts unchanged on `mode-arbiter` and `fsm-combined`. `test_rule_subsumption_agrees_with_ltlsynt` (`test/runner/spot_tests.cpp`) checks each rule verdict against a fresh `ltlsynt`, and `caches.realizability.rule_subsumed` in `run.json` counts them.

A query both passes miss can still be answered by a stored *controller*. On a FRETISH query with at least 10 guarantees, `ltlsynt` runs with `--hoaf` instead of `--realizability` and prints the winning *Mealy machine* after the verdict line, at the same cost. The checker keeps the 64 most recent machines per scope as Hanoi Omega-Automata (HOA) files in a per-process `mkdtemp` directory, because `autfilt --product` reads its operand only from a file. A later query goes to the three stored machines sharing the most interned conjuncts with it. A machine realises `(&A) -> (&G)` when its product with the automaton of `&A` and the automaton of `!g` is empty for every guarantee `g`. Each product is cached per machine and assumption set, each `!g` automaton per canonical formula, and each emptiness verdict per product and guarantee. Where the query assumes at least what the machine was built under, only the guarantees the machine's query lacked are checked. Emptiness is read from `--stats=<%w>`, since `--is-empty` filters the input before the product is taken. Only a pass is believed: a failure, timeout or tool error falls through to `ltlsynt`, so the store changes how a verdict is reached and never which one. A machine is stored only if every state has a transition for every input valuation, since a missing input would drop words from the product and pass a guarantee they violate. All 2,097 machines from a recorded `lift-plus-cruise-full` stream passed that test. Checking the whole formula `!((&A) -> (&G))` instead timed out at 120 s, which is why the check runs per conjunct. Below 10 guarantees the median `ltlsynt` call takes 8 ms, cheaper than the execs of a check.

On `lift-plus-cruise-full` (`peredur --seed 1 --diagnostics`, `generations = 3`, `population_size = 100`, release builds, arms interleaved, median of three), the store answered 958 of 1,285 attempted queries. It cut `ltlsynt` execs from 2,282 to 1,289 and `tool_calls.ltlsynt.total_s` from 1,837 s to 432 s, at a cost of 2,449 `ltl2tgba` and `autfilt` execs taking 35.5 s. The 10 s `ltlsynt` timeouts fell from 54 to 5, so the branch found 14 repairs where the base found 10 to 12. Wall time fell from 533 s to 144 s on a box shared with other builds. `mode-arbiter` and `fsm-combined` stay under the gate, with the same repairs and no store activity. `test_controller_reuse_agrees_with_ltlsynt` and `test_controller_reuse_never_answers_unrealizable` compare every answer against a fresh `ltlsynt`, and `caches.realizability.controller_reuse` and `tool_calls.controller_check` in `run.json` count the work.

With seed 1, population 100 and 10 generations on release builds, three interleaved runs per arm, `ltlsynt` execs fell from 242 to 166 on `mode-arbiter` and from 401 to 303 on `fsm-combined`, with byte-identical repairs; wall time moved from 3.6 s to 3.3 s and from 3.7 s to 3.7 s. On `lift-plus-cruise-mini` the pass settled 630 to 648 queries per run and the median exec count fell from 3,800 to 3,571, but queries near the timeout make those runs breed different populations, and the two arms' ranges (3,654 to 3,986 against 3,444 to 3,659) almost meet. TLSF passes no requirements, and `round-robin-arbiter-aurus` is unchanged.

A query whose environment has no inputs never reaches ltlsynt. With no inputs the environment makes no choice, so `A -> G` is realizable exactly when it is satisfiable, and Mealy and Moore semantics coincide. `plays_without_environment` (`src/runner/spot.cpp`) routes a query only when the input list is empty and every atom the formula mentions is a declared output, because ltlsynt under `--outs` reads any other atom as an input. FRETISH counts pure modes among its inputs (`environment_signals`), so a moded specification is never routed. The query goes to `check_satisfiability_by_black`, which asks black alone: a first build that went through `check_satisfiability` saw SPOT's `--satisfiable` stage run out its 500 ms on 2,141 of 3,674 routed queries, and the wall time did not move. Only a decided answer is cached there, and an undecided one falls through to ltlsynt. A routed verdict joins the memo and the subsumption table exactly as an ltlsynt one would, and `caches.realizability.satisfiability_routed` in `run.json` counts them. `test_input_free_routing_agrees_with_ltlsynt` (`test/runner/spot_tests.cpp`) checks each routed verdict against ltlsynt, including an unsatisfiable specification and two that are realizable only because the system can falsify an assumption over its own outputs.

Over 72 `lift-plus-cruise-mini` repairs (no inputs, 48 guarantees), ltlsynt took a median 0.538 s per query and black 0.028 s, and all 72 verdicts agreed. With seed 1, population 100 and 10 generations on release builds, three interleaved runs per arm, the median ltlsynt exec count on `lift-plus-cruise-mini` fell from 3,455 to 0 and the median wall time from 325.7 s to 49.3 s, while black execs rose from 1,989 to 5,465. All three branch runs wrote the same 38 repairs as two of the base runs; the third base run hit an ltlsynt timeout and wrote 34. `mode-arbiter` and `fsm-combined` have inputs, and their repairs stayed byte-identical at 167 against 168 and 302 against 301 ltlsynt execs.

Sides are sound only where every conjunct has a determinate polarity in the lowered formula. TLSF wraps whole sections, yet in `theta_e -> (theta_s & [strict: psi_s W !psi_e] & ((G psi_e & phi_e) -> ([!strict: G psi_s] & phi_s)))` INITIALLY, REQUIRE and ASSUME are all negative and PRESET, ASSERT and GUARANTEE all positive, empty sections included. REQUIRE occurs twice, but the negation in `!psi_e` flips the second back, so both occurrences are negative; an earlier reading got this wrong, so check polarity through the negation before calling a section non-monotone. `tlsf::specification_sides` tags each conjunct with its section and puts the semantics in the scope. Well-separation queries build `(A) -> (false)` rather than `to_ltl()` and pass no sides, sides being valid only for a query over the lowering itself. `test_tlsf_subsumption_agrees_with_ltlsynt` (`test/tlsf/filter_tests.cpp`) checks both semantics against `ltlsynt`, since a wrong verdict here is silent.

`run.json` reports every memo's hits and misses under `caches`. Archived TLSF campaigns read `{hits: 0, misses: 0}` for the fitness cache, whose per-template counters then reported the FRETISH instance. `tool_calls.ltlfilt.calls` is `LtlfiltStats::n_execs()`, the set `total_s` covers. `cached_count_traces` absorbs repeats before the `ltl2tgba` and ganak caches, so their low hit rates (4.8% for `ltl2tgba` against 71.8% above it) are not a defect.

`cached_count_traces` could answer `count(r & r')` with `count(r)` wherever `requirement_implies(r, r')`, since the two formulas are equivalent. The bounded count is a property of the automaton, though: `ltl2tgba -D -S` gives a canonical automaton only for obligation formulas, and a requirement with Eventually timing lowers to a recurrence. On 7,682 rule-proved pairs at bounds 6 and 20 the two counts agreed to a relative 2.4e-16, which is `long double` rounding, and they agreed exactly on 72 repair-against-original pairs from `lift-plus-cruise-mini`, `mode-arbiter` and `fsm-combined`. The reuse is not built: all `ltl2tgba` calls took 6.6 s of a 699 s `lift-plus-cruise-mini` run, and the ordered conjunctions are a fraction of those calls.

## Scoring dispatch

Every parallel region is a `run_bounded_async` call (`include/bounded_async.hpp`), and each is a full barrier: nothing after it starts until its slowest item finishes. A run at `generations = 10` spends 98-99% of its wall time inside 33 to 35 of them: per generation the vacuity filter, the score stage and the per-generation gate; per run the seed population's scoring, `conflict_degree_order`'s two passes under `mrs_admission_order = degree`, the final realizability gate and the implication filter. At 20 workers over four TLSF families, 5.4% to 13.0% of dispatch wall sat idle, all in the small regions; the O(n^2) implication filter takes 60-74% of wall at 99.1-99.4% *occupancy*. Campaigns run `parallel = 8`, so those idle figures are the pessimistic end.

**Longest-first launch.** `cost_ordered_indices` orders launches by descending cost estimate with index tie-breaks, and `run_bounded_async` takes it as an optional `launch_order`. Every call site collects results by index, so the order is unobservable. It bounds the *makespan* at (4/3 - 1/3m) of optimal for m workers.

**A candidate's score is no longer one task.** Scoring one candidate was a serial chain of subprocess calls on one worker, which no worker count shortens. `ObjectiveWork` and `FitnessPart` (`include/fitness/function.hpp`) split an objective into schedulable parts with cost hints, and `AggregateWeightedFitnessFunctionT` provides `cached_objectives`, `plan`, `store` and `scalar`. `score_population` (`include/genetic/generation.hpp`) plans the population without calling tools, then dispatches every part of every candidate in one region: one free syntactic part, one semantic part per changed slot, and a `black` query per component plus the realizability walk for status.

The walk's component short circuit is given up deliberately. The split path passes `ComponentCheck::Skipped` to `specification_status` and `tlsf_status` so that component queries are not asked twice, and a candidate with an unsatisfiable component therefore pays for its synthesis queries. On `lily11`, the family with the highest satisfiability miss rate, that costs 1.1% to 2.3% more `ltlsynt` misses; every other family's fell.

Repeats of one specification miss the fitness cache together, and scored populations are largely repeats (`stage_pad` and the apportion scheme both replicate). `plan_population` therefore folds repeats onto one plan, with `PlannedCandidate::indices` listing every slot it answers for. Without that fold the change is a net regression.

Over 12 paired runs across 4 TLSF families the repairs are byte-identical, 11 are faster at a median of about -3%, and non-pair occupancy rose 6 to 8 points. `arbiter-aurus` did not move, its straggler being the MRS walk, which cannot be split.

There is no config key, because scheduling changes no output and draws nothing from the `RandomSource`. It can shift which queries hit the `black` or `ltlsynt` timeouts, as any concurrency does; the 12 paired runs showed no such shift.

The implication filter already runs saturated, so the reachable target is the ~34% of wall spent in score stages. `make_predicate_filter`, the final gate and the implication filter accept a launch order, but none passes one yet.

**MRS lookahead.** The walk that split scoring could not shorten is one serial chain of `ltlsynt` queries, because each step's set depends on the verdict before it. On `lift-plus-cruise-full` (59 guarantees) at `parallel = 8`, stack samples showed six or seven workers idle in `worker_loop` while one or two walks finished the score stage. At `runtime.mrs_speculation_depth = d`, a walk at step i also submits the sets that steps i+1 to i+d would ask under every outcome of the steps not yet settled, at most 2^(d+1) - 2 of them. They run the walk's own oracle and only warm `RealizabilityChecker`'s memo. The walk still asks every query itself, in its serial order, and `test_mrs_lookahead_asks_what_the_serial_walk_asks` pins that sequence against the serial walk's. Up to d+1 steps then settle per query time where one did.

A walk submits no more lookahead queries than `ThreadPool::idle_workers()` reports, and submits them as `TaskPriority::Background`. A busy pool therefore takes none, and a scoring part queued later still runs first. A lookahead query the walk reaches before a worker has started it is cancelled and asked inline, and one already running is waited for rather than asked twice. The oracle never submits to the pool, so the walk only ever waits on a task that can finish without a free worker. That is the nested-wait hazard `conflict_degree_order` avoids by running outside the pool.

Each node passes from Pending to Running only by a compare-and-swap in its task. On return the walk cancels every node still pending and waits out every running one, so no started task outlives the oracle and the caller data it borrows. A cancelled task can still sit in the pool's queue after that, holding only its own node. Letting running tasks finish unwatched would need them to own the checker too, and they cannot: tests build their own, and `global_real_checker()` is a function-local static with no destruction order against the pool's. The wait costs at most the remainder of queries started within the last few steps, against a chain the lookahead shortens several-fold.

The verdicts the walk reads are the serial walk's whenever every query is decided. A lookahead verdict can still reach the walk through the subsumption table rather than the memo, since a realizable superset or an unrealizable subset answers the walk's own query without an exec. Where that exec would have timed out, the walk now reads a decided answer the serial walk did not, which is the same exposure concurrent scoring of other candidates already carries. Unlike the scheduling above, this does have a key, because the untaken branches cost real `ltlsynt` execs on a shared machine. `--diagnostics` and `run.json`'s `mrs_speculation` report the queries issued, started and consumed by the walk. Its wall-time effect has not been measured yet.

## Per-generation gate

The output gate grades every member of every generation, for the accumulator. Its status call, `gate_status`, used to walk the guarantee parts in index order, while the scoring walk under `mrs_admission_order = degree` admits them by conflict degree. The two walks ask `ltlsynt` about different subsets, so the gate missed `RealizabilityChecker`'s memo on most of its queries. Profiled under a `gate/verdicts` scope at 300 individuals, the gate took 98 s of a 299 s weighted-mrs run on `full-arbiter-aurus` and 106 s of 348 s on `humanoid-503`.

The gate now takes the run's status objective (`status_objective_of`) and grades with it, so the walk replays the one scoring already memoised. Realizability is monotone in the guarantees, so both walks reach the top tier exactly when the whole guarantee side is realizable; the verdicts differ only where a query times out in one walk and not the other. Over 11 paired runs on six families (seed 0, 300 individuals, both arms of the paper's design), every `repair_N.json`, accumulated repair and maximal set came out byte-identical. Wall time fell from 297 s to 238 s on `full-arbiter-aurus`, 350 s to 269 s on `humanoid-503` and 112 s to 87 s on `prioritized-arbiter-aurus`, all weighted-mrs; the nsga2-aurus arm and the small families moved under 2%. The TLSF final gate, `realizable_survivors`, grades with the same objective. The FRETISH final gate, `collect_realizable_specifications`, has no fitness function in reach and still makes its own call.

## Implication prefilter

The implication filter already runs saturated, so it gets cheaper only by asking the solver fewer pairs. `fingerprint::prefilter` (`src/fingerprint/prefilter.hpp`) evaluates each lowered formula on 256 *lasso words* (ultimately periodic, at most five positions) and packs the results into a bitset. A word that A accepts and B rejects refutes `A -> B`, so `refutes_implication` compares two machine words. On a 421-candidate `round-robin-arbiter-aurus` set it refuted 95.9% of ordered pairs. On FRETISH (seed 1, population 100, 10 generations) the sampled words alone refuted 39.6% on `mode-arbiter` and 52.6% on `fsm-combined`, and none on `lift-plus-cruise-mini`. That spec has 48 guarantees over 20 outputs and no inputs, and none of its 56 written repairs accepts any of the 256 words, so every fingerprint is zero and no word separates a pair. Random words cannot refute anything on a spec whose guarantees constrain most of its signals at every step.

So each candidate's own solver model joins the word set. `black_model` (`src/runner/black.cpp`) asks `black solve -m -o json` for one lasso per lowered candidate, with a 1 s budget (`k_model_budget`). The query is prepared as a satisfiability query is: weak operators are rewritten in terms of U and R and the constants respelled, and both rewrites are equivalences, so a model of the query black reads is a model of the candidate. `word_of_model` (`src/fingerprint/prefilter.cpp`) turns the model into a lasso word over the signal template. An atom black leaves `undef` is unconstrained at that state, so it is set false, as is every signal the model never names. A `loop` equal to the model's size means no obligation was left open, so any continuation is a model, and the last state is repeated. A timeout, UNSAT or UNKNOWN gives no word, and black never touches the `RandomSource`.

Every candidate is evaluated on every model word, and those bits follow the 256 sampled ones in each bitset. The sampled bits fill exactly four `uint64_t` elements, so they are unchanged and `refutes_implication` reads both parts with no change. Two fingerprints compare only when both were evaluated on the same model words, so the streaming filter now redraws the table over its maximal set and each new batch at every merge, where it used to keep one fingerprint per member. Models are memoised on `formula_key::canonical()`, since a model names atoms, which keeps that to one black call per candidate. The calls run in parallel, on the background queue under streaming, and misses are stored in index order so a shared key keeps the same model whichever call finished first.

A script measured the idea first on the 70 `lift-plus-cruise-mini` candidates. One model each took a median 22 ms, and the 70 models refuted 4,152 of the 4,830 ordered pairs. SPOT confirmed 40 of 40 sampled refutations. Of the 678 pairs left unrefuted, SPOT found 567 non-implications and 111 implications, so the models refute 88.0% of the known non-implications, and SPOT spent 1,480 s on those 678 pairs alone.

In the engine, release `maximal --timeout 1` ran on four fixed candidate sets, base `d9d9921` against this change, interleaved per case, three times each, and the figures are medians. The machine ran at a load average of 22 to 35 throughout, so the counts carry more weight than the wall times:

| `lift-plus-cruise-mini` | 70 | 70 | 0 → 4,150 | 1,092 → 219 | 23 → 14 | 38 → 38 | 31.9 s → 12.8 s |
| `mode-arbiter` | 41 | 41 | 1,497 → 1,497 | 37 → 37 | 0 → 0 | 14 → 14 | 0.12 s → 0.25 s |

Every run of both arms kept the same survivor set. On the three small sets the sampled words already refute every pair a model refutes, so the black calls cost about 0.1 s and buy one pair. An earlier 500 ms budget lost up to 5 of the 70 `lift-plus-cruise-mini` models under the same load, and one run that lost five kept a 39th survivor whose implication query had timed out. `implication.model_words` and `implication.model_refuted` in `run.json` count the model words in the sweep's tables and the ordered pairs only a model word refuted; `model_refuted` is a part of `fingerprint_refuted`. `test/fingerprint/prefilter_tests.cpp` checks every model refutation of a small family against SPOT, on both paths, and checks the evaluator and SPOT against each model word with its `undef` atoms set false.

It is sound because a word can refute an implication but never confirm one, whatever produced the word, so unrefuted pairs still reach the solver and output is byte-identical. For the same reason there is no config key.

Refuted pairs must be removed before dispatch. `run_bounded_async` bounds the items in flight, so a task that returns at once still takes a slot, and the sweep would pay O(n^2) scheduling anyway. `antichain::merge_subsumed` (`src/filter/antichain.hpp`) erases doubly-refuted pairs from `pairs` first. `implication.fingerprint_refuted` in `run.json` (`n_fingerprint_refuted`) is the only evidence the prefilter worked, because refuted pairs never reach `comparisons`.

Both paths share one template walk, since fingerprints compare only when drawn from the same words. The signals are `m_inputs` then `m_outputs` on TLSF, and `environment_signals` then `m_out_atoms` on FRETISH. Modes must be in the set: an atom that no word names is false everywhere, so each scope would be evaluated as if its mode never held. FRETISH lowerings reparse because `requirement_to_ltl` emits only X, G, F, U, W and R over propositional connectives. If `prop_formula_internal::try_parse_formula` cannot reparse a lowering, the table comes back empty and the sweep runs unfiltered.

## Implication residual query

An implication query negates the whole destination, and SPOT builds an automaton for that negation. Repairs of one original share most of their guarantees verbatim, so most of that automaton restates what the source already guarantees. `residual_destination` (`src/filter/implication_check.cpp`) and `tlsf_residual_destination` (`src/tlsf/filter.cpp`) mark the shared guarantees removed in a copy of the destination, and `spec_implies` and `tlsf_spec_implies` query that copy instead. A destination left with no live guarantee is implied with no query at all.

The shortened query has the same answer only where the source's guarantees are in force under the destination's premises. On FRETISH every live assumption of the source must be implied by one of the destination's, by identity or by the rules below. On TLSF the semantics and the live INITIALLY, REQUIRE and ASSUME conjuncts must agree, and a conjunct is dropped only from the system section it shares. Strict semantics needs no special case, since `(x & y) W e` is `(x W e) & (y W e)`. `test_residual_agrees_with_whole_query` and `test_tlsf_residual_agrees_with_whole_query` check every ordered pair of a small family against the whole-formula query under both semantics.

On `lift-plus-cruise-mini` (seed 1, population 100, 10 generations, debug build) the final implication filter took 337 s of a 699 s run, and 528 of its 2,033 comparisons timed out. Its repairs carry 48 guarantees, any two differ in a median of 5, and all 3,080 ordered pairs of the 56 written repairs had identical assumptions. Over 8 ordered pairs of those repairs, timed with `ltlfilt -F <file> --satisfiable -c`, the shortened query ran 3.2× to 8.1× faster (median 4.8×) and agreed on every verdict. The two slowest whole queries took 12.2 s and 12.1 s, against 2.6 s and 1.5 s shortened.

There is no config key, by the argument the prefilter is recorded under: the shortened query holds on the same traces as the whole one, so it changes cost and no verdict. A run can still differ where a query that timed out now finishes. `implication.residual_queries` and `implication.residual_settled` in `run.json` count the shortened and the settled checks.

On FRETISH a requirement can also be dropped, or an assumption accepted, when a rule proves the implication instead of identity. `requirement_implies` (`src/filter/implication_check.cpp`) looks for a chain from one requirement to the other that changes one field per step. Each step is an implication in the context the other fields give it: a response or stop moves along its polarity, a continual condition moves backwards, a trigger's condition only to an equivalent one, and the timing, scope and condition type move along their orders (`timing_implies`, `scope_implies`). The propositional steps are decided by `count_models_exhaustively`, so no step launches a process, and the search tries every order of the five fields (32 states). Rules only ever compare a requirement with the one in its own slot, because slots pair by index across repairs of one original and lift-plus-cruise-mini's 48 guarantees would otherwise give 48 candidates for each uncovered one. A pair the rules cannot prove still reaches the shortened query, so the rules change cost and never a verdict. `test_requirement_implies_is_sound` sends every proved pair of a 31,284-pair sample to SPOT: SPOT confirms all 1,976 proved pairs, and finds 2,070 implications among the sample, so the rules reach 95.5% of them. `implication.rule_covered` in `run.json` counts the requirements a rule proved.

Both changes were measured together with `maximal --timeout 1` (the engine's `black_timeout_ms`) on fixed candidate sets taken from seed-1 runs at population 100 and 10 generations. | `mode-arbiter` | 43 | 0.25 s → 0.10 s | 0 → 0 | 14 → 14 | 27 |
| `round-robin-arbiter-aurus` | 73 | 0.39 s → 0.33 s | 0 → 0 | 27 → 27 | n/a |
| `prioritized-arbiter-aurus` | 9 | 0.06 s → 0.04 s | 0 → 0 | 6 → 6 | n/a |

Each arm gave the same survivors in all three runs, and the new survivors are a subset of the old ones in every case. The survivor counts fall only where queries timed out: a timeout reads as no implication, so the old sweep keeps both sides of every pair whose query ran out, and the new one proves those dominations. Each proved domination also skips the dominated candidate's remaining pairs, which is why `lift-plus-cruise-mini` runs 1,091 comparisons instead of 2,111. The TLSF sets gain least, since only identical conjuncts are dropped there and neither set timed out to begin with. `ventilator-controller` wrote no candidates within 40 minutes at this size, and `rad` and `full-arbiter-aurus` wrote none.

## Implication model probe

An implication query between two whole specifications is `(A) & !(B)`, and on the large TLSF families SPOT cannot build its automaton in time. Over 48 sampled `humanoid-742` repair pairs `ltlfilt --satisfiable` took a median 7.96 s, and 5 ran past 20 s. Every one of the 43 it decided was satisfiable: implications between repairs rarely hold. black found a model for all 48 in 51 ms at the median and 70 ms at worst. Under the old route, with SPOT alone at a 1 s budget, nearly every such pair timed out and was kept.

`SatisfiabilityChecker::implication_answer` (`src/runner/black.cpp`) now routes every `ExpectUnsat` query in three steps. SPOT gets a 200 ms first look, then black gets 300 ms to find a model, then SPOT gets its full budget. Only black's SAT is taken. A model is a proof, and SAT is the verdict SPOT gives whenever it finishes, so the probe changes what a pair costs and never what it reads. black's UNSAT is discarded, and an implication is still only established by SPOT. Weak operators are rewritten away first, as on the escalation path, since black is unsound on W under negation.

The two budgets come from `lift`, the one family where a first look of 100 ms and a probe of 1 s cost wall time. There SPOT decides implications in 30-530 ms, and black never proves a valid one inside 5 s. A 1 s probe therefore spent its whole budget on each valid implication before SPOT's second look, and `lift` ran 17-20% slower. Every valid implication in a 60-pair `lift` sample decided inside 230 ms, so a 200 ms first look leaves most of them to SPOT. black's slowest model there took 180 ms.

A query of 4096 characters or more skips the first look (`k_implication_long_formula`). `lift`'s queries run to 1.8k characters, while `pcar-v2-888`'s and `humanoid-742`'s run from 9.5k, where SPOT took a median 0.71 s and 7.96 s and black still answered within 70 ms on most pairs. On `humanoid-531`, whose queries run to about 7k characters, black settled 672 of 742 comparisons, each after a first look that had already run out; skipping it took a 300-individual run from 491 s to 322 s, with repairs byte-identical to the base binary's. Leading with black costs only on a valid implication, 4 of 40 sampled `pcar-v2-888` pairs.

At the paper's budget (1000 individuals, seed 1), `humanoid-742` under `nsga2-apportion`/`aurus` fell from 2,510 s to 1,860 s and `humanoid-531` from 1,140 s to 981 s, with byte-identical repairs. At 300 individuals, 42 paired runs over 21 TLSF families came out byte-identical, and families whose implications SPOT already settles moved by under 3%. Where they differ, on `pcar-v2-888` and the weighted `humanoid` arms, the base binary does not reproduce itself either, since implication and `ltlsynt` timeouts land differently from run to run. `n_model_probe_sat` in `run.json` counts the pairs the probe settled.

## Tool subprocesses

Every pipe a runner opens must be created with `pipe2(..., O_CLOEXEC)`, as `execute_and_capture` (`src/runner/process.cpp`) and the formaliser (`src/runner/formaliser.cpp`) do. Runners are called from many threads, so a fork on one thread would inherit other calls' pipes past its exec, and their readers would never see end of file. `pipe` followed by `fcntl` races a concurrent fork. `dup2` clears the flag on the child's standard descriptors.

`spawn_piped_child` (`process.hpp`) is the one fork for any bidirectional child, so a second user differs only in `ParentDeathPolicy` and `ExecutableLookup`. Nothing may fork outside `process.cpp`. Linux forks every child, because `posix_spawn` has no attribute for `PR_SET_PDEATHSIG`. macOS starts children with `posix_spawn` and forks only when that fails, so a failed exec is still reported from the child. A fork from an AddressSanitizer (ASan) build costs a fixed 74 ms on macOS against 1.2 ms for `posix_spawn`, whatever the heap holds, and the switch took the serial debug suite from 366 s to 55 s. `POSIX_SPAWN_SETPGROUP` replaces the child's `setpgid`. A `KillWithParentThread` child starts suspended, and the parent registers its group with the reaper before sending `SIGCONT`. If PEREDUR dies before the registration lands, the stopped child's group is orphaned and the kernel's `SIGHUP` kills it, which is why the child gets `SIGHUP` reset to its default.

The macOS reaper leaves PEREDUR's process group as soon as it is forked, by `setpgid` on both sides of the fork, and ignores `SIGHUP`, `SIGINT`, `SIGQUIT` and `SIGTERM`. GNU `timeout` puts itself and the run in one group and signals that group on expiry, as Ctrl-C does to the foreground group. A reaper inside the group died with PEREDUR, while each tool, in a group of its own, never saw the signal. A `timeout 2400` run on `examples/ventilator-controller` left two `ltlsynt` at 87% CPU for 3 h 16 min that way. `timeout 20` on the same specification reproduced it with one survivor, and a `kill -TERM` of PEREDUR's pid alone left none. Only leaving the group survives `timeout -s KILL`. Ignoring `SIGHUP` also matters when PEREDUR dies with the reaper stopped: the group is then orphaned, and the kernel sends `SIGHUP` before `SIGCONT`. The `process_runner` suite signals the group of `contained_child_helper` with both `SIGTERM` and `SIGKILL` and checks that its child dies.

A formula reaches a tool on stdin through `execute_and_capture_with_input`, never as an argv string. Linux caps each argv string at `MAX_ARG_STRLEN` (131072 bytes), and a lowered 68-guarantee FRETISH specification produced a 136,058-byte ltlsynt formula whose exec failed with `E2BIG`. The SPOT tools read it with `-F -`, which takes one formula per line, so `spot_formula_line` (`src/runner/formula_input.hpp`) turns line breaks into spaces. black reads it as the file `-`. `ltlfilt --equivalent-to` accepts only an argv string, so `ltl_equivalent` puts the smaller side there and falls back to an unsatisfiable exclusive or on stdin when both sides are large. The input goes into an in-memory file (`memfd_create`; an unlinked temporary file on macOS) written before the fork, not into a pipe, so a large input cannot deadlock against the output being read, and a child that exits without reading it raises no `SIGPIPE`. Measured over 400 interleaved `ltlfilt --simplify` pairs on the debug build, the median call took 26.27 ms through argv and 26.28 ms through stdin. A failed exec now writes `peredur: cannot exec <path>: errno <n>` into the captured output, naming `E2BIG`, where it used to leave only exit status 127 and empty output.

## Profiling

`PEREDUR_PROFILE=<path>` enables the *scope profiler* (`include/profile.hpp`): a table on stderr plus JSON at the path, while `PEREDUR_PROFILE=1` gives only the table. The report registers with `atexit` on the first scope opened, so every binary reports without extra wiring. The `peredur` drivers also call the idempotent `profile::report_if_enabled()` so the profile prints before the manifest and `Done in`.

Read wall time against per-thread CPU time. A site with high wall time and near-zero CPU is waiting on a child process, as `proc/read` shows at a cpu/wall ratio of about 0.01.

The profiler is in-process because `kernel.perf_event_paranoid=4` and yama `ptrace_scope` rule out `perf` and `gdb` on the dev box, and `strace` can only launch a process, never attach. The site registry and the intern table behind its names are deliberately leaked so that they outlive the `atexit` report that prints them.
