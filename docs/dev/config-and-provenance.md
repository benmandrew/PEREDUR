# Config keys and provenance

What adding, moving or removing a config key does to archived campaigns, and how a binary and an archive record the commit they came from.

## Config keys

A new TOML key needs an entry in `k_config_keys` in `src/config/keys.hpp`, which drives the reader and the unknown-key warning in `src/config_io.cpp` and `config_json()` in `src/repair/manifest.cpp`, and an entry in `schemas/config-schema.json` (else editors reject it). An enum-valued key also needs its spellings in `EnumNames` in `src/config/enum_names.hpp`, which both the parser and `run.json` use. A check that spans two keys is written by hand in `apply_toml`. `scripts/check_config_schema.py`, run by `lint`, checks the table against the schema and `example-config.toml`.

Both repair paths share one key set, and some keys are read by one path only: the `[mutation]` rewrite arms `p_trigger`, `p_response`, `p_timing`, `p_condition_type`, `p_scope` and `p_stop`, and `[fitness] keyword_similarity` and `semantic_trace_weight`, by FRETISH, and `[tlsf] muc_max_iterations` and every `[tlsf.mutation]` key by TLSF. `k_single_path_keys` in `src/repair/manifest.cpp` lists them. A run warns on stderr about each key of the other path set to a non-default value, and its `run.json` records every such key as null. Neither is fatal, because campaign configs and `example-config.toml` set every key. `[tlsf] repair_mode` is the exception: the FRETISH path exits 1 on any value but `monolithic`. A new single-path key joins `k_single_path_keys`.

Every value in `example-config.toml` must equal its default in `include/config.hpp`, so copying the file whole is a no-op. The same script enforces this through `DEFAULT_FIELDS`; a new key goes there or into `UNPINNED_KEYS` (the enums and `runtime.parallel`), or the check fails. Eight keys had silently drifted before it existed.

A knob is worth keeping only if some archived config sets it, so count the configs under `experiments/` that set one before adding it and when auditing. The per-filter run intervals, the `[syntactic]` weights, `tlsf.mutation.p_guarantee` and `runtime.report_cpu_timing` were removed after appearing in none of ~65k. `python scripts/campaign.py describe --all --json` answers the same question per archive, and the configs win where the two disagree.

## Commit provenance

Every binary answers `--version` with `commit=`, `commit_short=` and `dirty=` lines, resolved at *build* time: `cmake/version.cmake` runs `cmake/write_version_header.cmake` on every build, which rewrites `build/generated/git_version.hpp` only when the commit changed. Configure-time resolution would report a stale HEAD after a new commit. Only `src/version.cpp` includes the header, and `dirty` counts modified *tracked* files only.

`scripts/run_experiments.py` reads `peredur --version` once at startup, never `git rev-parse`, and stamps `commit` and `dirty` onto every CSV row and a per-host manifest. It refuses to launch when a binary's commit differs from HEAD, was built dirty, or cannot be read, unless given `--allow-stale-binary`. Neither column may join the resume key in `run_experiments.py` or `KEY_FIELDS` in `merge_experiments.py`: archived rows have no commit, so every finished campaign would re-run.

Campaigns closed before this existed carry a reconstructed `PROVENANCE.json` (`"attribution": "inferred"`) whose `binary_commit` is `null` and must stay so; the "Commit attribution" section of `experiments/README.md` at `274d496` documents the method.

Each archive vendors the `gen_configs.py`, `run_experiments.py` and `merge_experiments.py` that ran it under `experiments/<campaign>/scripts/`, and `vendored_scripts` in `PROVENANCE.json` records each file's source commit and blob sha; check a copy with `git hash-object`. Attribution defaults to `profile_commit`, overridden where campaign content such as the `CSV_FIELDS` header pins the runner revision; `factorial`, `wellsep`, `genpop-sweeps` and `tlsf-genpop` are attributed that way, so do not "correct" them back. Recorded shas that are not ancestors of `main` are held reachable by annotated `provenance/*` tags, and no such tag may ever be deleted, because `git gc` would collect the objects. `provenance/tlsf-branch` holds `genpop-sweeps` and `tlsf-genpop`, which ran off the unmerged TLSF branch. `provenance/replicate-campaign` holds `2026-07-31-replicate`, whose branch was split into reconstructed pull requests. `provenance/assumption-reach` holds `2026-08-26-assumption-reach`, whose branch was rebased after the run; its shas are not repointed, since its results CSV stamps them. `provenance/selection-smoke` holds `2026-08-26-selection-smoke` and was cut *before* its branch was rebased, which is the order to keep, as a tag cut afterwards depends on `git reflog`. Re-check an archive whenever its branch is rebased, split or otherwise rewritten: blob shas survive a rewrite and commit shas do not, so the blob check cannot stand in for the tag. These paths, `README.md` and a campaign's pre-registered `PLAN.md` are the only tracked files under `experiments/`, via `.gitignore` negations that must re-open descent into any new subdirectory.

An archived config states only the keys its sweep overrides, so moving a C++ default silently changes what it means. Archived configs are not edited to compensate; record the move under "Config vintage" below. `allow_output_assumptions` and `run_well_separation` moved to `true` when `2026-08-06-wellsep-timing` closed and are now removed, so older archives reproduce only at their own commits. On 2026-09-11 `[mutation] p_condition_type` and `p_scope` moved from 0 to 0.15 and `p_monotone` to 0.25, so a FRETISH archive needs all three written in at `0.0`; the fitness weights moved from 0.2/0.5/0.5 to 0.1/0.2/0.7 that day, and `gen_configs.py` writes them into every config. `[mutation] p_stop` arrived on 2026-09-15 at 0.15; it draws only on a requirement with an `until` or `before` timing, and no archived specification has one, so it needs writing into no archived config.

*Removing* a key warns and ignores: `warn_unknown_keys` in `src/config_io.cpp` prints `config: unknown key <path>, ignoring`, with a `retired_key_hint` naming any replacement. Retire the sweeps and profiles that emit a key along with it, keeping their `merge_experiments.py` entries; those campaigns reproduce only at their own commits through their vendored `scripts/`. Removed so far:

- `[filters.intervals]`: TLSF sweep V and the `wellsep-timing` profile, whose campaign cannot be regenerated.
- `fitness.weight_halstead` (2026-08-13): sweep C.
- `[filters] run_weakening`, `run_well_separation`, and `[tlsf.mutation] p_monotone`, `connective_implies`, `monotone_atom_rules`, `monotone_extra_rules` (2026-09-11): FRETISH sweep J, TLSF sweeps W and Q, and the `cj-large`, `weakening-arbiter`, `wellsep`, `arbiter-hp` and `arbiter-padd` profiles. 79,236 of 79,255 archived configs set `run_weakening` and 12,323 set `run_well_separation`; the `monooff` arm of `2026-08-23-monotone` now runs at the 0.25 default.
- `[tlsf.mutation] p_burst_continue`, `p_remove_assumption`, `[mutation] allow_output_assumptions`, `[runtime] max_concurrent_realizability`, `ganak_timeout_ms` and `[filters] run_vacuity` (2026-09-11): archived configs set only `allow_output_assumptions` (12,323) and `max_concurrent_realizability` (4, in `2026-08-03-libspot-soak`).

Retiring a key's *value* goes further, because the parser refuses it. On 2026-08-06 `nsga2` became `nsga2-truncate` and `nsga2-replicate` became `nsga2-apportion`, and the old spellings are rejected by name rather than aliased, so an archived config reproduces only at the commit its `PROVENANCE.json` names.

Archived *results* still join. `scheme_of()` in `run_experiments.py` reads the scheme's directory name into the `selection` column of `KEY_FIELDS`, and `canonical_scheme()` in both scripts maps retired spellings onto new ones wherever `selection` is read back, so all 224,861 archived `nsga2` rows keep their resume key. Renaming any other factor directory needs a mapping entry too, or a finished campaign silently re-runs from zero.

## Where the campaign records are

The campaign archives under `experiments/` and the narrative log `EXPERIMENTS.md` left this repository after `274d496`, which is the last commit of `main` that holds them. A path of the form `experiments/<campaign>/...` or a reference to `EXPERIMENTS.md` in a comment or in these docs resolves at that commit: `git show 274d496:experiments/<campaign>/REPORT.md`. A campaign closed on its own branch after that commit resolves at its `provenance/<campaign>` tag. The campaigns behind the paper's evaluation are also in the paper's Zenodo artifact, with their raw output. Campaign tooling is unchanged, and a new campaign still writes to `experiments/`.

## Config vintage

`gen_configs.py` writes a key only when a sweep overrides it, so an archived config states a fraction of the settings its campaign ran under and inherits the rest from the binary. That makes a changed C++ default a silent change to what an archived config means. Two such changes have happened, both in the commit that closed `2026-08-06-wellsep-timing`: `allow_output_assumptions` and `run_well_separation` each defaulted to `false` for every campaign archived here and then defaulted to `true`. Re-running an archived config therefore needed both keys written in as `false` explicitly. Without the first, the run admitted output atoms into assumptions where the campaign did not; without the second it also dropped the candidates that draw produces, so the two omissions did not cancel — they compound into a search neither the old nor the new default describes. The arms that set the keys themselves (the wellsep and ablation factorials, and wellsep-timing's own three levels) are unaffected, since they state them either way.

`run_well_separation` has now crossed the line a second time, in the other direction: it defaults to `false` again from the commit that folded well-separation into the status score. It is the only key to have moved twice, and on 2026-09-11 it was removed with the per-generation stage it governed, so writing it in now has it warned about and ignored at either value. `allow_output_assumptions` followed it on 2026-09-11, as the eleventh change below records, so neither key can be restored by hand any longer. A campaign that depended on either reproduces at the commit its `PROVENANCE.json` names, through the vendored `scripts/` beside it, as the tenth and eleventh changes below record.

`genetic.selection_scheme` crossed the line on 2026-08-14, moving from `nsga2-truncate` to `nsga2-apportion` on the `2026-08-11-selection-default` campaign. Almost nothing here is exposed: 73,467 of the 73,531 archived run configs state the key themselves, so a current binary reads them exactly as their campaign ran them. The 64 that do not are all under `2026-07-13-fretish-sweeps`, every one a `sweep_B_pop50_takeoff_*`.

Those 64 need `selection_scheme = "weighted"` written in, not the scheme this change replaced. The default has moved three times, and only the last is this campaign's doing: `WeightedAverage` until 2026-07-15 (`587a5b6`), `Nsga2` from there until the 2026-08-06 rename to `Nsga2Truncate` (`96c7633`), and `Nsga2Apportion` from 2026-08-14. That campaign is anchored at `4d76d53`, which predates the first of those, so its unstated configs ran under `weighted` and have been misread since 2026-07-15 — a crossing this note did not record at the time. Re-running one against a current binary otherwise gets a scheme two changes removed from the one it measured.

The same commit changed what the status *scale* means rather than what a config says, which no amount of writing keys back repairs. `k_status_realizable` (1.0) now requires a candidate to be well-separated as well as realizable, and one the system can satisfy only by forcing its own assumptions to fail scores `k_status_unrealizable` (0.5) — level with a candidate no strategy exists for, where it previously scored the top tier. Status is a selection objective on both paths, so status-derived numbers and every quality figure downstream of selection are on different scales either side of this commit and do not compare across it.

`fitness.status_grading` crossed the line on 2026-08-11, and it is the widest crossing so far because the key did not exist before that date. Every campaign archived here ran the three-point `tiered` scale, none of them can state a key their binary had never heard of, and the default is now `mrs` — so reproducing any of them means writing `status_grading = "tiered"` into the config by hand. Omitting it does not shift a threshold, it swaps the status objective for a different function: `tiered` scores every unrealizable candidate 0.5, where `mrs` spreads that same region over the fraction of guarantee-side parts a greedy sweep keeps. Selection then sees a gradient the campaign never had. `2026-08-11-status-grading` is the one exception, and only because sweep G writes the key into both arms.

That campaign is also what moved the default, and it measured the size of the difference rather than assuming it: paired over 20 TLSF specifications and 24 seeds, `mrs` yielded 410/480 repairs against `tiered`'s 367/480 (50 `mrs`-only pairs to 7, sign test p < 0.0001) at a median paired wall cost of 1.15x. Almost all of the gain is on two specifications `tiered` grades as one flat value — `arbiter` 0/24 → 22/24 and `rg1` 7/24 → 24/24 — which is the reason a zero-yield row from an archived TLSF campaign on those families measures the scale rather than the search.

`fitness.mrs_admission_order` crossed the line on 2026-08-14, and like `status_grading` it does so from a standing start: the key did not exist before that date, so no archived config can state it. It is read only under `status_grading = "mrs"`, and every campaign archived here ran `tiered`, so reproducing one already means writing `status_grading = "tiered"` in by hand — and with that written, `mrs_admission_order` is not read at all and needs nothing. `2026-08-11-status-grading` is the exception that matters. Sweep G writes `status_grading` into both arms, so its `mrs` arm does read the new default and needs `mrs_admission_order = "spec"` written in explicitly to reproduce. Omitting it there does not shift a threshold. The greedy walk admits guarantee-side parts in a different order, and greedy returns a maximal subset rather than a maximum one, so the order decides the score. Over populations of mutants across six TLSF specifications the two orders score 0.587 against 0.529, and on `detector` the original specification scores 6/7 under `degree` against 1/7 under `spec`. The default moved on that population measurement rather than on a paired campaign, unlike `status_grading`, so a campaign is still owed. `gen_configs.py --pin-vintage` now writes the key, so campaigns archived from here on state it.

Three more moved in the commit that narrowed the defaults for push-button use: `ltlsynt_timeout_ms` `0` → `500`, `ltl2tgba_timeout_ms` `0` → `60000` and `max_scoring_failure_rate` `0.05` → `0.15`. Every TLSF campaign archived here already set all three to those exact values, so the TLSF archives are unaffected and reproduce as they stand. The FRETISH campaigns state none of them, and so now run under bounded tools where they ran unbounded; write the three in as `0`, `0` and `0.05` to reproduce one.

`mutation.p_remove_guarantee` crossed the line on 2026-08-13, and like `status_grading` it does so from a standing start: the key did not exist before that date, so no archived config can state it, and it arrives defaulting to `0.05` rather than to the `0` that describes every campaign here. It adds a mutation operator rather than shifting a threshold — the search can now delete a guarantee outright, which is a move none of these campaigns could make — so reproducing any of them means writing `p_remove_guarantee = 0.0` into the config by hand. That value is exact rather than approximate: the operator's probability is tested before the RNG is drawn, so at zero it costs no draw and the whole breeding stream is byte-identical to what it was before the operator existed. At any other value it is not, and no archived seed reproduces.

`tlsf.mutation.p_monotone` crossed the line on 2026-08-21, from the same standing start: the key did not exist before that date, and it arrives defaulting to `0.25` rather than to the `0` that describes every TLSF campaign archived here. It adds a third rewrite arm, offered ahead of the temporal and propositional ones, whose result is comparable to the formula it replaces under implication — a move none of these campaigns could make — so reproducing one means writing `p_monotone = 0.0` in by hand. Since 2026-09-11 it goes into the `[mutation]` table, that key having replaced `[tlsf.mutation] p_monotone`; the old spelling is warned about and ignored, so writing it there leaves the arm at `0.25`. As with `p_remove_guarantee`, that value is exact rather than approximate: the probability is read before the RNG is drawn, so at zero the arm costs no draw and the breeding stream is byte-identical to what it was before it existed. FRETISH campaigns were unaffected by this crossing, the arm being TLSF-only at the time; the FRETISH arm's own crossing is recorded below.

`tlsf.mutation.p_clone_assumption` crossed the line in the same commit range, on 2026-08-21, and from the same standing start: it defaults to `0.25` where every campaign archived here ran the equivalent of `0`. It changes what `p_add_assumption` appends — a copy of a live ASSUME conjunct rather than a formula built from the template — so a campaign that measured the template alone no longer measures it. Write `p_clone_assumption = 0.0` into the `[tlsf.mutation]` table to reproduce one; the probability is read before the RNG is drawn, so at zero it costs no draw and the stream is exact. FRETISH campaigns are unaffected.

`genetic.accumulate_repairs` crossed the line on 2026-08-25, moving from `false` to `true`. The exposure is every archived config that omits it, which is all of them bar the `2026-08-19-accumulator` campaign's own two arms and the sweeps that write the key explicitly, so reproducing any other campaign here means writing `accumulate_repairs = false` into the `[genetic]` table by hand. Unlike every other key in this note, the search is untouched by it. `RepairAccumulator` never draws from the `RandomSource`, so the seed stream is byte-identical at either value and only the set a run emits differs. That set moves enough to matter. It changes `n_repairs`, and it flips `implies_ideal` on a run whose good repair was lost from the final population, which are the primary endpoints of most archives here. The campaign that measured the key made it a *candidate* default, subject to a FRETISH replication that has not been run, so the flip departs from that campaign's own condition and the replication is still owed.

A third change is sharper than a shifted default, because it stops an archived config from running at all. On 2026-08-06 the two NSGA-II selection schemes were renamed: `nsga2` became `nsga2-truncate` and `nsga2-replicate` became `nsga2-apportion`. The old spellings are **rejected**, not aliased, so every config archived here — all of which pin one of them — fails against a current binary with an error naming the replacement. This is deliberate. Reproducing a campaign means building the commit its `PROVENANCE.json` names and running the vendored `scripts/` beside it, not editing the archived config to suit a newer binary; a config edited to run under today's defaults is no longer the record of what ran.

The archived **results** are unaffected and stay readable. Their `selection` column still says `nsga2`, and `canonical_scheme()` in `run_experiments.py` and `merge_experiments.py` maps that onto `nsga2-truncate` wherever the column is read, so archived rows still join new ones for resume, merge and cross-campaign comparison. Nothing under `experiments/` was rewritten to match the new names, and nothing should be: the column records the name the campaign ran under.

A fourth change keeps both its key and its value and moves only what they mean. The per-generation false-condition filter has been folded into the *vacuity* filter, which has also gained a semantic screen: a specification is rejected if any one of its guarantees is *valid*, tested one guarantee at a time by asking whether that guarantee's negation is satisfiable. Previously `filters.run_vacuity` gated a satisfiability check on the conjoined assumption side and nothing else, while the false-condition screen — a syntactically `false` condition on any assumption or guarantee — ran unconditionally, outside the flag entirely. All three screens are now one filter under `run_vacuity` alone.

The default did not move: `filters.run_vacuity` was `true` until the eleventh change removed it. No archived config sets it, so every campaign archived here ran the filter on, under the older and weaker meaning of the same word. That puts this change outside both cases above. Unlike the shifted defaults there is no key to write back, the archived value being the one a current binary reads; unlike the rename the config still runs, because nothing about it is rejected. It is the quietest of the four. An affected campaign re-run today raises no error and no warning, and simply searches under a stricter filter than the campaign did, discarding tautological guarantees the campaign was free to keep. The remedy is the one the rename already prescribes: build the commit the campaign's `PROVENANCE.json` names and run the vendored `scripts/` beside it.

One consequence reaches forward rather than back. Setting `run_vacuity = false` now also switches off the false-condition screen, which used to run whichever way the flag was set. No archived config sets the key, so no archive here is affected, but an ablation that turns vacuity off is no longer isolating the assumption satisfiability check — it drops three screens and prices them as one. A flag that gains screens gains them for its off position too, which is the half of a merge that is easy to leave unstated. The key itself went on 2026-09-11, as the eleventh change below records, so no ablation can switch the stage off at all any longer.

A fifth change moves no key, no value and no default, and still stops archived numbers from comparing. From this commit the gate that collects the realizable survivors applies the well-separation check to every one of them, whatever `filters.run_well_separation`, since removed, said. Before it that check ran per generation alone, so a not-well-separated specification still reached the output whenever it arrived by a route the offspring filters never cover — an elite carried through unchanged, or a copy of the seed population. Those repairs are now rejected at the gate, so written-repair yield falls from this commit on and a campaign's repair counts do not compare across it. Which candidates are bred and scored is unchanged; only which survivors are written out is.

A sixth change removes a key outright: `fitness.weight_halstead` went on 2026-08-13 with the Halstead objective it weighted. An archived config that sets it has the key warned about and ignored, and every config archived here states it, so every one of them runs against a current binary without the objective its campaign scored. Sweep C's `no-halstead` level goes in the same commit, and with it the Halstead ablation the `ablate-fret` and `ablate-tlsf` arms crossed as their third factor: the level set the weight to `0` against a default of `0.1`, so with the key gone it says nothing the `default` level does not. Both arms stand as 2x2 factorials of selection scheme by similarity metric from here on. The archived results are unaffected and stay readable, their `level_name` column still recording `no-halstead`, and the campaigns that ran the ablation reproduce the way the rename already prescribes: build the commit their `PROVENANCE.json` names and run the vendored `scripts/` beside it.

`filters.run_weakening` moved from `true` to `false` on 2026-08-20, and it is the first crossing recorded here that exposes nothing at all. All 1,464 archived run configs under `experiments/` state the key explicitly, because `gen_configs.py` pins it: the weakening screen is a crossed factor and `weakening` is one of `merge_experiments.KEY_FIELDS`, so a config that omitted it could not be joined back to the row it produced. Every one of them therefore read on a later binary exactly as its campaign ran it, until the key was removed on 2026-09-11 with the screen itself; the tenth change below records what that removal exposes.

A seventh change removes a key outright rather than shifting what it means. `genetic.repaired_operators` went on 2026-08-20 with the gating it provided, and the repaired mutation and crossover grammar is unconditional from that commit on. This is the case the "Config keys" section of `docs/dev/config-and-provenance.md` describes: an archived config that *sets* a removed key has it warned about and ignored. The three campaigns archived that day — `2026-08-20-ops-pilot`, `2026-08-20-ops-grammar` and `2026-08-20-ops-weakening` — set it in every one of their configs, on both arms, so every one of them runs against a current binary on the repaired grammar, whichever arm it recorded. Sweep O retires with the key, along with the `ops-fret`, `ops-tlsf`, `ops-pilot`, `opswk-fret` and `opswk-tlsf` runner profiles, following the precedent where `[filters.intervals]` retired the `wellsep-timing` profile and TLSF sweep V. The `PROFILE_CSVS` entries in `merge_experiments.py` are deliberately kept, so the archived CSVs stay mergeable after the profiles that wrote them are gone. Reproduce those three campaigns at the commits their `PROVENANCE.json` files name, through the vendored `scripts/` beside them.

An eighth change removes a key outright and exposes nothing at all. `mutation.strengthen_assumptions` went on 2026-08-26, and unlike the sixth and seventh removals it reinterprets no archived config: zero of the 75,646 archived `.toml` files under `experiments/` state the key. None of them could. `gen_configs.py` never emitted it and no sweep table ever crossed it, and its own doc comment said it was "retained as a flag only so the two directions can be crossed as an experiment factor", which none of the 19 archived campaigns did. The flag governed the direction in which the FRETISH assumption-side timing rewrite mutates, and at its default of `true` that direction follows the side, weakening a guarantee and strengthening an assumption. That default is now hard-wired in `src/genetic/mutation.cpp`. Every campaign archived here ran at it, so every one of them reproduces bit-for-bit, RNG stream included; the flag was read outside the draw sequence and never cost or consumed a draw. The TLSF path already ignored it entirely, `tlsf_monotone_rewrite` drawing its direction as a fair coin and deliberately not reading the key. The default move of `filters.run_weakening` above exposed nothing because every archived config pins it explicitly, and this key exposes nothing for the opposite reason, no archived config being able to name it at all.

`mutation.p_condition_type` and `mutation.p_scope` crossed the line on 2026-09-11, moving from `0` to `0.15`, and the FRETISH arm of `mutation.p_monotone` moved from `0` to `0.25` in the same commit. No campaign measured either move. Every FRETISH campaign archived here ran all three at `0`, so reproducing one means writing `p_condition_type = 0.0`, `p_scope = 0.0` and `p_monotone = 0.0` into the `[mutation]` table by hand. Each probability is read before the RNG is drawn, so at zero the stream is exact. `p_condition_type` reaches every FRETISH specification, where `p_scope` reaches only one that declares modes, which among the examples is `mode-arbiter` alone. The `p_monotone` arm fires inside `p_response` and `p_trigger`, so a sweep level setting both of those to `0` is unaffected by it.

The three `[fitness]` weights moved in the same commit, `weight_syntactic` `0.2` → `0.1`, `weight_semantic` `0.5` → `0.2` and `weight_status` `0.5` → `0.7`, following AuRUS's `Settings.java`. The exposure is only an archived config that omits them, and `gen_configs.py` pins them at `0.33` each and always emits them. They reach the `weighted` scheme's ranking alone; under either NSGA-II scheme they decide only the order repairs are written in and the reported `best_fitness`.

A ninth change moves the TLSF draw stream with no key to put it back. On 2026-09-11 `tlsf.mutation.connective_implies` was removed and case (2d) of `mutate_temporal` always offers `->`, drawing `next_index(5)` where it drew `next_index(4)`. `tlsf.mutation.monotone_atom_rules` and `monotone_extra_rules` went in the same commit, and the monotone rewrite offers both widenings unconditionally. All three defaulted to `false` and no archived config sets any of them, so every TLSF campaign archived here drew from the narrower menus, and no value written into a config restores them. No archived TLSF campaign therefore reproduces seed-for-seed at this commit or later; reproduce one at the commit its `PROVENANCE.json` names, through the vendored `scripts/` beside it. The FRETISH stream is untouched by these three, its call site having always offered both widenings.

A tenth change removes keys that archived configs do set. `filters.run_weakening` and `filters.run_well_separation` went on 2026-09-11 with the final weakening screen and the per-generation well-separation stage they governed, and `[tlsf.mutation] p_monotone` went with them, replaced by `[mutation] p_monotone`. A removed key is warned about and ignored, so an archived config that sets one still runs, under whatever the binary now does in its place. `mutation.p_stop` arrived on 2026-09-15 at `0.15`, from a standing start like `p_remove_guarantee`, and exposes nothing. It rewrites the stop condition of an `until` or `before` timing, and it tests whether the requirement holds one before it reads its probability or draws, so on a requirement without a stop timing it costs no draw at any value. No specification any archived campaign ran carries one, those timings having entered the grammar the same day, so every archive here reproduces seed-for-seed with the key omitted.

`fitness.keyword_similarity` crossed the line on 2026-10-06, moving from `"syntactic"` to `"semantic"` the day the key arrived. Every FRETISH campaign archived here ran the syntactic placement, and none states the key, so reproducing one means writing `keyword_similarity = "syntactic"` into its `[fitness]` table. Omitting it moves the timing, scope and condition-type order measures out of the syntactic objective and into the semantic one, mixed with the trace count at `semantic_trace_weight = 0.5`, and compares the keyword fields in the syntactic objective as tokens alone. Both objectives change, so selection changes and no FRETISH archive reproduces seed for seed without the key. `2026-10-06-keyword-weight` fixed the weight: re-scoring 4,694 archived candidates, the weights 0.25, 0.5 and 0.75 select the same first front in the median run. TLSF ignores both keys and is unaffected. `gen_configs.py --pin-vintage` writes both from this commit on, and `golden_config()` pins the syntactic placement so the determinism goldens hold.
