# counter

C++17 genetic algorithm for repairing unrealizable FRETISH specifications, using bounded model counting (SPOT + Ganak) for semantic similarity.

## Build

Enter the dev shell first (Nix is the primary workflow):

```sh
nix develop
```

Two presets — `debug` (ASAN+UBSAN, `build/`) and `release` (`build-release/`):

```sh
cmake --workflow --preset debug      # configure + build + test
cmake --workflow --preset release

# Incremental build only (after initial configure):
cmake --build build
cmake --build build-release
```

Non-Nix: requires CMake ≥ 3.25, Ninja (the presets' generator), a C++17 compiler, `libunwind`, and Node.js (runs the vendored FRET formaliser CLI, not fetched by CMake); everything else is fetched by CMake.

## Tests

```sh
ctest --preset debug                  # run all tests
ctest --preset debug -R syntactic     # run tests matching a regex
```

Test binaries land at `build/test/counter_tests`. The test framework uses `expect(bool, message)` and `fail(message)` from `test/test_support.hpp`; each test suite is a free function declared in `test/test_suite.hpp`.

The dashboard page's script is tested separately, under node's built-in runner (`test/web/*.test.mjs`, registered with ctest as `dashboard_page`; run directly with `node --test "test/web/*.test.mjs"`). `test/web/harness.mjs` extracts the `<script>` block from `web/dashboard.html` and evaluates it, so the tests run against the page that actually ships rather than a copy of it. CMake skips them when `node` is absent.

`test/drivers/e2e_tests.cpp` holds one end-to-end suite per driver (`driver_counter`, `driver_realize`, `driver_ltl`, `driver_mucs`, `driver_compare`, `driver_maximal`, `driver_lint_ideals`, `driver_signal_tracer`), each spawning the binary through `execute_and_capture` rather than calling into the library — the only cover `src/main.cpp`, `src/repair/`, `src/crash/` and each tool's own argument handling get. A new driver needs all of a suite function, its declaration in `test/test_suite.hpp`, both dispatch points in `test/main.cpp` (the named-suite branch and the run-everything list), an `add_dependencies` entry in `test/CMakeLists.txt` (or ctest runs before it is built) and the ctest registration; omit any one and nothing covers it. They assert the driver's contract — exit status, stdout markers, `run.json` fields, and `n_repairs` against the `repair_N` files written — rather than which repairs the search finds, which the `determinism` suite pins instead; asserting it here would break them on every deliberate operator change. Fixtures are inline rather than drawn from `examples/`, so editing an example cannot change what they assert, and a TLSF run writes a `repair_N.fitness.json` sidecar per repair, so a `repair_` prefix filter double-counts.

## Lint & Format

```sh
cmake --build build --target lint          # cpplint + clang-tidy + cppcheck + config parity
cmake --build build --target lint-cpplint
cmake --build build --target lint-clang-tidy
cmake --build build --target lint-cppcheck
cmake --build build --target lint-config-schema

cmake --build build --target format        # apply clang-format in-place
cmake --build build --target format-ci     # dry-run (fails if unformatted)
```

clang-tidy results are cached through ctcache, which the dev shell puts on PATH; being on PATH is the whole switch, and a translation unit is re-analysed only when its preprocessed content or the `.clang-tidy` config changed. The cache defaults to `<build-dir>/ctcache` rather than ctcache's own per-user `/tmp` directory, so it is gitignored with the rest of the build and each preset keeps its own — a deleted build directory costs one cold sweep. `CTCACHE_DIR` overrides the location, which is what CI sets so `actions/cache` can restore it between runs.

The same checks run from `.githooks/pre-commit`, which is tracked. Git refuses to clone hooks, so `core.hooksPath` has to be set locally once per clone; `cmake/githooks.cmake` does it at configure time, since the hooks shell out to build targets and cannot work before that anyway. Edit the hook in `.githooks/`, not in `.git/hooks/`, which git no longer reads once the path is set. Bypass a hook with `git commit --no-verify`; CI is the real enforcement.

## Coverage

`python scripts/coverage_badge.py` is the whole workflow: it configures the `coverage` preset (clang only, `-fprofile-instr-generate -fcoverage-mapping`, into `build-coverage/`), builds, runs `ctest --preset coverage`, merges the raw profiles with `llvm-profdata`, exports over `src/` and `include/` with `llvm-cov export --summary-only`, and writes `docs/coverage.svg`, which the README embeds. gcc cannot build that preset, the flags being clang's, and gcov would be a different number from a different tool. Only the preset's test half sets `LLVM_PROFILE_FILE`, so a suite run any other way leaves nothing to measure; stale profiles are deleted first, since an old one credits lines this build may no longer contain, and a failing suite refuses to write the badge. `llvm-profdata` and `llvm-cov` must be the same LLVM release as the clang that built the tree — the profile format is versioned and an older tool reads a current profile as malformed — which is why `llvmPackages.llvm` is in the dev shell.

The badge is a committed file rather than a call out to a badge service, so the README renders on a fork with no secrets and in an offline clone, which holds only while it is regenerated when the number moves. `--check` re-measures and fails on a byte difference; it runs as the tail of the `coverage` entry in the CI build matrix, under `--no-run`, so the badge check costs an export over the profiles that entry's `ctest` already wrote rather than a second instrumented build. That entry is on pushes to `main` rather than on pull requests, so a commit moving the figure fails after the merge; run the script before merging one. The denominator is every instrumented binary rather than `counter_tests` alone — 89.3% over the test binary against 83.6% over all eight — and every file in `src/` and `include/` has held non-zero coverage since the driver suites landed, the remainder being error and terminal branches (`include/status_line.hpp` at 54.8%, its tty-only paths, and the per-driver argument-error paths). A new binary must join `BINARIES` in the script, which fails loudly on a name it holds that is not built. The figure moves up to two tenths of a point between runs of one binary, the suite spawning real tools and branching on their timings and peak resident set, and 83.6% sits a tenth above a rounding boundary — so `--check` allows `CHECK_SLACK`, a quarter of a point beyond the committed number's rounding band, and fails on anything wider. Tightening that back to a byte comparison makes an unrelated commit fail on main over which side of 83.5% its runner happened to land.

## Config keys

Adding a TOML config key means editing four places, none of which the compiler ties together: the `apply_*` function in `src/config_io.cpp` that reads it, `config_json()` in `src/repair/manifest.cpp` that reports it (else the key never reaches `run.json` and a campaign's arms are invisible in the manifest it is meant to read, which is what two `[tlsf.mutation]` keys cost), `config_key_spec()` back in `src/config_io.cpp` (else the parser warns "unknown key" on a key it accepts), and `schemas/config-schema.json` (else editors reject it). `scripts/check_config_schema.py` enforces the last three against each other and against `example-config.toml`, and runs as part of `lint`.

`example-config.toml` is not merely illustrative: every value in it must equal the built-in default from `include/config.hpp`, so copying the file whole is a no-op. The same script enforces that, via a `DEFAULT_FIELDS` table mapping each TOML path to the `Config` member behind it — a new key must be added there (or to `UNPINNED_KEYS`, for the enums and for `runtime.parallel`, whose default is hardware concurrency) or the check fails rather than skipping it. This exists because eight keys had silently drifted, so the template quietly configured a different run from the one a user got by omitting it.

A config knob is worth keeping only if something turns it. Before adding one, and when auditing, count how many configs under `experiments/` actually set it — six per-filter run intervals, the `[syntactic]` component weights, `tlsf.mutation.p_guarantee` and `runtime.report_cpu_timing` were all removed on that evidence, having never been set in ~65k archived campaign configs. `python scripts/campaign.py describe --all --json` answers the same question over the 19 archives rather than the 65k files, by deriving each campaign's factor cross from its results CSV; the configs remain the authority where the two could disagree.

## Commit provenance

Every binary answers `--version` with `commit=`, `commit_short=` and `dirty=` lines, naming the commit it was built from. The hash is resolved at **build** time, not configure time: `cmake/version.cmake` runs `cmake/write_version_header.cmake` in script mode on every build, which renders `cmake/version.hpp.in` into `build/generated/git_version.hpp` via `configure_file` (so the file is rewritten only when the commit changed). Resolving it at configure time instead would bake in whatever HEAD was when cmake last ran, and `cmake --build` after a new commit would keep reporting the old hash — the exact failure this exists to catch. Only `src/version.cpp` includes the generated header, so a new commit recompiles one translation unit. `dirty` counts modified *tracked* files only.

`scripts/run_experiments.py` shells `counter --version` once at startup — never `git rev-parse`, which reports the source rather than the binary — and stamps `commit` (abbreviated) and `dirty` onto every CSV row, plus a per-host `<stem>-manifest-<host>.json` beside the CSV. It refuses to launch when a binary's commit differs from the working tree's HEAD, was built dirty, or cannot be read at all; `--allow-stale-binary` downgrades that to a warning. Neither column may join the resume key in `run_experiments.py` or `KEY_FIELDS` in `merge_experiments.py`: archived rows have no commit, so keying on it would make every one of them miss and re-run finished campaigns.

Campaigns closed before this existed carry a reconstructed `PROVENANCE.json` in their archive directory (`"attribution": "inferred"`), covering the profile commit only; `binary_commit` is `null` there and must stay that way. `experiments/README.md` documents the method and why a commit landing inside a run window proves nothing.

Each archived campaign also carries `experiments/<campaign>/scripts/` — verbatim copies of the `gen_configs.py`, `run_experiments.py` and `merge_experiments.py` that ran it, so the directory reproduces without the git history. `vendored_scripts` in its `PROVENANCE.json` records the source commit and blob sha per file; check a copy with `git hash-object`. Attribution defaults to `profile_commit`, but campaign content overrides it where the two disagree: `CSV_FIELDS` in `run_experiments.py` grew one column at a time, so a header pins the runner revision independently of any mtime, and the profile's seed budget, spec set and timeout caps narrow it further. The column count alone is necessary but not sufficient — a runner must also define the profile the campaign ran. Four campaigns (`factorial`, `wellsep`, `genpop-sweeps`, `tlsf-genpop`) are attributed against their anchor on that basis; do not "correct" them back. The last two ran off the unmerged TLSF branch and their source commits are not ancestors of `main` (`reachable_from_main: false`); the annotated tag `provenance/tlsf-branch` points at that branch's tip and holds all of them reachable, so never delete it — without it they are dangling objects that `git gc` collects and the recorded shas stop resolving. `2026-07-31-replicate` sits in the same position for a different reason: its branch `feat/replicate-campaign` was split into reconstructed pull requests rather than merged, so the same content reached `main` under fresh shas while every sha its `PROVENANCE.json` names still points into the branch, and `provenance/replicate-campaign` holds those under the same never-delete rule. `2026-08-26-assumption-reach` sits there through a rebase: `feat/assumption-construction` was rebased onto main on 2026-08-26 after PR #145 closed the manifest gap, rewriting all three shas its `PROVENANCE.json` names — the profile commit `2f2e260`, the two binary commits its rows carry, `0510b31` and `8b3cb23`, and `8b3cb23` again as the source of its vendored `scripts/` — into `3a10401`, `62af3ab` and `1593957`. Those shas are not repointed, being facts about the run: the results CSV stamps `0510b31` and `8b3cb23` into its own `commit` column, so editing them would falsify the record rather than correct it, and `provenance/assumption-reach` points at `8b3cb23`, the pre-rebase tip, holding all three reachable under the same never-delete rule. A rebase invalidates a recorded sha exactly as a split does, and is the likelier accident of the two, since a branch gets rebased whenever main moves under an open pull request, so re-check a campaign archive whenever its branch is rebased, split, or otherwise has its history rewritten. `2026-08-26-selection-smoke` is the second campaign to land there and the first to land there on purpose: `campaign/selection-smoke` was rebased onto main on 2026-08-27 after PR #146 merged, rewriting `3382e7f`, `921ce1b` and `6597b8c` into `a7c68fe`, `6d05f7e` and `a3d099e`, and `provenance/selection-smoke` was cut at `6597b8c` *before* the rebase rather than recovered afterwards. That is the order to keep: the tag is cheap beforehand and depends on `git reflog` once the branch has moved. Blob shas survive that and commit shas do not, so a vendored script still verifies under `git hash-object` while the `source_commit` beside it stops resolving, which is why the tag protects the archive and the blob check alone cannot. These paths plus `README.md` and `experiments/<campaign>/PLAN.md`, a campaign's pre-registered plan where one was written before launch, are the only tracked files under `experiments/`, via negations in `.gitignore` that need each directory level to be ignored by content rather than by name; adding a tracked file under a new subdirectory means re-opening descent into it first. The plan is tracked so its decision rule stays checkable against the result it was meant to bind; the root `PLAN.md` stays gitignored, a working file with no such claim on it.

A campaign's archived config is a partial record: `gen_configs.py` emits a key only where a sweep overrides it, so everything else comes from the binary's default at run time. Changing a C++ default therefore changes what every archived config *means* without touching a byte of it. `allow_output_assumptions` and `run_well_separation` crossed that line together, from `false` to `true`, in the commit that closed `2026-08-06-wellsep-timing`; `run_well_separation` crossed back later, and both have since been removed (see below). Writing either back to `false` is therefore warned about and ignored, and a campaign archived before that commit reproduces only at its own commit, through its vendored `scripts/`. On 2026-09-11 `[mutation] p_condition_type` and `p_scope` moved from 0 to 0.15 and `[mutation] p_monotone` from 0 to 0.25, so reproducing a FRETISH archive also means writing all three in at `0.0`. The fitness weights moved the same day, from 0.2/0.5/0.5 to 0.1/0.2/0.7 (syntactic, semantic, status), which reaches only a config that omits them; `gen_configs.py` writes all three into every config. Archived configs are not edited to compensate; the note in `experiments/README.md` ("Config vintage") is the record. Flipping a default that archived configs omit means adding to that note.

*Removing* a key is the sharper version of the same problem. An archived config that sets one still runs: `warn_unknown_keys` in `src/config_io.cpp` prints `config: unknown key <path>, ignoring` to stderr, with a hint from `retired_key_hint` naming the replacement where there is one, and the run proceeds without the key. The config is reinterpreted with one line of warning. The `[filters.intervals]` table went that way, which retired the `wellsep-timing` profile and TLSF sweep V along with it — that campaign's arms were three values of `well_separation`, so it cannot be regenerated at all and its archive is the only record. Retire the sweep and profile when their key goes; a generator that emits a key the binary warns on is worse than an absent one. `fitness.weight_halstead` went the same way on 2026-08-13, removed with the Halstead objective it weighted, which had no measurable effect on repair outcomes. Sweep C, the Halstead-weight ablation, is retired with it. On 2026-09-11 `[filters] run_weakening` and `run_well_separation` went with the machinery they gated, and `[tlsf.mutation] p_monotone`, `connective_implies`, `monotone_atom_rules` and `monotone_extra_rules` went with them. Of 79,255 archived configs, 79,236 set `run_weakening` and 12,323 set `run_well_separation`, so any that set either to `true` now runs without that filter. Every sweep T config of `2026-08-23-monotone` sets `[tlsf.mutation] p_monotone`, so its `monooff` arm now runs at the 0.25 default; no archived config sets the other three. FRETISH sweep J, TLSF sweeps W and Q, and the `cj-large`, `weakening-arbiter`, `wellsep`, `arbiter-hp` and `arbiter-padd` profiles retire with them, their `merge_experiments.py` entries kept, and those campaigns reproduce only at their own commits through their vendored `scripts/`. A second commit that day removed six more: `[tlsf.mutation] p_burst_continue` and `p_remove_assumption` with their operators, `[mutation] allow_output_assumptions` (an appended assumption's guard may always draw an output), `[runtime] max_concurrent_realizability` with `RealizabilityChecker::set_max_concurrency` and `gen_configs.py --max-realizability`, `[runtime] ganak_timeout_ms`, and `[filters] run_vacuity`, the vacuity stage now running every generation. Archived configs set only two of them: `allow_output_assumptions` in 12,323, of which the 9 at `false` sit in sweeps W and Q, already retired above, and `max_concurrent_realizability` in 4 under `2026-08-03-libspot-soak`.

Retiring a key's *value* goes further, because the parser refuses it. The selection schemes were renamed on 2026-08-06 — `nsga2` to `nsga2-truncate`, `nsga2-replicate` to `nsga2-apportion` — and the old spellings are rejected rather than aliased, by name and with a message saying what to do. Every archived campaign config sets one of them, so none of them runs against a current binary; reproduce those at the commit their `PROVENANCE.json` names, which is what the vendored per-campaign `scripts/` exists for.

Archived *results* are the separate half, and the one that needed work. `gen_configs.py` turns the scheme name into a config directory name, `scheme_of()` in `run_experiments.py` reads it back into the `selection` column of every results CSV, and that column joins `KEY_FIELDS` in `merge_experiments.py` — so renaming what the harness emits would have made all 224,861 archived rows reading `nsga2` miss their resume key and re-run finished campaigns. `canonical_scheme()` in both scripts maps the retired spellings onto the new ones wherever a `selection` value is read back, which is what keeps resume and merge joining those rows. The scheme itself never changed, only its name, so the mapping is an identity on behaviour. Renaming any other factor directory means adding to that mapping in the same way; leaving it out is silent, and shows up as a finished campaign re-running from zero.

## Campaigns

A campaign is declared once, in `experiments/<name>/campaign.toml`: the branch it runs on, the seed range each lab host takes, and the phases to run. Everything that acts on a campaign goes through `scripts/campaign.py` and reads that file, so the seed split exists in exactly one place. Never hand-roll an `ssh … nohup … run_experiments.py` line and never choose a seed range at the prompt; two hosts sharing a seed run it twice and the merge keeps one row per key, which costs machine time and yields nothing. `campaign.toml` is tracked (a `.gitignore` negation), because the hosts get it by checking out the campaign's branch.

The verbs are `stage` (put a host on the branch and rebuild it), `start` (launch the phases detached), `enqueue` plus the cron-driven `tick` (the unattended path), `dequeue` (take an entry back out, killing the tick holding it), `status`, `queue`, `collect` and `describe`. A phase is a search run or, under `kind = "score"`, the offline maximality pass over a results directory, run through `scripts/score_campaign.py` on each host over its own seeds and collected with `collect --curves`; that second kind exists because `2026-08-29-aurus-matched` and `2026-09-04-aurus-rematch` both needed the pass after their search, at 716 and 312 worker-hours, and both times it was hand-rolled from ssh'd bash scripts with the provenance assembled afterwards. `describe` is the archive's half: the campaigns closed before any of this existed have no declaration, so it derives one from the merged results CSV, the per-host CSVs and `PROVENANCE.json`, and prints it. It writes nothing into `experiments/` — the sources sit in the directory it reads, and a campaign is reproduced from its vendored `scripts/` at a commit where `campaign.py` does not exist. Staging refuses a host that is dirty, is running something, or is on another branch; `--force` prints what it would discard and requires the host name typed back, so it cannot be answered from a script. Queued campaigns sit on different branches, so `enqueue` pushes its campaign's branch and freezes the commit and build command into the entry, and a tick standing on the wrong branch stages itself onto that commit before it runs a phase — it must, since the declaration is tracked on the campaign's own branch and is unreadable from anywhere else. It stages for the branch alone: a dirty checkout, a live run, and an unpushed HEAD each stop it with the reason in `last_error`, because those are the three things a reset destroys that no fetch brings back.

`campaign.py status` is the source of truth for what a campaign is doing, it is read-only, and it costs about a second. Never carry campaign state in conversation context — re-run the poll instead, and re-run it again later rather than predicting what it will say. Never poll in a loop, and never spawn an agent to watch a run: `enqueue` the campaign and let the five-minute tick drive it.

`KEY_FIELDS` in `merge_experiments.py` and the resume key in `run_experiments.py` are off limits to any of this, and `commit`/`dirty` may never join either (see "Commit provenance"): 224,861 archived rows resume against those keys, and a campaign whose key moved re-runs from zero in silence.

`scripts/CLAUDE.md` is the operating manual — the state each `status` value means, when `--allow-stale-binary` is legitimate, the queue's transitions, and how a campaign is closed.

## Docs

Every header file in `include/` must have a corresponding `.rst` page under `docs/api/` and be listed in `docs/index.rst`. When adding a new header, add the page and toctree entry before committing. The site covers `include/` alone: implementation detail under `src/` is deliberately not published.

Only `///` reaches the site. A `//` comment on a declaration is invisible to Doxygen, which is why every `Config` member read as undocumented until its block was converted. The conversion is not free: `///` text goes through Doxygen's comment parser, so a bare `<input>` or `<output-dir>` parses as an HTML tag and `WARN_AS_ERROR` fails the build — wrap those in backticks, which also renders them as code.

Maths is `\f$ ... \f$` / `\f[ ... \f]`, rendered by KaTeX, not the MathJax that Sphinx would default to. Nothing is fetched at view time, which is the point: `sphinxcontrib-katex` bundles its JS but leaves `katex_css_path` pointing at a CDN, so `cmake/docs.cmake` stages `katex.min.css` and its fonts from the `katex` package into `_static/katex/` and `docs/conf.py.in` overrides that default. The stylesheet resolves its fonts relatively, so the two must stay in the same directory.

## Code style

- **Standard**: C++17, `-Wall -Wextra -Wpedantic -Werror` on all targets.
- **Formatting**: clang-format (`.clang-format` at repo root). Run `format` target before committing.
- **Linting**: clang-tidy (`.clang-tidy`), cpplint (`.cpplint.cfg`), cppcheck (`.cppcheck_suppressions.txt`). A blanket suppression in any of the three hides every future instance, not just the one that prompted it, so prefer a path-scoped entry or an inline `NOLINT` carrying the reason. Suppressions also go stale silently: check a candidate by removing it and re-running the linter before assuming it still does anything.
- **Comments**: only when the WHY is non-obvious — no narrating what the code does, no docstrings repeating parameter names already clear from the signature.
- **Assertions**: use `assert()` for internal invariants; `throw` only at API boundaries.
- **Overflow**: arithmetic on `Count` values must go through `count_add_overflow` / `count_mul_overflow` with an assert on the overflow flag.
- **Visitor pattern**: prefer `std::visit` with `if constexpr` branches over chains of `std::get_if` when dispatching on `std::variant` (see `requirement_to_ltl`, `mutate_timing`).

## Algorithm flow (`counter`)

1. Load `Specification` from `--input` JSON.
2. Build `AggregateWeightedFitnessFunction` (syntactic + semantic + status) and per-generation `FilterFunction` list from the original spec. The `vacuity` stage comes from a shared correctness table — `correctness_checks` (`include/filter/correctness.hpp`), TLSF twin `tlsf_correctness_checks` (`include/tlsf/filter.hpp`) — which builds one stage per row whose `per_generation` bool is set. Since 2026-09-11 that is a plain bool on the row rather than a pointer to a config flag, true for `vacuity` and false for `not-well-separated`, so the latter drives the input screen and the step-5 gate alone and no correctness stage can be switched off from a config. The same table screens the input spec once at load time. A failing check warns and names itself; it does not reject. An ill-separated FRETISH input is realizable outright, so rejecting would foreclose the repair the gate now makes reachable, a *descendant* that fixes the property. The verdict is `input_screen` in `run.json` (null when every check passed), so a campaign partitions on a key rather than grepping the log. The `status` objective scores on the three-point scale in `include/fitness/status.hpp` — 0 for a component unsatisfiable on its own, `k_status_realizable` (1.0) for realizable *and* well-separated, `k_status_unrealizable` (0.5) for everything between. Both front ends fold the well-separation query in behind the realizability one, so it is asked only where it can change the answer. A candidate realizable only by defeating its own assumptions therefore scores level with one no strategy exists for, deliberately: that is a correction to what the top tier meant, not a fourth tier, since a tier between 0.5 and 1.0 would rank cheating above failing and ill-separation is cheap for mutation to reach and expensive to leave, so the intermediate score would be the broad plateau the aggregate fitness already settles on for gutted vacuous repairs. Scoring it level keeps the candidate as breeding material and pays it nothing for the cheat. That is what `status_grading = "tiered"` and `"mrs"` both do, and what `"aurus"` deliberately does not: the third value reproduces AuRUS's own six-level ladder (0, 0.05, 0.1, 0.2, 0.5, 1.0, graded by which side is satisfiable alone) value for value so an ablation can cross the two gradings, and AuRUS asks about well-separation nowhere in its search — `WellSeparationAnalysis.java` has no caller in its `src` — so folding the query in behind that scale's realizability check would make it measure something other than the thing it is named after. It changes the search's scoring alone; the step-5 gate still asks every row of the correctness table whatever the search scored on.
3. Seed an RNG (from `--seed` or `std::random_device`); register crash metadata.
4. Run `Config::generations` rounds of `evolve_generation`: crossover + mutation, apply filters to the offspring (dedup, bloat cap, vacuity), then score the survivors in a thread pool. The `vacuity` stage runs three tests cheapest-first: a syntactic screen (a `false` condition, plus the TLSF section-literal equivalents), then a per-guarantee validity check, then the assumption-satisfiability conjunction. The separate `false-condition` stage was folded in on 2026-08-07, so one stage runs all three, and it has run unconditionally since `[filters] run_vacuity` was removed on 2026-09-11. The guarantee side splits per formula and the assumption side does not, deliberately: validity distributes over conjunction and unsatisfiability does not (`G p` and `G !p` are each satisfiable, jointly not), and the split gives a cache key per requirement rather than per side, which is what keeps the added solver calls near zero after the first generation. There is deliberately no syntactic test for a `true` guarantee *response* on the FRETISH path: `expand_after` negates the response, so under `AfterTicks` a `true` response is the strongest guarantee expressible rather than a no-op. Only the semantic check reads the lowered formula, so only it is right per timing. The TLSF screen's `true` test is sound because no condition/response lowering is involved. Both paths run the same list under the same stage names. Filters run **before** scoring, so a dropped candidate never costs a model-count or a synthesis query, and a filter's solver calls warm the caches scoring then hits. A stage that re-tests a filter's own predicate on the population that filter already judged is therefore dead code, not a safety net. The same ordering is why the per-generation well-separation stage and its `run_well_separation` key were removed on 2026-09-11, having defaulted off since `b101ada`: on, the filter dropped an ill-separated candidate before anything scored it and the 0.5 tier never fired, exactly as the old assumption-side tier sat unreachable behind the vacuity filter (`a64f833`, 887k scored candidates). That tier is now the only per-generation pressure against ill-separation, and output correctness is the gate's job (step 5). The one deliberate re-test is the filter fallback: when the chain empties the offspring, it re-applies the `FilterKind::Correctness` filters alone to the *unfiltered* offspring, a set those filters never saw, because dedup and the bloat cap run first and shadow them. It re-admits the candidates dropped for being duplicates or oversized and none of the ones dropped as unfit to breed from; with no correct offspring at all the elites carry the generation, and only an elite-free run restores them unscreened. Tagging a new filter is therefore load-bearing, and the untagged default is `Correctness` so a forgotten tag costs a wasted re-test rather than a re-admitted bad candidate. Selection follows `Config::selection_scheme`, whose two NSGA-II schemes rank identically and are named for the survivor step, the only thing that differs between them: `Nsga2Truncate` (TOML `nsga2-truncate`) ranks by non-dominated sorting + crowding distance over the individual objectives (`include/genetic/nsga2.hpp`) with (μ+λ) survivor pooling, then truncates the pool at `population_size`; `Nsga2Apportion` (TOML `nsga2-apportion`, the default since `c71ecf0`) ranks identically but deduplicates the pool before sorting and apportions the `population_size` slots over the distinct survivors by `1 / (1 + rank)`; `WeightedAverage` ranks by the aggregate scalar, but converges prematurely and is kept for comparison rather than use. These were spelled `nsga2` and `nsga2-replicate` until 2026-08-06, when the old spellings were removed rather than aliased — see "Selection scheme rename" below, which is the only reason ~225k archived result rows still read `nsga2`. The scored population always carries both the per-objective vector and the weighted scalar (`Scored<Spec>`).
5. Collect the realizable survivors from the final population (re-checked with `black` + `ltlsynt`). This gate is the enforcement point: it asks the status query, then every row of the correctness table unconditionally, in one conjunct order shared by both paths. The status query is asked on the run's own `status_grading` on both paths; the FRETISH gate hard-coded `Tiered` until 2026-09-09, so a run configured `aurus` scored its search on the six-level ladder and judged its output on the three-point one. That never changed the admitted set, the correctness table being applied whatever the scale folded in, and it cost a cold well-separation query per survivor under a grading whose search asked none. Neither path passes an admission order here: the order decides which queries the MRS walk memoises, never whether the top tier is reached. A row's `per_generation` bool governs per-generation search pressure alone, so no property enforced during the search is dropped at the output — which is what closes the elite and seed-population leak. Well-separation goes last, being the one row that can be cold at the gate: status is a scored objective and vacuity's queries are keyed per requirement, so both are already memoised, and no generation stage warms an `ltlsynt` well-separation query. Adding a `FilterKind::Correctness` filter therefore means adding a table row, or the gate never sees it; the `correctness` test suite asserts that every such stage the generation chain runs has a matching row, by name and on both paths.
6. Apply final filters over what the gate returned: dedup, then the optional implication filter to keep only maximal specs. That filter now collapses equivalence too: mutual implication subsumes one side, the survivor being the one with the higher syntactic similarity to the original and `Specification::operator<` deciding a similarity tie, because equivalent specifications are one repair written two ways and emitting both charges a reader with a choice that is not one. The tie-break is a total order rather than whichever pair finished first, the pairwise checks running concurrently and a first-finished rule not reproducing under a fixed seed; it costs no extra solver call, both directions having been computed already, and a timed-out check reads as non-implication, so an equivalence neither direction proves in time keeps both sides. It shrinks `n_repairs` and `n_implies` out of comparability with archived campaign rows while moving no endpoint, `implies_ideal` being a per-run existential and `best_relation` a maximum, and it bit harder on TLSF than on FRETISH until 2026-09-11, when `spec_implies` stopped decomposing per requirement and began lowering the whole specification to one LTL formula as `tlsf_spec_implies` always had, so the two now ask the same question of the same shape of formula; `n_equivalent_collapsed` in the diagnostics counts the pairs found equivalent, a class of k members contributing k-1. That FRETISH change is a comparability break of its own, and a wider one. The old check asked each of dest's guarantees to be implied by *some single* guarantee of from, and the assumptions the other way round, so it missed every implication holding only through several requirements together and asked 9 to 26 queries per pair where one now suffices. It under-detected, so the new check admits implications it missed, and `n_repairs` and `n_implies` move on every FRETISH row ever recorded; `compare` and `lint_ideals` call the same function and move with them. Measured over 25 paired runs (`fsm`, `fsm-timing`, `fsm-combined`, `takeoff` and `mode-arbiter` at seeds 0 to 4, gen10/pop200, arms interleaved per case), `n_accumulated_repairs` is identical on 25 of 25, so the search is untouched and the whole difference is the final filter: `n_repairs` falls 17.8% pooled, 860 to 707, per cell between -60.7% (`fsm` seed 1) and +6.9% (`mode-arbiter` seed 1), down on 22 cells and up on 2, so a single run can go either way. `implies_ideal` does not move, reading 15 of 25 in all three compare cells (the old binary scored by the old `compare`, the new binary scored by the new one, and the old output rescored by the new `compare`). Nothing guarantees that, the filter keeping the weaker side of an implication and the dropped side being the one that may have implied the ideal, so it is a result rather than a corollary. The relation mix does move, incomparable falling 819 to 662 between the first two cells, and `strictly weaker` rising 9 to 26 when the new `compare` rescores the old output, the cell that isolates the compare half. The sampled-word prefilter shipped in the same arm cuts implication comparisons 76.5%, 37,947 to 8,917 over 205,549 refutations, and wall time 28.9%, and one `fsm-combined` cell gained 7 implication timeouts where the old arm had none. Both paths' final filters run on a `SatisfiabilityChecker` of their own, with `set_simplify(false)` and SPOT's budget raised to `black_timeout` — TLSF since 2026-09-03, FRETISH since 2026-09-09. Their queries are whole-specification implications of 1000–1600 characters, and on humanoid-531 the stage was 264s of a 312s run with 96.7% of its solver time in `ltlfilt --simplify`, a pass that settled nothing `--satisfiable` could not; the search's 500ms `k_spot_budget` then left 316 of those unsimplified queries undecided, and an undecided `ExpectUnsat` query is never escalated, so it read as "keep both". FRETISH kept the search's settings for a year longer because its implication check decomposed per requirement and that shape had not been measured. Measured at 40 generations of 1000 it pays the same tax: the simplify pass is 59–61% of every `ltlfilt` exec a run makes (37,171 of 61,100 on `fsm`, 28,573 of 48,093 on `takeoff`, the identity being `ltlfilt calls = simplify misses + satisfiability misses`), 122 of `takeoff`'s simplify calls spent the whole 10s `ltlfilt_timeout` and returned the formula unchanged, and `takeoff` declined 109 escalations at the 500ms budget against `fsm`'s 0, so the budget was costing output on the larger families and not only time. The per-generation checker is untouched on both paths, its single-requirement queries being the ones the simplify pass and its `normalised` cache key were measured to help (`src/runner/black.cpp`), and the same two settings drive `maximal` and `compare` for the same reason. A weakening screen sat between dedup and the implication filter until 2026-09-11, when it was removed with `run_weakening`. It had defaulted off since 2026-08-20, because over the 720 matched runs of `experiments/2026-08-20-ops-weakening` turning it off gained `implies_ideal` on 38 and lost it on none. It reaches the same antichain as one sweep over the union wherever no implication check times out, and a timed-out check reads as non-implication on either route, as it always did. The two routes ask different pairs, each batch asking the pairs within itself and between itself and the maximal set so far, so `run.json`'s `implication.comparisons` and `skipped` do not compare with a batch run's. ## Elitism

`elitism_rate` defaults to **0.1**, and both standing arguments point at 0: under either NSGA-II scheme the (μ+λ) survivor step already pools parents with offspring and keeps the best, so a carry-over on top adds nothing on paper, and elites bypass the offspring filter chain, so that fraction of every generation skips the correctness stages — which costs search pressure rather than output correctness, the step-5 gate screening what an elite carried in either way (`d7733fc`). The 2026-08-07 A/B (`experiments/2026-08-07-elitism`, at `nsga2-truncate`) found TLSF yield better at 0, 0.746 against 0.714 on McNemar p = 0.0002, for 16.2% more wall time. That yield advantage did not replicate: the 2026-08-23 `monotone` campaign crossed the same two values at `nsga2-apportion` over 500 paired TLSF runs with `accumulate_repairs` on in both arms, and read 472 of 500 against 470, quality null on every read (exact McNemar p = 1.0000 run-level, exact Wilcoxon p = 0.7188 per family), and 4.0% more wall time at 0. So the only measured difference on the corpus counter is now benchmarked against is that 4.0%, and only 0 and 0.1 have ever been measured. `golden_config()` in `test/genetic/determinism_tests.cpp` pins the key explicitly, so a later default move fails the determinism suite rather than silently re-recording itself.

## Crossover

Both crossovers follow AuRUS's `SpecificationCrossover` (`~/projects/tools/aurus/src/geneticalgorithm/SpecificationCrossover.java`, level ≥ 2, its default) and its `FormulaUtils.replaceSubformula` / `combineSubformula`. Per side — assumptions and guarantees on the FRETISH path, the assumption and guarantee sections on the TLSF one — **exactly one conjunct is drawn from each parent, uniformly and independently, and merged**: with probability 1/2 a subformula of the first is replaced by one drawn from the second, otherwise the two are joined under a fresh binary operator. Every other slot is the first parent's. There is no branch that copies a field verbatim, so a crossover that fires always recombines.

The donor's slot is unrelated to the target's, which is the point. Recombining every slot index-for-index, as both paths did until 2026-08-14, confined each graft to the pair of requirements already occupying the same position, so no material could move between slots. Two consequences follow from that change and are easy to reintroduce by accident:

- **The offspring keeps the first parent's shape**, since the merge is written back into a slot of the first parent. Only the in/out atoms (FRETISH) or signals (TLSF) have to match, and the equal-length guard both paths carried is gone. It existed only because index-for-index pairing needed it, and it meant the first individual to gain an assumption could no longer breed with anything.
- **A slot's descent is still positional.** AuRUS removes the target conjunct and *appends* the merge, which reorders the side and shortens it when the merge fails; counter cannot, because slot *i* of a candidate must keep descending from slot *i* of the original (see "Removable guarantees"). Writing the merge back in place is the whole adaptation.

Deleted and non-weakenable requirements are drawn as neither target nor donor. Two further divergences from AuRUS are deliberate. Its `≤ 2 temporal operators` rejection is dropped, since rejecting there means dropping the conjunct and counter has the bloat-cap filter for the same job. And on the TLSF path, where AuRUS grafts only whole temporal subtrees, a conjunct with no temporal subformula offers itself as its one graft site rather than failing: INITIALLY, PRESET, REQUIRE and ASSERT are routinely propositional, their temporal operator coming from the lowering, so without the fallback crossover would be a no-op over most of a specification. The FRETISH condition and response fields are propositional by construction, so that path selects propositionally throughout and joins under ∧, ∨, →, ↔ rather than AuRUS's ∧, ∨, U, W.

The determinism goldens moved with this (96 draws to 149): a graft that always fires draws once per node of the field it rewrites, where a copy branch drew once in total. The operator repairs below took the same stream to 212. There is one golden rather than two: the legacy arm was deleted with its key on 2026-08-20.

The condition type and the scope are crossed too since 2026-09-11, each taken whole from one parent on a coin after the timing's draw, where both had stayed with the first parent. That is two draws per crossover and ungated, so the goldens moved again, from 212 draws to 187, which is what `test_generation_draw_sequence_is_pinned` holds today. The count fell because the extra draws shift every later one, which changes which offspring deduplicate away and so how much later generations breed. The scope keeps its mode on the move, which is sound because `crossover_specifications` already refuses parents whose declared modes differ.

## Operator repairs of 2026-08-19

`experiments/2026-08-14-aurus-h2h/REPORT.md` measures a set of defects in the mutation and crossover grammar against 2,295 archived repairs; these are the fixes.

All seven are **unconditional** since 2026-08-20. They sat behind `[genetic] repaired_operators` while the campaign that would decide them ran; the key and both legacy code paths were then deleted outright rather than the default being flipped, so there is one grammar and one RNG draw stream. Restoring the old behaviour means reverting that commit, not setting a key.

The measurement is `experiments/2026-08-20-ops-grammar` and `experiments/2026-08-20-ops-weakening`, two paired campaigns over the same 720 `(spec, seed)` cases, written up in the latter's `REPORT.md`. Read it before revisiting any of this, because it does not say what the smoke test predicted. With the weakening screen on the repaired arm wins TLSF at p = 0.047; with the screen off (the default from that day until the screen's removal on 2026-09-11) both paths are null, and the 2x2 shows why: dropping the screen lifts the *legacy* arm by 19 TLSF runs against 6 for the repaired one, so the two changes recover substantially the same repairs. The pooled null is not flat, though. `minepump` is unreachable under the legacy grammar with the screen on (0/20 against 12/20) and still leads 13 to 7 with it off, while `humanoid-531` loses runs to the repairs in both campaigns, being the family the pilot measured building much larger formulae. The graft helps where a repair needs new material and hurts where it only bloats.

The decision to make them permanent therefore rests on that reachability result and the 2026-08-14 audit rather than on the pooled endpoint, which is null under the shipping configuration; the pre-registered rule, read under that configuration, said do not flip. Both readings are recorded in the two archives' `PROVENANCE.json`. Sweep O and the `ops-*`/`opswk-*` runner profiles retire with the key, and every config in those archives sets it, so they reproduce only at their own commits through their vendored `scripts/`.

Three simplifier folds landed in the same commit as the repairs and were never gated: `G G φ → G φ`, `F F φ → F φ` and the U/W/R self-joins in `src/prop_formula/simplify.cpp`, `Formula::simplify()` having no configuration in reach. Eighteen more followed on 2026-08-28, the boolean constants folding through every temporal operator: `simplify()` had folded them propositionally only and `Next` had no case at all, so the `Constant` monotone rewrite's own output left `G(false)`, `X(true)` and `(true) W (false)` standing as distinct spellings of one constant, and 30.4% of the formulae reaching `simplify_ltl` and 43.7% of those reaching `ltlsynt` mentioned one. `φ W false ≡ G φ` and `false R ψ ≡ G ψ` are the two that do not simply annihilate. **This is not a wall-time change.** A paired A/B over 33 cases read null (median +1.0%, 16 of 33 faster, sign p = 1.000), and the two halves fail for opposite reasons: on FRETISH the folds never fire, the temporal structure there being assembled as a string by `requirement_to_ltl` rather than held as a `Formula`, and all nine pairs returned identical repair counts; on TLSF they fire hard, cutting the constants SPOT still had to reduce by 18.1%, and 22 of 24 pairs then returned a different repair count, the per-case spread swallowing a 5% effect whole. The case for keeping them is that a guarantee which folds to `true` is a gutted guarantee whether or not anything notices, which is a search-quality question and wants its own campaign. The FRETISH determinism goldens do not move, `Formula` on that path being propositional by construction. They shipped in both arms, so both campaigns measured the repairs *given* the folds and neither can attribute anything to them — `experiments/2026-08-20-ops-grammar/PLAN.md` section 4 registered that before the run.

- **An atom can grow.** `mutate_atom_formula` draws a third move beside rename and negate: graft a drawn anchor onto the atom under a connective. The only in-place growth rule before this was `mutate_not_subtree`'s, which fires at a `Not` node alone, so guarding a positive literal took three chained draws through unrealizable intermediates while guarding a negated one took a single draw. An empty atom pool keeps the old two-move draw, there being no anchor to take.
- **The temporal path can preserve a connective.** `mutate_temporal` case (3) gained a fourth arm that keeps the node's own kind and mutates its children, so an implication is no longer reachable only to be destroyed. `pick_binary_kind` excluded `Implies` at the time, following Brizzio's fragment — which is Owl's negation normal form, where an implication is a disjunction and there is nothing to re-emit; it draws `Implies` since 2026-08-21 (see "Implication in the TLSF grammar" below).
- **An assumption obliges an input.** `tlsf_add_assumption` draws the consequent's literal from the inputs alone, while the guard may draw an output as well. `allow_output_assumptions` governed the guard alone until 2026-09-11, when it was removed and output guards became unconditional. An assumption obliging an output is one the system can defeat by withholding its own signal; well-separation catches the unconditional `G F <output>` and passes the guarded form, which 180 of the corpus's 783 appended assumptions were. The consequent's modality is drawn from {F, X, nothing} rather than hard-wired to F, and a guard identical to its consequent has its polarity flipped rather than emitting a tautology.
- **Sections are not sides.** Mutation and crossover both read a slot's section, not only its side. An initial condition — INITIALLY or PRESET — draws from its own signals, takes only the propositional rewrite, and accepts a crossover donor only from its counterpart section. Basic TLSF requires both to be propositional over one side's signals, and the corpus holds 15 INITIALLY entries carrying a temporal operator and 8 PRESET entries carrying an input. The atom pool moved per-section on this argument; the bloat cap's baseline deliberately did not, having been tried and measured (see below).
- **One occurrence gives way.** TLSF crossover's graft replaced every occurrence of the chosen subformula, multiplying the donor where a conjunct held it twice; it now replaces the first, which is what its callers document.
- **The FRETISH graft site is uniform.** `replace_subformula` and `combine_subformula` drew a fair coin at each node of a post-order walk, reaching the k-th node with probability 2⁻ᵏ and grafting nowhere at all with probability 2⁻ⁿ — half the time for a single-atom field, which returned the first parent's field verbatim from an operator documented as always recombining. `mutate_atom_name` also gained the distinctness guard its TLSF twin already had.

One change the report recommended is **not** kept. Giving the bloat cap a per-section baseline, rather than the largest formula anywhere in the original, tightens it exactly where a graft needs room: a weakening grows a conjunct, and a small conjunct in a section of small conjuncts has nowhere to grow. Measured over 20 seeds it raised the bloat-cap drop rate on `arbiter-aurus` from 1.6% to 9.4% and cost that family 9 of its 10 ideal-implying runs, with `rg2` losing 2 of 20. The cap keeps its specification-wide baseline. A filter tightening that fights an operator loosening is the general shape to watch for here.

The graft draws its anchor's polarity as well as its atom. A positive-only anchor cannot reach `high_water & !methane` from `high_water`, which is `minepump`'s ideal, and a first implementation without the polarity draw left that family unmoved at 1 of 20.

Two of the seven change more than a branch, and the gating has to keep the *order* of draws as well as their count. `tlsf_mutate` draws its slot after the atom pool under the legacy grammar and before it under the repaired one, because the repaired pool follows the slot's section; and `cross_side` on the TLSF path tests the donor pool for emptiness before drawing its target under the legacy grammar and after it under the repaired one, for the same reason. Collapsing either pair into one order silently breaks the arm it is not written for, and the FRETISH determinism goldens do not cover the TLSF path.

## Implication in the TLSF grammar

`pick_binary_kind` (`src/tlsf/mutation.cpp`) draws from {∧, ∨, →, U, R, W} — six kinds, `Implies` included since 2026-08-21. It excluded `Implies` and `Iff` before that, following Brizzio's fragment, which is Owl's negation normal form and has no implication node to re-emit. The FRETISH twins in `src/genetic/mutation.cpp` and `src/genetic/crossover.cpp` always drew `{And, Or, Implies, Iff}`, so the gap was TLSF-only and the FRETISH determinism goldens do not move with it.

The exclusion put three subjects out of reach outright. `ltl2dba-r-2`'s sole ideal is its input with the root `<->` replaced by `->`, and `ltl2dba-theta-2` and `ltl2dba27` are the same shape; `mutate_temporal` case (3) already reaches an `Iff` node — it is the default branch, over any binary node — so widening the draw is the whole change and no dedicated arm is needed.

`Iff` stays out of the draw. The defect measured was that a biconditional could not be *weakened*, not that one could not be built, and a rewrite that manufactures biconditionals has nothing behind it.

`pick_connective_kind`, the sibling drawing the connective for case (2d) of `mutate_temporal`, draws `Implies` as well, as `next_index(5)` over {U, W, ∧, ∨, →}. Case (2d) is the arm firing at an atom or a unary node, and it grafts a drawn anchor onto the mutated child under a connective, so without `Implies` the shape `p -> X phi` took more than one draw to reach at exactly the nodes where a guard has to be introduced. That is the shape of every minimal guarantee weakening, and the shape `tlsf_add_assumption` hard-codes. The graft passes the anchor first, giving `anchor -> inner`, the guard-implies-response direction. `Release` stays out of this menu, being already in `pick_binary_kind`. The arm sat behind `[tlsf.mutation] connective_implies`, default false, until 2026-09-11, when the key was removed rather than flipped, so the TLSF draw stream changed and no key restores the old one. The FRETISH determinism goldens do not move, the gap being TLSF-only, and `Iff` is now the one propositional connective the FRETISH twins draw and the TLSF menus do not.

## Monotone rewrites

`monotone_rewrite` (`src/genetic/monotone.cpp`, declared in `include/genetic/monotone.hpp`) is called by both front ends, and both read one key, `[mutation] p_monotone` (`Config::p_monotone`, default 0.25), which replaced `[tlsf.mutation] p_monotone` on 2026-09-11. On the TLSF path it is a third rewrite arm, offered ahead of the temporal and propositional ones at the rate it always had. On the FRETISH path it is offered *inside* the `p_response` and `p_trigger` arms, so it is unobservable unless one of those two is above 0, and its default there moved from 0 to 0.25 with the merge. It was `tlsf_monotone_rewrite` in `src/tlsf/mutation.cpp` until 2026-09-09. The move went downward because `src/tlsf/mutation.cpp` includes `genetic/mutation.hpp`, so shared code goes into the genetic layer and never the reverse; `draw_literal` moved down with it and is declared in `include/genetic/mutation.hpp`. Its result is *comparable to its parent under implication*: `Weaken` returns a formula the parent implies, `Strengthen` one that implies the parent. It exists because the general rewriters leave the implication order, which the 2026-08-14 audit's section 5 measures as changing the AST shape 93.6% of the time. The size of that gap was misread until 2026-08-27. That audit read `best_relation` as incomparable on 238 of counter's 499 runs (47.7%) against 20 of AuRUS's 780 (2.6%), and the two sides were not measured over the same set. The counter figure is a maximum over its maximality-filtered `repair_N` output (`run_implication_filter` defaults true), where AuRUS's was a maximum over its unfiltered realizable and well-separated solution set, a mean of 317.7 solutions per run against counter's 37.9; that filter migrates a run from `strictly weaker` to `incomparable` whenever a weaker solution is dominated by an off-axis one. Rescored through counter's own maximality filter, over 203 cells spanning the 20 families both tools cover, AuRUS reads incomparable on 46 of 203 (22.7%) against counter's 150 of 400 runs (37.5%) on the 2026-08-21 ship campaign over those same families. The real gap is about 15 points rather than the ~45 the old figures implied, and counter remains the more incomparable of the two, so the operator's premise holds. Nothing about the operator changes. Two limits sit on that rescore: the AuRUS side is a partial sample, 203 of roughly 600 cells for those families, and the counter side comes from the ship campaign rather than the audit that produced the 47.7%. `implies_ideal` was invariant under the filter on 202 of the 203 cells, so only the relation mix was misread and the audit's endpoint conclusions stand. The rescore is `experiments/2026-08-14-aurus-h2h/PROVENANCE.json` `maximality_rescore`, with its script vendored beside it as `scripts/aurus_maxscore.py`. AuRUS has the property structurally: two of its three mutation visitors (`FormulaWeakening`, `FormulaStrengthening`) are monotone by construction, a 2-in-3 share against which a quarter is a conservative first value. The campaign that tunes it is owed.

**Polarity is what makes the guarantee hold through nesting.** A weaker subformula weakens the whole formula only where it occurs positively, so `Not` flips the direction, so does the antecedent of an `Implies`, and a child of an `Iff` has no polarity at all and is not a rewrite site — a biconditional is monotone in nothing. The site is drawn uniformly over the nodes with a determinate polarity and the rule uniformly over those applicable at that node, following the same argument as "The FRETISH graft site is uniform": a fair coin per node reaches the k-th with probability 2⁻ᵏ. Adding a rule means adding it to `rules_at` or `extra_rules_at` under the kind it fires at *and* to the direction it belongs to; a rule filed under the wrong direction fails `test_monotone_rewrite_direction_holds` rather than surfacing later as a repair the implication filter drops. The FRETISH arm is the same argument applied to the lowering rather than to the formula, and it comes out as a three-entry table in `src/genetic/mutation.cpp`. `scope_wrap` places its argument positively in all eight scope branches, and the continual wrapper `G(c -> body)` and the trigger's two conjuncts `G((!c & Xc) -> X(body)) & (c -> body)` all place `body` positively, so the response takes the requirement's own direction, flipped under an `only` scope, whose lowering applies the dual wrapper to `negated_timing_body` and so puts the response under a `Not`. Under `after n ticks` the response is sat out rather than reversed: `expand_after` builds `!r & X(!r & X(... & X(r)))` and the bounded form conjoins `for n (!r)` with `within n+1 r`, so the response occurs at both polarities and no rewrite of it says anything about the requirement. The condition is uniformly negative under a continual condition type, being the antecedent of `G(c -> body)`, so it takes the flipped direction, and under a trigger it is sat out too, the rising edge `(!c & Xc)` holding it at both polarities at once. `test/genetic/monotone_arm_tests.cpp` (ctest `counter_tests.fretish_monotone`) checks that table against a solver rather than against the argument for it, lowering each mutated requirement and asking the implication through `global_sat_checker()` at `QueryPolarity::ExpectUnsat`; each entry was verified by mutation, dropping the `only`-scope flip, the `after n ticks` guard or the trigger guard each failing the suite.

The direction is a fair coin rather than aligned with the side, and deliberately does not follow the assumption-side timing rewrite, which is hard-wired to strengthen. Repairing unrealizability does mean weakening the guarantee side and strengthening the assumption side, but a search that can only move that way cannot recover from an ancestor that weakened past the ideal, and `implies_ideal` is lost by overshooting as surely as by never arriving. What the arm buys is comparability, which both directions deliver equally, leaving the aggregate fitness to choose between them — which is also why AuRUS draws its two monotone visitors with equal probability. That coin is the TLSF arm's alone: the FRETISH one takes the requirement's own mutation direction, as its timing, condition-type and scope arms already do.

Both paths reach it since 2026-09-09. The probability is read before the RNG is drawn on either path, so at 0 the arm costs no draw and the breeding stream is byte-identical to what it was before it existed — the `p_remove_guarantee`, `p_condition_type` and `p_scope` discipline, and the reason the key is in the "Config vintage" note in `experiments/README.md` twice, once for its TLSF arrival and once for the FRETISH default move. `test_zero_probability_costs_no_draw` in `test/tlsf/monotone_tests.cpp` pins the TLSF count; the FRETISH half extends `test_new_arms_cost_no_draw_at_zero` in `test/genetic/determinism_tests.cpp` and compares *rendered draw traces* rather than draw counts, since the arm replaces one rewrite with another rather than appending draws, so two rewrites of one field can draw the same number of times and take different branches doing it. The arm left the goldens where they were, and `golden_config()` pins the key at 0, which is why the 2026-09-11 default move did not shift them either.

`AddOperand` is offered at every node. `Constant` and `AddOperand` are the two rules sound at every node, and `AddOperand` was once offered at `And` and `Or` alone, leaving an `Atom` with `Constant` as its only monotone move, so growing a literal into a disjunction was reachable only where a disjunction already stood and gutting the node to a constant was the whole menu at a literal. Every assumption-shaped ideal in the corpus is a disjunction built out of literals, and AuRUS reaches them because its `FormulaWeakening` applies `a -> a | b` at a literal. The connective comes from the rewrite direction rather than the node's own kind, the two agreeing wherever the narrower menu offered the rule at all.

Five extra rules fill three gaps in the base menu: `Release` carries no base rule while its duals `Until` and `WeakUntil` each carry one, `Next` carries none, and `Iff` carries only the weakening to one of its implications, so without them the whole menu at all three was the rewrite to a constant. Each is an operand or a disjunct of the semantics it fires at. `phi R psi` weakens to `psi` and strengthens to `G psi`, from `phi R psi == G psi | (psi U (psi & phi))`; `X phi` weakens to `F phi` and strengthens to `G phi`, from `F phi == phi | X phi | XX phi | ...` and `G phi == phi & X G phi`; `a <-> b` strengthens to `a & b` or `!a & !b` on a fair coin, as `IffToImplies` draws between its two directions. `rules_at` appends `extra_rules_at`'s result after its own switch.

Both widenings sat behind `[tlsf.mutation] monotone_atom_rules` and `monotone_extra_rules`, default false, until 2026-09-11, when the keys and the `MonotoneRules` struct carrying them were removed; the signature is now `monotone_rewrite(formula, direction, atoms, random_source)`. The FRETISH call site had always passed both on, so that path is unchanged and the TLSF draw stream changed. `test_monotone_rewrite_direction_holds` carries a `Release` and a `Next` in its subject list, so every rule is checked monotone against `black` rather than against the argument for it. A FRETISH condition and response are propositional by construction, so the `Release` and `Next` rules never come up there and the propositional ones carry the path. Manifest `k_schema_version` went 24 to 25 for the FRETISH key, and no campaign has measured the arm.

## Cloned assumptions

`tlsf_add_assumption` emits at most 7 nodes — `G F ℓ`, or `G(guard -> modality(ℓ))` — and the assumption-shaped ideals are far larger. `gyro-var2`'s single ideal is roughly a 29-node assumption, the polarity mirror of the specification's own third assumption, and over 112 emitted `gyro-var2` repairs counter appended only 6 assumptions, every one template-shaped. Under `[tlsf.mutation] p_clone_assumption` (default 0.25) the operator instead appends a **copy of a live ASSUME conjunct**, which ordinary mutation edits on later generations. AuRUS reaches a near-duplicate assumption through its level-1 crossover, which unions conjunct subsets; counter's crossover draws exactly one conjunct per side and cannot, so the move belongs to mutation here.

Only ASSUME is drawn from, not the whole assumption side: an INITIALLY entry is an initial condition and a REQUIRE entry is lowered under an implicit `G`, so copying either into ASSUME changes what it says rather than duplicating it. Tombstones are skipped, and with nothing live to copy the template stands in rather than the operator becoming a no-op. The template keeps the majority of the draw because it is the only form that can introduce a fairness property no existing assumption carries — the repair `p_add_assumption` was added for.

Like `p_remove_guarantee` and `p_monotone`, the probability is read before the `RandomSource` is touched, so at 0 the clone costs no draw and the breeding stream is what it was before the arm existed; the key is in the "Config vintage" note in `experiments/README.md` for the same reason.

## Assumption construction

## Termination modes

Three keys let counter and AuRUS be given the same search budget: `[genetic] termination` (`"generations"`, the default, or `"individuals"`), `max_individuals` (0) and `max_wall_s` (0). All three are no-ops at those values. Counter's budget is a count of `generations` rounds and AuRUS's is a count of individuals, so the two were never measured against a common currency. AuRUS's `GeneticAlgorithm.java` stops once `numberOfVisitedIndividuals` reaches `GA_MAX_NUM_INDIVIDUALS` — 1000 in the drivers behind its published numbers — incrementing once per new mutant and once per crossover offspring, and `checkTermination()` runs after every offspring, so it terminates mid-generation and `-Gen=1000 -Pop=100` never runs to completion. The `2026-08-14-aurus-h2h` campaign gave counter 10 generations at population 200 against that, roughly twice the individuals.

It is 1000 *bred individuals*, never 1000 solutions, and the distinction is worth holding because the second reading is the intuitive one and it is wrong. Both increment sites sit inside the breeding loops, before the population is scored, so nothing about realizability has been decided when the counter moves; all 679 archived h2h logs carrying a settings banner read `GA_MAX_NUM_INDIVIDUALS=1000, GA_POPULATION_SIZE=100, GA_EXECUTION_TIMEOUT=7200`; over the 600 archived runs printing a final count, solutions per run read median 486 and maximum 741 with **zero** reaching 1000; and Brizzio et al., GECCO '23 sec. 6 says "the termination criterion is reached either when 1000 individuals are generated or after 2hrs of execution time". The paper is silent on *how* an individual is counted, saying nothing about the per-mutant and per-offspring sites or the exclusion of an offspring equal to its parent, so `SearchBudget` matches the code and not the published text — a code-level match, and it should be described as one. AuRUS's own 7200 s deadline never fires: its `GENETIC ALGORITHM TIMEOUT REACHED` line appears in 0 of 780 logs, because `checkTermination()` cannot interrupt the `parallelStream()` scoring of a whole population, so a run stuck there overruns and dies at the harness's external kill instead. The paper reports 7400 s for five cases against its own 7200 s cap, which is the same overrun.

`scripts/gen_configs.py` emits the mode under `--termination` and `--max-individuals`, following the `--max-wall-s` sentinel pattern: `termination` reaches the TOML only when it differs from `"generations"` and `max_individuals` only when positive, so every existing grid stays byte-identical, and `parse_args` rejects the mode without a cap because `config_io.cpp` does. Both keys are in `GEN_CONFIGS_FIELDS` in `scripts/check_config_schema.py`, which is a fifth site the four in "Config keys" do not cover — a `DEFAULTS` entry in neither that table nor `GEN_CONFIGS_EXEMPT` fails `lint`. Matching the cap alone is not matching the budget: 1000 individuals at population 200 is half the generations of 1000 at population 100, so `--population-size 100` travels with it. The `matched` profile in `run_experiments.py` is the campaign that does this; `generations` must stay far above what the cap needs (counter breeds `population_size - elite_n` offspring a generation and counts only those differing from their parent, so 1000 individuals needs at least 12 generations at population 100), and `stopped_by` reading `generations` on any row of such a campaign means it measured a different budget.

An offspring counts only where it differs from the parent it was bred from, matching AuRUS's `!chromosome.equals(mutated)` on the mutation arm and its distinct-from-first-parent filter on the crossover arm. The budget is checked inside `breed_offspring` (`include/genetic/pipeline.hpp`) between slots, and again at the head of each driver's generation loop. Checking at the generation boundary alone would overshoot by up to one generation's offspring, 20% of a 1000-individual cap at population 200. Breeding then returns a short offspring set and the rest of the generation completes normally, as AuRUS's does after it breaks out of its loops.

The mechanism is a `SearchBudget` (`include/genetic/pipeline.hpp`), owned by the driver and passed by reference through `run_evolution` (FRETISH) and `tlsf::run_repair` → `run_monolithic`/`run_muc` → `evolve_population` (TLSF). It has to be the run's rather than the generation's, and above all not the core's: `run_muc` restarts its generation count per core (`gen_offset += cfg.generations`), so a per-core budget would silently multiply the cap by `muc_max_iterations`.

`max_wall_s` is independent of the mode and honoured under both. A run killed by the harness's external `timeout` writes no `run.json` and is censored with no data at all, where a run that stops on its own deadline writes its repairs and its manifest — which is what a survival analysis such as time-to-first-repair needs. It is measured from the same origin as the manifest's `wall_s`. Nothing interrupts filters, scoring or the final gate, so a run overruns by whatever the generation it was in had left: a smoke run with `max_wall_s = 1` finished at `wall_s = 3.96`. At campaign scale that overrun is the larger half of the bill, not a rounding error. `2026-08-28-selection-grading` ran 600 TLSF runs at a 400 s deadline with `run_implication = true` and cost 335 compute-hours against the 67 the cap predicts — a factor of **2.2**, the final realizability gate and the implication filter over the accumulated set being what the deadline does not bound. 245 of those runs were then killed by the harness's own 3600 s `timeout_caps` and lost their manifests. Size a deadlined campaign at roughly 2.2x the cap, set `timeout_caps` well clear of that, and read the real figure off the first ~40 rows rather than the plan — `campaign.py`'s ETA is unreliable below about 30. What survives a harness kill is `accumulated/index.tsv`, which is appended and closed per repair: 244 of those 245 runs still show their last accumulation at the deadline, so the discovery curves came through intact and only the manifest and the gate-filtered `repair_N.json` set were lost.

Manifest schema version 21 adds `stopped_by` (`generations`/`individuals`/`deadline`), `generations_run` and `individuals_bred`. The last is null rather than zero when the budget is inactive, since counting an offspring costs a comparison against its parent that an unbudgeted run does not pay, and a zero would read as a fact rather than an absence. Individuals is reported ahead of a deadline where both trip, matching the order `checkTermination()` tests them in. `SearchBudget::active()` is false at the defaults and breeding reads it once before the slot loop, so neither the parent comparison nor the `steady_clock` read happens and the `RandomSource` draw stream is byte-identical to what it was before the keys existed — the `p_remove_guarantee` and `p_monotone` discipline. The determinism goldens did not move, and no entry is owed in the "Config vintage" note in `experiments/README.md`, the defaults having stayed where they were.

The trap is that `max_wall_s` makes output depend on the machine, so a seeded run stops reproducing across hosts under it, the same property the `[runtime]` per-tool budgets already carry. Do not set it in a campaign that pins seeds for a paired comparison unless the pairing is on the arm rather than the seed.

## Timing donation

The two extremes of the FRETISH timing order move only into a timing the specification donates, never one conjured from nothing. `collect_timing_pool` gathers the distinct timings across both requirement lists, skipping tombstones, and `donated_candidates` (`src/genetic/mutation.cpp`) turns that pool into the set both extremes draw from: each quantified donor lends its tick count alone, spent as `for n ticks`, and a donated Immediately or NextTimepoint lends itself. With no usable donor the extreme is returned unchanged, so a specification with no interior timing anywhere cannot acquire one.

It is one set because Always and Eventually sit at opposite ends and everything in it lies strictly between them, so the same candidates strengthen the one and weaken the other — `move_off_extreme` is the shared step. A donor's *kind* is never taken, only its count: `within n` would be a second spelling of one count, and `after n` is not comparable to Always at all, forbidding the response at the ticks Always demands it.

Eventually gained this on `fa07f89`; Always followed. Always had been a fixed point in both directions since `f4968ab` (2026-07-08), which froze it after its weakening — a hard-coded `for 10 ticks` — produced a degenerate `fsm` repair. The invented constant was the objection, and the pool is what answers it. The freeze cost more than it looks: `mutate_specification` weakens guarantees and strengthens assumptions, Always is the top of the order, so an Always guarantee's timing field never moved at all, and 7 of the 9 guarantees across the three FRETISH input specs carry Always. Crossover was no escape either, `crossover_timing` picking between the two parents' timings, so on `fsm` — every guarantee at Always — no other timing existed in the population to pick.

The risk to watch is the one `p_remove_guarantee` carries: weakening a guarantee's timing is monotonically good for realizability and pays nothing on the similarity objectives, so under NSGA-II a gutted timing sits on the front. That wants a campaign rather than an argument.

The determinism goldens did not move. No golden specification carries an Always guarantee, and guarantees only ever weaken, so the new draw never fires there; `move_off_extreme` also reads the pool before touching the `RandomSource`, so an empty pool costs no draw either.

## Removable guarantees

`p_remove_guarantee` deletes one guarantee, the mirror of `p_add_assumption` appending an assumption. Both paths have it: a FRETISH guarantee requirement, or a TLSF guarantee-side conjunct drawn from PRESET, ASSERT and GUARANTEE together. It exists because some repairs are reachable no other way — every `drop-*` ideal in `examples/` deletes a guarantee, and for amba, full-arbiter, load-balancer, prioritized-arbiter and round-robin-arbiter that is the only ideal there is, so PR #114's `lint-ideals` reported their `implies_ideal` as zero by construction. That PR's `reachable` check asserted the opposite bound and was inverted here: a guarantee side may now shrink, never grow, down to a floor of one.

A deleted guarantee is **tombstoned in place, never erased**: `Requirement::m_removed` on the FRETISH path, `tlsf::SectionEntry::m_removed` on the TLSF one. Erasing it would shift every later requirement, and the whole codebase pairs specifications by position — `average_timing_similarity` and both semantic-similarity folds zip by index, and both crossovers write a merge back into the slot it came from. A candidate that erased guarantee 0 of 3 would have its remaining two scored against the original's guarantees 1 and 2. Keeping the slot makes deletion a mutation of an existing position, which is the shape every comparison already assumes.

The flag is part of `operator<`, `operator==` and `hash` on both paths, because the fitness cache keys on the whole specification: a deleted guarantee must not hash equal to the live one it replaced and inherit its score. Everything that reads a requirement list skips tombstones — lowering to LTL, the status components and the MRS walk's index map, vacuity, well-separation, the bloat cap, `all_implied_by_some`, the timing pool, the mutation and simplification pools, MUC extraction and the guarantee-part split. Crossover draws neither its target slot nor its donor from a tombstone, so it can neither resurrect a deleted guarantee nor delete a live one; removal is mutation's move alone. `tlsf::SectionEntry` converts implicitly *from* `Formula` and deliberately not back, so a new read site fails to compile rather than silently ignoring the flag.

JSON and TLSF text are the boundary where a specification stops being search state and becomes a document, and a deleted guarantee's meaning there is absence: `to_json` and `tlsf::write` omit tombstones entirely rather than marking them, so `parse(write(spec))` returns the specification without them and no reader that has never heard of the flag can misread a repair.

It defaults to **0.05**, matching `p_add_assumption`: the two are the same move in opposite directions. The probability is tested before the RNG is drawn, so at exactly 0 the operator costs no draw and the breeding stream is byte-identical to what it was before it existed — which is what reproducing a pre-2026-08-13 campaign needs, and the reason this key is in the "Config vintage" note in `experiments/README.md` rather than exempt from it. Archived configs cannot state a key their binary never had, so every one of them now means something it did not: write `p_remove_guarantee = 0.0` in by hand. The determinism goldens were re-pinned in the same commit (115 draws to 96, since a firing removal returns before the rewrite draws); `golden_config()` pins the key explicitly so a later default change fails that suite rather than silently re-recording it.

The risk to watch is that deletion is monotonically good for realizability: the status objective pays for it while the similarity objectives do not, so under NSGA-II a gutted candidate is non-dominated and sits on the front. TLSF sweep D exists to measure whether that costs repair quality, with `prem0` as the pre-operator control.

## FRETISH scopes

`Requirement::m_scope` (`include/requirement.hpp`) is FRET's fifth field, the interval over which the requirement is enforced relative to when a *mode* holds. `ScopeKind` has eight values — Global (the default, and what an omitted FRET scope means), In, NotIn, Before, After, OnlyIn, OnlyBefore and OnlyAfter. FRET's own scope object is `{type, exclusive, required}` and its parser never sets `required`, so eight is the complete set reachable from FRETISH text rather than a chosen subset of a larger one.

The spellings are `in m` (synonyms `during`, `while`), `except in m` (synonyms `unless in`, `when not in`), `before m`, `after m`, `only in m`, `only before m` and `only after m`. A bare `not in` is a parse error, which is why the internal name `NotIn` and the emitted text differ. The mode is a bare identifier, and `in (a & b)` is a parse error, so a scope names an atom rather than a formula.

The lowering is in `src/requirement.cpp`. With `SoM = (!m & Xm)`, the point *before* mode entry, and `EoM = (m & X!m)`, the last point in mode, each scope contributes a boundary marker that discharges a bounded obligation early, plus an outer wrapper. In and OnlyAfter take `EoM`; NotIn, Before and OnlyIn take `SoM`; Global, After and OnlyBefore take none. Under a boundary `B` the relaxations are `G r` to `B R r`, `F r` to `!B U r`, `X r` to `B | X r`, `F[0,n] r` to `F[0,n] r | F[0,n-1] B`, and `G[0,n] r` to `G[0,n] r | (B R r)`. The continual wrapper `G(c -> body)` becomes `B R (c -> body)`, and the trigger wrapper takes the same treatment with `!B` conjoined into its rising edge, an edge at the boundary belonging to the next interval. The three `only` scopes apply the dual scope's wrapper to the De Morgan dual of the body, so OnlyIn reuses NotIn's wrapper exactly.

**The Global path is byte-identical to the pre-scope lowering.** That is deliberate and load-bearing. Every archived run, every memoisation key and the determinism goldens were recorded against those exact strings, so a change in the Global path invalidates all three at once. `test_global_scope_lowering_is_unchanged` in `test/scope_tests.cpp` pins them, and `build/ltl` output over all 23 FRETISH files under `examples/` was diffed against the pre-change binary and is identical.

**Validation is against the vendored formaliser, on equivalence rather than on string equality.** `test_scope_agrees_with_formaliser` crosses 8 scopes x 2 condition types x 7 timings and checks each row with `ltl_equivalent`. The strings do not match because FRET special-cases rows. `in m ... always` prints as `G(m -> r)`, where the general form expands far larger. During development the model was checked over 312 rows, adding a no-condition arm and tick counts 0, 1 and 2; 291 agreed and the other 21 were rows where FRET's own output contains a degenerate `F[0,-1] ...` that SPOT refuses to parse, with zero semantic disagreements. That degenerate case is the zero-tick `within` under a bounded scope, where the boundary disjunct spans an empty interval and the obligation is not relaxed at all. `test_scope_zero_ticks_is_unrelaxed` pins it by hand and the fuzzer skips it, the CLI's answer there being unusable rather than merely different.

**Modes are their own namespace.** `Specification::m_modes` is disjoint from `m_in_atoms` and `m_out_atoms`, checked at load, and joins ltlsynt's *input* side through `environment_signals()`, which every partition query now goes through. A mode on the output side would let the synthesised system pick its own scope. An `In`-scoped guarantee is implied by `G !mode` and a `Before`-scoped one is discharged by holding the mode at t=0, so every scope would carry a free gutting move. An undeclared mode is rejected rather than defaulted, ltlsynt being passed only `--ins` and treating every unmentioned atom as an output, so an undeclared mode lands silently on exactly the wrong side.

**A mode is an atom of the lowered formula that sits in no `Formula` field, and the counting path had to be told.** `count_joint_atoms` (`src/fitness/transfer_matrix.cpp`) built its universe from the two requirements' conditions and responses alone, so a scoped requirement's mode was missing from `n_total_atoms` while still reaching the automaton's atomic propositions. `count_guard_models` then computed `free_count = n_total_atoms - n_mentioned` on `std::size_t`, which wrapped, and `mul_pow2` looped on a 64-bit exponent until the overflow assertion fired. It is asserted there now rather than clamped, a wrong free count being a wrong trace count that nothing else would catch. Any future field carrying an atom outside `m_condition`/`m_response` lands in the same place.

**No mode axiom is generated.** FRET carries mode exclusivity in its variable definitions, as an `idType == "Mode"` with a `modeRequirement` assignment, and the `formalize` path never sees them. Exclusivity is written by hand as an ordinary non-weakenable requirement, which `examples/fsm-combined/spec.json` already does for its enum atoms.

**Two directional mutation arms, both defaulting to 0.15.** `[mutation] p_condition_type` and `[mutation] p_scope`, at `p_timing`'s rate. Both defaulted to 0 until 2026-09-11 and moved without any campaign having measured either. Each reads its probability before touching the `RandomSource`, so at 0 neither costs a draw and the breeding stream is byte-identical — the `p_remove_guarantee` discipline. `golden_config()` pins both keys at 0, so neither the arms nor the default move shifted the determinism goldens. `test_new_arms_cost_no_draw_at_zero` checks each arm actually draws when turned on, since a guard written this way passes just as happily when the arm is dead. Manifest `k_schema_version` went 21 to 22 for the two keys. The default move is in the "Config vintage" note in `experiments/README.md`.

**Condition type carries a universal order.** Continual implies Trigger for every scope and every timing, because a trigger fires on the rising edges of its condition, which are a subset of the timepoints where it holds. So Continual strengthens and Trigger weakens, and the arm needs no table. The two coincide in 10 of the 80 scope-by-timing cells: at `always` under the five plain scopes, and at `eventually` under the three `only` scopes, whose lowering applies the dual wrapper to the negated body and so moves the coinciding cell to the dual timing. This was checked against the vendored formaliser with `ltlfilt --imply` at tick counts 1 and 2, and `test_condition_type_order_is_pinned` asserts both the order and exactly those coincidences.

**The scope order is thin and depends on the timing.** It was measured with `ltlfilt --implied-by`, and tick counts 2 and 4 give identical orders, so it is independent of n. Continual at any timing but `eventually` gives `global => in`, `global => notin`, `global => before`, `global => after` and `notin => before`, and trigger at `always` gives the same. Trigger at any other timing but `eventually` keeps only `global => before` and `notin => before`. At `eventually`, continual gives `global => after` and `notin => before`, and trigger gives `notin => before` alone. The order is not uniform because a boundary *relaxes* a bounded obligation and *tightens* an unbounded one. `in m ... eventually r` demands the response arrive before the mode ends, which global scope does not. `notin => before` is the one edge holding in every cell, the interval strictly before the first mode entry being contained in the set of points where the mode does not hold. The three `only` scopes are an antichain in every cell, so a requirement carrying one cannot move on this field at all. `test_scope_order_is_pinned` re-derives every cell and checks the non-edges too, a missing edge costing reach and a false one being unsound.

**A mode travels with a non-Global move.** `notin m` implies `before m` and implies nothing about `before m'`, so only a move off Global draws from the mode pool, which is `Specification::m_modes`.

**Syntactic similarity averages five terms.** They are the condition, response, timing, scope and condition-type terms, in both the per-requirement and the specification-level overload (`src/fitness/syntactic_similarity.cpp`). The last three pair by index, through `average_timing_similarity`, `average_scope_similarity` and `average_condition_type_similarity`, because slot *i* of a candidate descends from slot *i* of the original, which is the only pairing that compares a requirement with what it came from. Timing, scope and condition type are each a *Jaccard* overlap of downward closures in the field's implication order, so none of the three carries a chosen penalty. Condition type takes the two-element order above, Continual implying Trigger, so its values are fixed at 1 and 1/2 with nothing to tune. The term scores the fields and not their lowerings, so the cells where the two coincide still score 1/2.

**The scope term is the exception and does not use that order.** The scope order is timing-dependent, a boundary relaxing a bounded obligation and tightening an unbounded one, where a similarity between two scopes has to be a property of the scopes alone. Relative to one mode a trace divides into four regions: the prefix before the mode first holds, the points where it holds, the gaps between mode intervals, and the suffix after it last holds. Every scope is a union of them, and the term is the Jaccard overlap of the two region sets, averaged with whether the two scopes name the same mode. The mode is an opaque atom, so it is compared for equality rather than for structure. Polarity is folded into that Jaccard rather than averaged as a third term. An `only` scope's regions are tagged apart from a plain scope's, so `except in m` and `only in m` share every region and still earn no region credit; they make opposite claims about the same timepoints, and untagged they would score as the most similar distinct pair of scopes there is.

**The invariance argument this section used to carry is wrong.** It recorded the scope term as a constant 1.0 across an all-Global corpus, making the mean a positive affine transform of the old three-term one and leaving both NSGA-II schemes untouched. Each per-index term divides by the *larger* of the two requirement counts. A candidate that gained an assumption (`p_add_assumption`, 0.05) or tombstoned a guarantee (`p_remove_guarantee`, 0.05) therefore scores below 1 on the new terms even where every matched pair agrees. The terms are constant per matched pair rather than in aggregate, and the invariance holds only where the two specifications have the same shape — the case those two structural operators break.

**The change was measured rather than argued.** Seeded runs over `fsm`, `fsm-timing` and `fsm-combined` at five seeds each, 3 generations at population 40, were compared against the same tree with the three-term mean restored from commit `9133035`. 12 of the 15 runs returned different repairs. Two returned one repair more (`fsm-combined` seed 3 from 0 to 1, `fsm-timing` seed 2 from 6 to 7) and none returned fewer. 15 runs at that search size is far too small to read as a quality result; the finding is that the search moves, not that it improved. The mechanism is worth recording. On an unscoped corpus with unchanged condition types, both new terms reduce to the matched-slots-over-total shape signal the timing term's denominator already carries, so adding them weights that signal more heavily against the two formula terms. Roughly ten tests that pinned the old means were re-pinned, which is arithmetic.

**The scope arm is dead on most of the corpus.** Every pre-existing specification under `examples/` is global-scoped and declares no modes, so the pool is empty and Global is the only scope reachable. `examples/mode-arbiter` is the one scoped subject, added with this work: unrealizable, with one ideal (`fixes/guard-maintenance.json`) that passes every `lint-ideals` check. `p_condition_type` has no such limit and acts on every FRETISH specification, so its 2026-09-11 move reaches the whole FRETISH corpus where `p_scope`'s reaches one subject. Both moved without the campaign this section said was owed, and one scoped subject is still thin ground to run it on.

## Profiling

`COUNTER_PROFILE=<path>` turns on the *scope profiler* (`include/profile.hpp`), which writes a table to stderr and JSON to that path; `COUNTER_PROFILE=1` gives the table alone. Every binary reports. The report registers with `atexit` on the first scope opened, so `realize`, `mucs`, `compare` and `maximal` need no wiring of their own — and a binary that opens no scope prints nothing at all. Both `counter` drivers additionally call `profile::report_if_enabled()` explicitly, so the profile lands before the manifest write and the closing `Done in` rather than after them; the call is idempotent, so the `atexit` registration remains the mechanism.

Read wall time against per-thread CPU time. A site with large wall and near-zero CPU is blocked on a child process, not computing: `proc/read` sits at a cpu/wall ratio of about 0.01 on a real run. That ratio is the diagnostic.

It is in-process instrumentation rather than `perf` or `gdb` because neither is available on the dev box — `kernel.perf_event_paranoid=4` and yama `ptrace_scope` rule out both. `strace` works only by launching the process, never by attaching. The counter registry is deliberately leaked so that it outlives the `atexit` report; destroying it first would free the names the report is about to print.

## Run output

stdout is for watching a run in progress: the per-generation status line, the filter report, the scoring report, and the closing `Done in`, which is printed last on both paths. Engine-internal counters (per-tool calls, tautology substitutions, constant-folded, fitness cache) print only under `--diagnostics`; every figure in them, plus `wall_s`, the effective config and the commit, is in `<output-dir>/run.json` on every run that completes, which is what a campaign should read. Adding a counter to `print_diagnostics_report` means adding it to `write_run_manifest` too and bumping `k_schema_version`, or the flag's default silently loses it — that is why the manifest is at version 28. A new config key falls under the same rule and must join `config_json` in `src/repair/manifest.cpp` as well as `config_key_spec()`, the schema and `example-config.toml`. Two `[tlsf.mutation]` keys (`p_monotone` and `p_clone_assumption`) reached no `run.json` at all until that was fixed; `scripts/check_config_schema.py` is the check that catches it, parsing `config_json()` out of `src/repair/manifest.cpp` and requiring its key set to equal `config_key_spec()`'s in both directions, so a manifest field with no key behind it fails too, and it reports 50 keys agreeing across `config_io.cpp`, `manifest.cpp`, `config-schema.json` and `example-config.toml` under the `lint` target. The scoring report is the one block that must keep printing unconditionally: `run_experiments.py` parses `"N individual(s) dropped"` out of the log.

Anything that moves the cursor must go through `stdout_is_tty()` (`include/status_line.hpp`). `run_experiments.py` redirects every run to `<output-dir>/run.log`, so a redirected run is the common case, and an unguarded `\r`/`\033[J` keeps every frame it ever drew: one unguarded status line was 59KB of escape codes for 1.2KB of content. `StatusLine` columns may be declared *transient*, meaning live-only and dropped from the committed line — the within-generation percentage is the motivating case, since it reads 100% on every committed line by construction.

Report "best fitness" as the population maximum, never `population[0]`/`front()`. Under either NSGA-II scheme the population is ordered by front rank and crowding distance, so the leading individual need not hold the highest weighted scalar; reporting it makes the printed best *fall* between generations while the search is still improving. Both drivers got this wrong independently (`src/repair/evolution.cpp`, `src/tlsf/evolve.cpp`), each while a correct maximum sat a few lines below feeding the dashboard.

`counter` rejects unknown arguments rather than ignoring them (`find_unknown_arg`). Adding a flag means adding it to the table in `src/main.cpp` too, or the binary refuses to start with it.

## Live dashboard

Opt-in, via `counter --dashboard` or `[runtime] dashboard = true` (the flag can only enable). Off by default so a campaign of many runs does not pay for the file and its flushes with nobody watching. When on, both drivers stream progress to `<output-dir>/progress.jsonl` (one JSON object per line, flushed as written) and copy `web/dashboard.html` there as `index.html`. To watch a run: `python3 -m http.server -d <output-dir> 8000`. The page polls once a second; `?poll=<seconds>` overrides that (`?poll=0` loads once and stops polling).

Each `stage` record carries `distinct` beside `n_in`/`n_out`: how many of the survivors are distinct specifications. The population is largely repeats, which no size can show, so this is the field that measures whether a selection scheme actually keeps diversity. Computing it hashes the whole population, so `run_generation_pipeline` only does so when an observer is attached — a run without the dashboard pays nothing.

The page's script keeps everything above its `boot()` call free of DOM access at load time: `boot()` runs only when `document` exists, and otherwise the script exports its functions for `test/web/` to test under node. Adding a top-level `document.getElementById` (rather than one inside a function) breaks that and takes the JS tests with it.

The page derives its stage list from the `stage` records of the latest generation, so a new filter or pipeline stage shows up with no change to either side. Generation stages come from `make_generation_pipeline` (`include/genetic/pipeline.hpp`), which returns an ordered vector of named `PipelineStage`s; `run_generation_pipeline` reports each to an optional `StageObserver`. Breeding must stay a single stage — crossover and mutation interleave per offspring slot, so splitting them reorders every RNG draw after the first and breaks seed reproducibility. The `determinism` test suite pins the draw stream against exactly that.

Two calls that both draw from the `RandomSource` must never be arguments of the same call: argument evaluation order is unspecified, and gcc and clang pick opposite orders, so a seed stops reproducing across compilers. Sequence each draw into its own local (as `rewrite_post_order` does). The CI matrix's gcc job is what catches this, since the goldens are pinned under clang.

## TLSF repair modes

Binaries: `counter` (genetic repair), `realize`, `compare`, `ltl`, `mucs`, `maximal` — run each with `--help` for flags.

`mucs` extracts a minimal unrealizable core. Prints the smallest subset of the guarantee-side sections (PRESET, ASSERT, GUARANTEE) that stays unrealizable against the full, unchanged environment side (INITIALLY, REQUIRE, ASSUME) — the culprit formulae behind unrealizability. Uses QuickXplain over `ltlsynt`. Prints `REALIZABLE (no core)` if the input is already realizable. TLSF-only (FRETISH JSON is not supported).

The same core extraction drives an alternative TLSF **repair mode**. `Config::repair_mode` (TOML `[tlsf] repair_mode = "monolithic" | "muc"`, default `monolithic`) selects between evolving the whole spec at once and the MUC-guided loop in `run_muc` (`src/tlsf/pipeline.cpp`): extract a core, evolve only that sub-spec, reintegrate the repaired core with the untouched non-core guarantees (`tlsf::reintegrate`), and repeat until the whole spec is realizable or `muc_max_iterations` trips. FRETISH ignores it. `scripts/gen_configs.py --repair both` and the `muc` profile in `run_experiments.py` cross the two modes as an experiment factor over the TLSF spec corpus.

## Cache keys

Every memoisation cache between the search and the external tools is keyed on a rendered formula string, and `Formula` is a binary tree with no canonical shape, so one formula reached a cache under many spellings and each spelling bought its own subprocess. `formula_key.hpp` is the fix: `canonical()` renders `Formula::canonical()` (commutative operators flattened, their operands ordered and deduplicated, double negation dropped) and `renamed()` additionally renames the atoms to a canonical sequence. Each memoises on its raw input and hands out a reference into an append-only store, so a spelling already seen costs a hash rather than a parse.

**Which key a cache may take is decided by what it stores, and getting this wrong is silent.** A cache holding a verdict or a count takes `renamed()`, those being invariant under a bijection on the atoms — the satisfiability cache, `cached_count_traces` and `run_ganak_on_formula`. A cache holding a formula or an automaton takes `canonical()`, which preserves atom names: reading a renamed value back would mean renaming atoms inside a tool's own output, and SPOT prints a unary operator hard against its operand, so `F` applied to an atom named `fk1` comes back as `Ffk1` and no tokenisation separates the two. That was measured, not guessed — a rename-back over `ltlfilt --simplify` output silently turned an atom into `Ffk1` and broke `normalize_ltl`'s idempotence. `run_ltl2tgba_for_counting`, `simplify_ltl` and `rewrite_weak_operators` therefore take `canonical()`. `RealizabilityChecker` takes `formula_key::realizability()`, a partition-preserving renaming plus the count of declared signals the formula never mentions, those being interchangeable among themselves but part of the alphabet ltlsynt plays over.

The satisfiability cache keeps **two** keys into one map, tagged apart. `ltlfilt --simplify`'s own collapse is the larger of the two and neither contains the other: ltlfilt simplifies, which the canonical form deliberately does not, and the canonical form renames, which ltlfilt does not. Replacing the `normalised` key with the canonical one rather than adding to it was measured on `rg2` at 2,773 execs against 2,211 — a regression, and the reason the raw-formula key is consulted first (it also skips the ltlfilt exec that computing the second key costs) and `normalised` second.

The parser had to grow the temporal operators for any of this: `node_to_string` had emitted `G(...)`, `(a) U (b)` and the rest since the temporal kinds landed, and nothing could read them back, so a key built from a rendered formula was a string this process could not reparse. An operator spelled as a letter is only an operator when the next character cannot continue an identifier, or `Grant` lexes as `G` applied to `rant`. `Formula::try_parse` is the entry point for a string from outside: the constructor asserts, the asserts are gone under `NDEBUG`, and the walk then ran past the end of the text — `G(` threw out of `std::string::compare`.

Measured over six specifications with the search held fixed, the keys and the subsumption table together remove about 15% of `simplify_ltl`'s execs, 26% of `ltlsynt`'s, 9% of `cached_count_traces`'s, 7% of `ltl2tgba`'s and 6% of the satisfiability cache's, which weights to roughly 13% of external-tool time. The ceiling measured offline was 22%; the gap is `simplify_ltl` being unable to take the renaming, and the canonical form not doing what SPOT's simplifier does. Exec counts vary a percent or two between runs of one seed — two scoring threads that miss on the same key both compute it, by design — so read these as approximate. The repairs do not vary.

`run_ganak_on_formula`'s own cache joined that list on 2026-09-11. It was keyed on `normalize_ltl`'s output, so two HOA guards differing only in atom naming bought an exec each, and the renaming is sound there for the reason the paragraph above gives: the value is a number, and the free variables of the wider alphabet are multiplied back in by `count_guard_models` outside the cache. Over nine specifications it removes 20.3% to 49.5% of the ganak execs a run makes, 5,651 to 3,875 pooled. Median wall time over seven paired families falls 5.2%, and the repairs are byte-identical on all seven.

`count_guard_models` then stopped calling ganak at all. A HOA guard is a propositional formula over the atoms one transition mentions, and over the 2,932 distinct guards those nine specifications produce the widest mentions 12 atoms, so the truth table is enumerable in process. `count_models_exhaustively` (`src/fitness/exhaustive_count.hpp`, internal) builds one bit column per atom over the 2^n assignments, evaluates the tree bitwise bottom-up and popcounts the root, which is position-independent at every step, so the one mask for a sub-word table applies at the root alone. It declines a temporal formula, an unparsable one and anything above `k_exhaustive_count_max_atoms` (16), leaving ganak behind it as the fallback for a guard no measured specification produces. Ganak execs go to zero on all nine families, and median wall time falls 3.6% to 88.7% over seven paired families, 50.1% pooled. `humanoid-531` is the 88.7%, being the family where ganak was 54.5s of a 29s wall.

Both figures are paired medians over three repetitions with the two binaries interleaved per family, and the pairing is what makes them readable. Measured the obvious way (one arm's nine families, then the other's) the in-process count read *slower* on seven of nine, by up to 87.2%, on a shared 20-core box whose load average drifted between 12 and 18 across the two arms. A repeat of one arm against itself then moved 25.2% on `fsm`. Interleave the arms and read a median before concluding anything about wall time here.

The `normalize_ltl` call under that cache went the same day. It ran `ltlfilt --simplify` over the guard and handed the output to ganak, and that pass eliminates a variable wherever one term subsumes another: SPOT 2.15.1 returns `a` for `a | (a & b)`. `count_guard_models` multiplies the count by two per variable of the wider alphabet and takes that exponent from the HOA label, computed before the pass, so a dropped variable undercounted the guard by 2^(dropped) and nothing would have caught it. The shape never arrived. SPOT prints a label off a reduced BDD as an irredundant cover, so a subsumed term cannot appear in one, and 0 of 27 distinct guards sampled from five formulae lose a variable under the pass. `formula_key::canonical` replaces it, flattening, ordering and deduplicating the operands of a commutative chain and dropping double negation, none of which removes an atom, and it costs no subprocess where the pass cost one exec per distinct spelling. The cache key moved with it, from the simplifier's output to the raw formula, so it gives up whatever ltlfilt collapsed beyond the canonical form. No measured specification exercises that, `count_models_exhaustively` having taken every guard the nine produce in process. `test_ganak_counts_over_every_mentioned_variable` pins the count at 2 for the subject above. That was `normalize_ltl`'s last caller, so the wrapper and its tests went with it; `simplify_ltl` is the one entry point to the pass now, and a caller wanting a constant result folded away has to do it itself.

`RealizabilityChecker` also carries a **subsumption table**. Realizability is monotone in both sides, so a realizable specification stays realizable when a guarantee is dropped or an assumption added, and an unrealizable one stays unrealizable in the other direction; a query standing in the right relation to one already decided is answered by comparison rather than by exec. Conjuncts are interned to integer ids and each side carries a 64-bit signature, so most entries are rejected by one AND rather than by a set walk. Only decided entries subsume — an undecided one is memoised but carries no direction. Comparison is scoped: two queries over different atom partitions, or different TLSF semantics, are over different formula shapes and never meet. Measured over six specifications it removes 26.2% of ltlsynt execs, 13.6 to 36.4% per specification.

**Both front ends pass sides, and the TLSF side is the one that needed proving.** Supplying sides is sound wherever every conjunct sits at a determinate polarity in the lowered formula. FRETISH is the easy case, being the two conjunctions joined by an implication over each requirement's own `m_ltl`. TLSF wraps whole sections rather than conjuncts — `G psi_e` is one `G` over the conjunction of every REQUIRE entry — and it still holds: over `theta_e -> (theta_s & [strict: psi_s W !psi_e] & ((G psi_e & phi_e) -> ([!strict: G psi_s] & phi_s)))` the three environment sections (INITIALLY, REQUIRE, ASSUME) are all negative and the three system ones (PRESET, ASSERT, GUARANTEE) all positive. REQUIRE is the one that looks like a counterexample and is not: it occurs twice, in `G psi_e` under the inner antecedent and in `!psi_e` under the strict weak-until, and the negation flips the second back, so both occurrences are negative and strengthening it weakens the formula either way. Every empty-section case agrees, introducing a section introducing the term it governs in the same direction. `tlsf::specification_sides` builds them, tagging each conjunct with its section — one formula means different things in PRESET and in GUARANTEE — and putting the semantics in the scope. The well-separation queries build `(A) -> (false)` rather than `to_ltl()` and pass no sides; sides are valid only for a query over the lowering itself.

This is the second time a "REQUIRE occurs on both sides" argument has come up here, and the first reading of it was wrong — the two occurrences point the same way. Check the polarity through the negation before concluding a section is non-monotone; `test_tlsf_subsumption_agrees_with_ltlsynt` in `test/tlsf/filter_tests.cpp` crosses both semantics against `ltlsynt` for exactly that reason, a wrong verdict here being silent.

Reporting: `run.json` carries a `caches` block with the hits and misses of every memo, at schema 20. Before it, three hit rates were unreadable. The fitness cache's counters were `inline static` members of a class template, so each instantiation carried its own and the manifest read the FRETISH one — every archived TLSF campaign records `{hits: 0, misses: 0}` for the top-level cache on the path counter is now benchmarked against. `SatisfiabilityChecker::n_cache_misses` reached no field at all, the black row reporting black's own exec count (deliberately, since SPOT takes the first stage), leaving the largest cache in a run at 237,969 lookups with no visible rate. And `tool_calls.ltlfilt.calls` counted `simplify_ltl`'s and `rewrite_weak_operators`' misses while `total_s` beside it also covered every `spot_satisfiable` exec, understating the exec count by 35.5% and dividing one tool's seconds by another set's calls; it is now `LtlfiltStats::n_execs()`, the set `total_s` is actually over. `cached_count_traces` sits above both `ltl2tgba`'s cache and ganak's and absorbs the repeats before they arrive, so those two read as the residue of it — 4.8% for `ltl2tgba` against 71.8% for the layer above. Reading either without that in front of it reads a defect that is not there.

## Scoring dispatch

Every parallel region in a run is a `run_bounded_async` call (`include/bounded_async.hpp`) and each one is a full barrier: nothing after it starts until its slowest item finishes. At `generations = 10` a run opens 33 to 35 of them and 98-99% of its wall time sits inside one. Per generation there are the vacuity filter, the score stage, and under `accumulate_repairs` the per-generation gate (a bounded-async region on the TLSF path, a serial sweep on the FRETISH one). That gate ran unconditionally on FRETISH until 2026-09-09, tied to the status line's `real` column; the column is now printed only where the sweep runs, a solver call per candidate per generation being too much to pay for one. Per run there are the initial scoring of the seed population, `conflict_degree_order`'s two passes (only under `mrs_admission_order = degree`, and skipped below 3 parts), the final realizability gate, and the implication filter. Instrumenting each region's wall against the summed duration of its tasks at 20 workers, `generations = 10` and `population_size = 200` over four TLSF families put 5.4% to 13.0% of dispatch wall in idle worker slots, all of it in the small regions. The implication filter has O(n^2) pair items, takes 60-74% of the wall and runs at 99.1-99.4% *occupancy*. The score stages ran at 54-84%, with 27-70% of each region falling after its last launch and up to a third of it spent with 2 parts still running. Campaigns run `parallel = 8` rather than 20, so those idle figures are the pessimistic end.

**Longest-first launch.** `cost_ordered_indices` (`bounded_async.hpp`) builds a launch order by descending cost estimate and breaks ties on the index, so the permutation is a function of the estimates alone, and `run_bounded_async` takes an optional `launch_order` that permutes only which item goes out when. This is sound at every call site because every one of them already collects verdicts by index and rebuilds its output in item order, so the launch order was never observable. It bounds the *makespan* at (4/3 - 1/3m) of optimal for m workers, against an unbounded ratio for an adversarial index order.

**A candidate's score is no longer one task.** `ObjectiveWork` and `FitnessPart` (`include/fitness/function.hpp`) let an objective expose its work as independently schedulable parts carrying a cost hint, and `AggregateWeightedFitnessFunctionT` gained `cached_objectives`, `plan`, `store` and `scalar`. `score_population` (`include/genetic/generation.hpp`) plans the whole population first, which is cache lookups and slot walks with no external tool, then puts every part of every candidate into one region. Syntactic is one part costed as free, being in-process; semantic is one part per changed requirement slot (`semantic_similarity_terms`, and the TLSF twin), each of them three bounded model counts; status is one `black` query per component plus the realizability walk. It was needed because one scoring task was a serial chain of subprocess calls pinned to a single pool worker: a semantic term per slot, a satisfiability call per component, then under the default `status_grading = "mrs"` a greedy walk whose every admission is an `ltlsynt` query deciding the next. No number of workers shortens a serial chain.

One guard is given up deliberately. `specification_status` and `tlsf_status` gained a `ComponentCheck` parameter and the split path passes `Skipped`, so the walk does not re-ask the component queries its own parts already own and the fold applies the component tier instead. That loses the walk's short circuit: a candidate with an unsatisfiable component now pays its synthesis queries rather than being graded before they start. The guard cannot be kept without either duplicating every component query or serialising the walk behind them. Measured, `lily11` -- the family with the highest satisfiability miss rate, 65% -- pays 1.1% to 2.3% more `ltlsynt` misses, and every other family's `ltlsynt` misses fell, by 0.3% to 9.9%.

Planning is serial and runs before any dispatch, which is where the trap sits. Every repeat of a specification in the population misses the fitness cache together, so each repeat would dispatch its own copy of the same queries, and populations reaching the score stage are largely repeats: `stage_pad` cycles survivors back up to the target size and the apportion scheme replicates deliberately. `PlannedCandidate` therefore holds `indices`, a list of every population slot it answers for, and `plan_population` folds repeats onto the first plan of that specification. Without that fold the change is a net regression. With it the behaviour is strictly better than the old code, which let two workers race onto the same specification.

Over 12 paired runs (4 TLSF families x 3 seeds, arms alternating per case) the repair output is byte-identical on 12 of 12. It is faster on 11 of 12, median about -3%, total wall 140.3s to 138.1s (-1.6%), with one +11.1% outlier on `lily11` seed 2. Occupancy over the non-pair regions rose 6 to 8 points: `rg2` 77-80% to 85-87%, `minepump` 81-83% to 88-89%, `lily11` 82-85% to 90-91%. `arbiter-aurus` did not move at all (61-68% to 60-68%), and that is the informative case, its straggler being the MRS walk, the one part that cannot be split because each admission's verdict decides the next. It still gained the `ltlsynt` reduction from repeat-folding, -6.9% to -9.2%.

**There is no config key for any of this**, contrary to the discipline every operator change here follows. Scheduling changes no output, so there is one code path and nothing to gate. The determinism goldens did not move, no part draws from the `RandomSource`, and breeding is untouched. What the change can move is which queries hit their `black` and `ltlsynt` timeouts, a timed-out query resolving as unsatisfiable or unrealizable, which is the same exposure the existing concurrency already carries; the 12 paired runs found no such difference.

The ceiling on all of this is small, because the implication filter dominates every run measured and already runs saturated, leaving the ~34% of wall spent in score stages as the reachable target. `make_predicate_filter`, the final gate and the implication filter can each take a launch order and none of them passes one yet, the vacuity regions being about 5% of wall at 62-80% occupancy. The mechanism is in place and mostly unapplied, so the next person to look at a straggler here has a cheaper move available than restructuring another objective.

## Implication prefilter

The final implication filter is an O(n^2) pairwise sweep, it dominates every run measured, and it already runs saturated ("Scoring dispatch"), so the way to make it cheaper is to ask the solver about fewer pairs. `fingerprint::prefilter` (`src/fingerprint/prefilter.hpp`) is that. If A implies B then B accepts every word A accepts, so one word A accepts and B rejects refutes `A -> B` outright with no solver call. It samples 256 *lasso words* — ultimately periodic words of at most five positions — over the specification's declared signals, evaluates each lowered formula on them in process, and packs the verdicts into a bitset, so `refutes_implication` is two machine words rather than a subprocess. Over the ordered pairs of a 421-candidate `round-robin-arbiter-aurus` set that refuted 95.9% of them and left 4.07% for the solver. That figure is the TLSF path's; the FRETISH one is unmeasured.

Sampling is one-directional and that is what makes it sound. A word can refute an implication and can never confirm one, so a pair no word refutes still goes to the solver and the filter's output is byte-identical to what it was without the prefilter. There is no config key for the same reason the `run_bounded_async` launch order has none: a change that moves cost and no output has one code path.

A refuted pair must be dropped **before** dispatch rather than short-circuited inside its task. `run_bounded_async` bounds the items in flight, so a task that returns immediately still occupies a slot and the sweep would pay the full O(n^2) in scheduling whatever the prefilter settled. `antichain::merge_subsumed` (`src/filter/antichain.hpp`), the one sweep both paths share, therefore erases the doubly-refuted pairs from the `pairs` vector and dispatches what survives. `n_fingerprint_refuted` in the diagnostics counts the ordered directions refuted and reaches `run.json` as `implication.fingerprint_refuted` at schema 26; it is the only reading of whether the prefilter worked on a given run, a refuted pair never reaching `comparisons`.

Both paths sample from one definition, two overloads over one template walk, because two fingerprints test implication against each other only where they were drawn from the same words. The signal set is whatever the specification declares: `m_inputs` then `m_outputs` on the TLSF path, and on the FRETISH path `environment_signals` (inputs plus modes) then `m_out_atoms`. Modes have to be in it. A scoped requirement's mode is an atom of the lowered formula sitting in neither atom list, and an atom no word names is false at every position, so omitting it would evaluate every scope against a trace where its mode never holds. The FRETISH side is reachable at all because `requirement_to_ltl` emits only X, G, F, U, W and R over propositional connectives, which `prop_formula_internal::try_parse_formula` reads back; a lowering this codebase's own parser cannot reparse returns an empty table and the sweep runs as it did before.

## Tool subprocesses

Every pipe a runner opens must be created with `pipe2(..., O_CLOEXEC)` — `execute_and_capture` in `src/runner/process.cpp` and the formaliser's bidirectional pair in `src/runner/formaliser.cpp`. These runners are called from many scoring-pool threads at once, so a fork on one thread inherits the pipes every other in-flight call has open and holds them past its own exec. The reader waiting on such a call never sees end of file. `pipe2` sets the flag atomically; `pipe` followed by `fcntl` races a concurrent fork. The `dup2` onto the child's own stdin, stdout and stderr clears the flag on those copies, which is what lets the descriptors the child actually needs survive.

`spawn_piped_child` in `process.hpp` is the one fork behind any bidirectional child — currently the formaliser alone — so `ParentDeathPolicy` and `ExecutableLookup` stay the only two things a second user would differ in. Nothing may fork outside `process.cpp`: `posix_spawn` in particular has no attribute for `PR_SET_PDEATHSIG`, which is the whole reason these run on `fork` at all.

A tool's peak resident set cannot be measured below counter's own. A forked child starts as a copy-on-write copy of its parent, and `exec` folds that pre-exec high-water into the child's `maxrss`, so `wait4` reports `max(parent RSS at fork, the tool's true peak)`. `ProcessResult` therefore carries `m_peak_rss_floor_kb` — counter's resident set sampled just before the fork — and reports `m_peak_rss_kb` as zero at or below it rather than passing counter's own footprint off as the tool's. The `tool/<name>/rss_*` counters follow: `calls` counts every invocation, `rss_measured` only those that cleared the floor, and the max, total and threshold counters are over the latter alone, so a mean is `rss_kb_total / rss_measured`. Any change here has to keep that distinction; the `process_runner` suite pins it by spawning a bare shell while holding a 512MB buffer.

`simplify_ltl` runs one `ltlfilt` exec per cache miss. Coalescing concurrent misses into one exec was tried and removed: measured over the corpus at `parallel = 8`, the misses do not coincide, so the mean batch size was 1.012, exec count fell 1.9%, and wall time rose 37% on 46 of 46 paired examples. Any second attempt has to show a batch size above 1 before anything else about it matters.

## External tools

- `ltl2tgba`, `ltlsynt` — from SPOT, built from source via `cmake/spot.cmake`; located via the `SPOT_BIN_DIR` compile macro.
- `black` — LTL satisfiability checker (`black-sat`); found on `PATH` or downloaded/built via `cmake/black.cmake`; path passed as `BLACK_EXECUTABLE_PATH`. **Always run with a timeout**: `black -t <seconds> ...`.
- `ganak` — model counter; downloaded as a release binary via `cmake/ganak.cmake`; path passed as `GANAK_EXECUTABLE_PATH`.
- `node` — runs the vendored FRET formaliser CLI (`vendor/fretCLI.main.js formalize --logic ft-inf --batch`, see `runner/formaliser.hpp`); looked up on `PATH` at run time, not built or fetched by CMake, so it must be installed separately (`nodejs` in `flake.nix`).

## Packaging

Five paths are compiled in as absolutes into the build tree — Spot's `bin/`, `ganak`, `black`, the formaliser script and the dashboard page — and each takes an environment override that wins over it: `COUNTER_SPOT_BIN_DIR`, `COUNTER_GANAK_PATH`, `COUNTER_BLACK_PATH`, `COUNTER_FORMALISER_SCRIPT`, `COUNTER_DASHBOARD_PAGE`. `tool_path_from_env` (`src/runner/tool_paths.hpp`) is the one reader, and every caller must hold its result in a function-local `static`: `getenv` is not thread-safe against a concurrent `setenv`, and every one of these resolvers is called from the scoring pool's threads at once. Reading once also stops a run changing tool half-way through. An empty value reads as unset rather than as an empty path, since the shells and container runtimes these variables travel through export an unset variable as empty, which would break exactly the deployments the override exists for.

Install rules live in `cmake/install.cmake`, every one of them in the `counter` component. `--component counter` is not optional: FetchContent brings its dependencies in with `add_subdirectory`, which brings their install rules with them, and an unqualified install writes Eigen's headers and cpptrace's cmake config beside the binaries, a large amount of material belonging to neither. Spot's binaries carry an absolute libtool RUNPATH naming the lib directory of the build tree they were configured in, so a copy of one anywhere else cannot find `libspot`. Each is therefore staged behind a wrapper that sets `LD_LIBRARY_PATH` to a sibling `lib` directory resolved from `$0` — the same shape `cmake/black.cmake` already used, generated from `cmake/tool-wrapper.sh.in`. Installing a Spot binary without its wrapper breaks silently at the first `ltlsynt` call.

`Config::parallel` defaults to `available_parallelism()` (`include/thread_pool.hpp`): the minimum of `hardware_concurrency()`, the `sched_getaffinity` CPU count and the cgroup CPU quota, each skipped when unreadable and floored at 1. `hardware_concurrency()` alone is wrong under a container, libstdc++ answering it from `sysconf(_SC_NPROCESSORS_ONLN)`, which reports the host's online CPUs and ignores both `--cpuset-cpus` and `--cpus`; a run given `--cpus=4` on a 64-core host sized its pool 64 and oversubscribed the quota 16-fold, with every worker also spawning solver subprocesses. Measured on a 20-core box: 20 unbound, 2 under `taskset -c 0,1`, 5 under `taskset -c 0-4`. The parsing halves of both cgroup formats are pure functions in `src/cpu_limits.hpp` so they can be tested at all, the reads themselves being of fixed paths that exist only under a container.

`-DCOUNTER_GIT_COMMIT=<sha>` (`cmake/version.cmake`) names the commit for a build whose source is a copy rather than a work tree, which is how the image is built. It requires the full 40 characters, the abbreviation being what gets printed rather than what gets recorded. It fills in what git cannot answer and does not get to contradict what git can: a build that has both and disagrees fails rather than picking a side, and a work tree git already read as dirty keeps that verdict, so `COUNTER_GIT_DIRTY` can set the flag and never clear it. Without the argument such a build reports `commit=unknown` and `run_experiments.py` refuses to launch against it.

The Dockerfile's stage layout is load-bearing rather than cosmetic. One stage per fetched dependency, each copying only the cmake module that drives it, because copying all of `cmake/` made an edit to `lint.cmake` cost a full Spot rebuild. Spot dominates that build by roughly two orders of magnitude — 248.1s against black's 3.6s and Ganak's 1.2s, at `BUILD_JOBS=8` on a 20-core machine — so its layer must be keyed on `cmake/spot.cmake` alone. `docs/docker.md` is the user-facing half.

`.github/workflows/docker.yml` builds each architecture on a runner of its own architecture and never emulates, and both build jobs push by digest under no tag, so only the merge job's `imagetools create` publishes one and a half-failed matrix cannot leave a tag resolving for one architecture alone. `cmake/black.cmake`'s architecture guard covers the prebuilt `.deb` alone since 2026-08-27; it guarded the whole Linux branch before that, which failed configure on Linux arm64 rather than falling through to the source build below it — a path with no architecture in it, and the one Darwin has always used. Moving that guard back up breaks arm64 images and nothing else, so an amd64 build will not show it.

## Key types

- `Timing` — `std::variant<Immediately, NextTimepoint, WithinTicks, ForTicks, AfterTicks, Eventually, Always>` (see `requirement.hpp`).
- `ConditionType` — `enum class { Trigger, Continual }` controlling how the condition activates a `Requirement`: rising-edge (Trigger) or at every timepoint where it holds (Continual).
- `Requirement` — holds `m_condition`, `m_response`, `m_timing`, `m_condition_type`, the derived `m_ltl` string, and `m_weakenable`. When `m_weakenable` is false the requirement is locked: the genetic algorithm never mutates it, uses it as a crossover source, or simplifies it. It is part of `Requirement`'s identity (`operator<`/`==`/`hash`). Serialised as the optional JSON key `weakenable` (default `true`, emitted only when `false`). `m_removed` is the removal tombstone — see "Removable guarantees".
- `Formula` — propositional AST with `syntactic_similarity`, `rewrite_post_order`, `n_subformulae`.
- `TransferSystem` — weighted automaton transition matrix for bounded model counting.
- `Count` — `long double` (x87 80-bit: integers exact to 2^64, exponent range to 2^16384). Trace counts are only consumed as ratios cast to `double`, so range matters more than exact integer width; `count_add_overflow`/`count_mul_overflow` report overflow as a non-finite result.
